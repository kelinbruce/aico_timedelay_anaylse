# NextAgent Workflow 能力评审设计

## 1. 背景

NextAgent 面向电信网络智能体，既要处理大量高频、标准化的网络运维问题，也要处理复杂、开放、需要模型探索的问题。

当前仅依赖模型驱动的 loop，可以覆盖长尾问题，但在高频典型场景中存在三个明显不足：

- 响应链路偏长，每次都需要模型重新规划。
- 执行路径不够确定，不利于电信场景中的准确率、审计和故障复盘。
- 对标准化诊断、查询、处置建议等问题，重复探索会浪费成本。
- 有些问题一开始只能靠模型探索，但执行多次后会呈现出稳定路径，如果不能沉淀下来，系统会一直重复付出探索成本。

另一方面，如果只依赖预置 workflow，又无法覆盖复杂、模糊、多步骤和新出现的问题。因此需要同时支持两类路径：

- **workflow 模式**：面向高频、典型、可标准化的问题，用预置流程提升性能、准确率和稳定性。
- **模型 loop 模式**：面向泛化和探索类问题，由模型动态分析、规划和调用能力。

本设计的核心目标，是让 NextAgent 能在请求进入后自动选择合适路径，并允许智能体开发者按业务场景定制选择规则。

## 2. 目标

本次设计希望达成以下能力：

1. **支持两种执行模式**
   - workflow 模式用于高频典型电信问题。
   - 模型 loop 模式用于复杂泛化问题。

2. **支持请求路由**
   - 系统根据规则判断请求应进入 workflow 还是模型 loop。
   - 智能体开发者可以配置路由规则。
   - 高级场景下，开发者可以提供完整的路由 policy。

3. **支持模型规划 workflow**
   - 模型在处理复杂任务时，可以提出一个多步骤 workflow。
   - 该 workflow 经过校验后，可交给确定性引擎执行。

4. **支持 model loop 自学习为 workflow**
   - 对多次执行且路径稳定的模型 loop，系统可以总结出 workflow 候选。
   - 候选 workflow 经过治理、校验和发布后，后续相似问题可以直接走 workflow。
   - 目标是持续提升执行效率和准确率，而不是每次都重新探索。

5. **支持 workflow DAG 优化**
   - workflow 以有向图表达步骤和依赖关系。
   - 系统在执行前校验图结构，并识别可优化的执行计划。

6. **统一 YAML DSL 与 TS workflow**
   - 预置 workflow 使用 YAML DSL，方便业务人员和智能体开发者维护。
   - 模型生成的 workflow 使用 TS 代码形态，表达更灵活。
   - YAML workflow 在运行前编译为 TS 形态，最终都交给同一个引擎执行。

## 3. 非目标

本设计不解决以下问题：

- 不新增对外 Web API。
- 不新增 workflow 的数据库持久化。
- 不实现分布式 workflow 调度。
- 不实现 workflow 快照恢复、断点续跑或回滚补偿。
- 不提供可视化 workflow 编排 UI。
- 不允许模型生成的代码直接在主进程中运行。

这些能力可以后续独立设计，避免当前方案过大、过早复杂化。

## 4. 核心设计

### 4.1 总体流程

用户请求进入 NextAgent 后，系统先进行请求路由：

```text
用户请求
  -> 路由判断
    -> 命中预置 workflow：执行 workflow
    -> 未命中或适合探索：进入模型 loop
    -> 模型 loop 规划出 workflow：校验后执行 workflow
    -> 模型 loop 多次走出稳定路径：自学习沉淀为 workflow
```

也就是说，workflow 和模型 loop 不是互相替代，而是协同：

- 简单高频问题直接走 workflow。
- 复杂问题先走模型 loop。
- 当模型发现任务适合拆成确定性步骤时，可以生成 workflow，再交给 workflow 引擎执行。
- 当模型 loop 多次成功解决同类问题，且步骤稳定时，可以沉淀成新的 workflow，后续同类请求直接复用。

### 4.2 workflow 模式

workflow 模式适合电信场景中的标准化任务，例如：

- 告警定位。
- 指标查询。
- 网络配置核查。
- 常见故障诊断。
- 标准化恢复建议生成。

workflow 的优势是：

- 路径固定，结果更稳定。
- 可提前校验，降低运行时错误。
- 可跳过模型反复规划，提升响应速度。
- 更容易审计和复盘。

### 4.3 模型 loop 模式

模型 loop 模式适合以下任务：

- 用户问题不明确，需要探索。
- 没有匹配的预置流程。
- 任务涉及多个不确定步骤。
- 需要模型动态选择工具、补充上下文或拆解目标。

默认情况下，如果路由没有命中 workflow，请求会回到模型 loop。这样可以保证系统仍具备泛化能力。

### 4.4 请求路由

请求路由由 Agent 内部负责，不能放到 Web 层或 runtime 层。原因是：

- 是否走 workflow 属于智能体业务决策。
- 不同 Agent 的 workflow 能力不同。
- 同名 workflow 在不同 Agent 下可能含义不同。

路由支持两种方式：

1. **规则路由**
   - 开发者配置一组有顺序的规则。
   - 第一条命中的规则决定走 workflow 还是模型 loop。
   - 适合简单、稳定、可解释的场景。

2. **完整 policy**
   - 开发者提供完整路由策略。
   - 适合复杂业务场景，例如结合场景、意图、Agent 配置和 workflow 元信息判断。
   - policy 的输入和输出都受系统约束，不能绕过安全边界。

### 4.5 模型生成 workflow

模型可以在复杂任务中生成 workflow，但生成结果不能直接执行。

系统会把模型输出视为一个候选 workflow，并经过以下检查：

- 格式是否合法。
- 是否符合当前 Agent 的能力范围。
- 是否引用了允许使用的能力。
- 图结构是否有效。
- 是否存在不安全代码或越权行为。
- 是否能转换为系统内部统一的 workflow 表达。

只有通过这些检查后，workflow 才能交给执行引擎。

### 4.6 model loop 自学习为 workflow

有些问题一开始没有预置 workflow，只能通过模型 loop 解决。但如果同类问题反复出现，并且模型多次走出了相似、稳定、可复用的步骤，系统就应该把这条路径沉淀下来。

自学习流程如下：

```text
模型 loop 多次成功执行
  -> 形成安全的执行轨迹摘要
  -> 判断路径是否稳定、可复用
  -> 生成 workflow 候选
  -> 校验、治理、发布
  -> 后续相似请求直接路由到 workflow
```

这里有两个关键约束：

- 学习出来的 workflow 只是候选，不能立刻执行。
- 必须经过校验和发布后，才能进入正式 workflow 列表。

这样既能利用智能体自学习提升效率和准确率，又能避免偶然成功的探索路径被错误固化。

### 4.7 DAG 优化

workflow 本质上是一个 DAG：节点表示步骤，边表示依赖关系。

执行前系统会做两类处理：

1. **校验**
   - 是否有唯一入口。
   - 是否存在缺失节点。
   - 是否存在非法循环。
   - 是否存在不可达步骤。
   - 分支条件是否可安全判断。

2. **优化**
   - 识别没有依赖关系的步骤。
   - 标记可并行执行的部分。
   - 保留有副作用步骤的执行顺序。
   - 生成更适合执行引擎消费的执行计划。

这里的优化是保守的：宁可少并行，也不能改变业务语义。

### 4.8 YAML 与 TS 的统一执行

预置 workflow 使用 YAML DSL，原因是：

- 更适合配置化和业务维护。
- 更容易做版本管理和人工评审。
- 对高频典型场景足够清晰。

模型生成 workflow 使用 TS 形态，原因是：

- 表达能力更强。
- 更适合动态规划出的复杂步骤。

但系统不会维护两套执行引擎。统一策略是：

```text
YAML workflow -> 编译为 TS workflow -> 转为统一 workflow 表达 -> 同一引擎执行
TS workflow   -> 校验和治理      -> 转为统一 workflow 表达 -> 同一引擎执行
```

这样可以避免 YAML 和 TS 产生两套行为，降低长期维护成本。

## 5. 关键规格

### 5.1 模式选择

- 系统必须支持 workflow 和模型 loop 两种模式。
- 未命中 workflow 时，默认进入模型 loop。
- 已选择 workflow 后，如果 workflow 失败，不能悄悄当作成功处理。
- 是否失败后回退模型 loop，必须由明确的策略决定。

### 5.2 路由策略

- 路由只能使用系统接受后的可信请求信息。
- 路由不能使用客户端传入的身份字段覆盖当前身份。
- workflow 必须按当前 Agent 查找，不能跨 Agent 复用同名 workflow。
- 非法路由结果必须安全失败。

### 5.3 模型生成 workflow

- 模型生成的 workflow 是候选结果，不是可执行结果。
- 候选 workflow 必须先校验，再执行。
- 校验失败时，不能执行任何节点。
- 动态 TS 代码必须通过沙箱边界处理，不能直接在主进程运行。

### 5.4 model loop 自学习

- 系统可以从多次成功的模型 loop 中学习 workflow 候选。
- 学习输入只能使用安全的执行轨迹摘要，不能使用原始 prompt、模型原始输出、工具原始输入输出、密钥或附件内容。
- 学习出的 workflow 候选必须先校验、治理和发布。
- 未发布的候选 workflow 不能被请求路由选中，也不能被执行。
- 已发布的 learned workflow 和预置 workflow 一样，必须受当前 Agent 范围约束。

### 5.5 DAG 校验与优化

- workflow 执行前必须校验图结构。
- 非法 DAG 必须在执行前失败。
- 优化不能改变有副作用节点的顺序。
- 优化结果只能输出安全诊断信息，不能暴露 prompt、模型原始输出、工具原始结果、密钥或本地路径。

### 5.6 统一执行引擎

- YAML 和 TS workflow 最终必须进入同一个执行引擎。
- 引擎看到的是统一后的 workflow 表达，而不是两套不同格式。
- 同一个 workflow 图，不应因为来源是 YAML 或 TS 而表现不同。

## 6. 设计取舍

### 6.1 为什么不只用模型 loop

只用模型 loop 最简单，但不适合电信高频典型问题。高频场景更看重确定性、性能、审计和稳定输出，workflow 更合适。

### 6.2 为什么不只用 workflow

只用 workflow 会限制泛化能力。电信运维问题中存在大量长尾场景，用户表达也可能不完整，仍需要模型探索和动态规划。

### 6.3 为什么路由放在 Agent 内部

workflow 是否可用、是否适合当前请求，依赖当前 Agent 的配置、能力和业务场景。放在 Web 层或 runtime 层会破坏 Agent 边界，也容易产生越权或错配。

### 6.4 为什么模型生成 workflow 不能直接执行

模型输出不可信。直接执行会带来安全、稳定性和审计风险。必须先经过校验、治理和沙箱处理。

### 6.5 为什么自学习 workflow 也不能自动直接启用

多次成功不等于永远正确。电信场景中，网络版本、地域、设备类型、客户策略不同，都可能导致执行路径差异。自学习只能生成候选 workflow，必须经过治理、校验和发布后才能用于后续请求。

### 6.6 为什么 YAML 最终也编译为 TS

如果 YAML 和 TS 各自有一套执行逻辑，长期会出现行为差异。统一编译和统一执行可以保证一致性，也降低维护成本。

### 6.7 为什么 DAG 优化采用保守策略

电信运维任务中很多步骤有外部影响，例如查询、调用能力、执行脚本、触发用户确认等。错误重排可能改变结果。首版应优先保证正确性，再逐步提升并行度。

## 7. 风险与缓解

| 风险 | 缓解方式 |
|---|---|
| 路由规则配置错误导致走错流程 | 规则按 Agent Scope 校验，非法配置安全失败 |
| 模型生成不安全 workflow | 只作为候选结果，必须校验和沙箱处理 |
| 自学习固化了偶然成功路径 | 只生成候选 workflow，经过治理、校验、发布后才能使用 |
| YAML 和 TS 行为不一致 | 统一转换为内部 workflow 表达，并用同一引擎执行 |
| DAG 优化改变业务语义 | 默认保守优化，有副作用步骤不随意重排 |
| 功能范围过大 | 不做持久化、恢复、分布式调度和 UI，后续独立设计 |

## 8. 验收标准

评审通过后，后续实现至少需要满足：

- 可以配置规则，让请求直接进入预置 workflow。
- 未命中规则时，请求进入模型 loop。
- 开发者提供的完整 routing policy 输出非法结果时，系统安全失败。
- 模型生成 workflow 时，校验失败不会执行任何节点。
- model loop 多次成功且路径稳定时，可以生成 learned workflow 候选。
- 未发布的 learned workflow 候选不能被路由或执行。
- 已发布的 learned workflow 可让后续相似请求从模型 loop 改走 workflow。
- YAML workflow 能转换为统一 workflow 表达。
- TS workflow 必须通过沙箱边界处理。
- 相同 workflow 图通过 YAML 或 TS 来源执行结果一致。
- 非法 DAG 在执行前被拒绝。
- DAG 优化不改变有副作用步骤顺序。
- 诊断、日志和事件不暴露敏感信息。

## 9. 评审关注点

本次评审建议重点确认：

- workflow 与模型 loop 的职责划分是否清晰。
- 请求路由是否应该由 Agent 内部负责。
- YAML DSL 与 TS workflow 统一到同一引擎的方向是否合理。
- 模型生成 workflow 的安全边界是否足够。
- model loop 自学习为 workflow 的治理边界是否足够。
- DAG 优化首版采用保守策略是否符合电信级质量要求。
- 当前排除持久化、恢复、分布式调度和 UI 是否可以接受。
