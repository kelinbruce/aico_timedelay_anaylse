# BAR-copy能力确认与修复方向

2026-10-29，已从远端更新至 `7351b890`。本轮新增两份原始结果：`result/bare_copy_capability.json`、`result/vm_copy_capability.json`，均保留未改动。

**结论已经推进到具体机制：裸机向Runtime提供BAR-copy能力，虚机明确报告该能力不可用；这与前一轮VM持续出现DMA提交和完成等待请求相吻合。当前优先修复对象是虚机的参数拷贝快速路径能力，涉及实际加载的HAL/驱动包与虚拟化映射能力。**

**尚未隔离的是能力为何缺失：两侧既有物理/虚拟场景差异，也有驱动包差异。因此现在可以确认能力不一致，不能承诺只升级驱动就一定恢复，也不能将业务全部性能差距归于这一项。**

## 1. 查询有效，零值就是不支持

两侧脚本SHA256均为 `c746fea2fe149936176f8ebcf8bac8b373e86a66710be1eb242a068f0739e4fb`，与发布代码一致；均为设备0、queue0、torch2.10.0+cpu、torch_npu2.10.0.post6、Ascend910B4-1。结构体大小16字节、字段偏移0/8均一致。

三次查询全部 `return_code=0`，不是查询失败或解析错误：

| 请求掩码 | 裸机返回 | 虚机返回 | 含义 |
|---|---|---|---|
| `0x2` | `0x2` | `0x0` | BAR memory能力：裸机支持、VM不支持 |
| `0x8` | `0x8` | `0x0` | BAR huge-memory映射能力：裸机支持、VM不支持 |
| `0xA` | `0xA` | `0x0` | 合并查询：裸机有可用能力、VM没有 |

`output_size=0`在两侧都出现；参考实现忽略该大小输出，不能据此把正常返回的掩码判为无效。`0x8`是这里的BAR映射能力，与此前已经配置的1GB hugetlb内存大页不是同一个开关。

## 2. HAL层差异现在有直接哈希证据

| 项目 | 裸机 | 虚机 |
|---|---|---|
| 查询进程可见的驱动包记录 | 26.1.2 | 25.5.0 |
| package_version | 26.1.2 | 25.5.0 |
| ascendhal_version | 7.35.23 | 7.35.23 |
| Innerversion | V100R001C10SPC010B220 | V100R001C23SPC005B219 |
| 实际加载HAL大小 | 2,213,288字节 | 1,861,224字节 |
| 实际HAL SHA256前缀 | `9ea3510f7b613e19…` | `12de70257ec2fcfc…` |
| Linux基础页大小 | 4096 | 4096 |

实际库均为 `/usr/local/Ascend/driver/lib64/driver/libascend_hal.so`。VM哈希与前一轮捕获DMA请求时记录的调用方HAL哈希完全一致，因此这次查到的就是该DMA路径使用的HAL。

`ascendhal_version=7.35.23`相同，不代表二进制相同；本轮文件大小、哈希、包版本和内部版本都证明它们不同。此前一致的11个CANN/torch_npu库没有包含HAL，现在补齐了这一层。

两个JSON记录的是查询进程可见的用户态库和version.info，不是Guest内核模块的构建证明。前一轮微基准的cgroup均有Docker路径，因此要同时处理容器与Guest操作系统的驱动边界。

## 3. 与前两轮证据的连接

已有三层证据：

1. Level2：`Runtime@LaunchKernelV2`的平均增量解释了HostArgs Launch平均增量的93.9%。该比例仅针对当轮带采集的小算例API。
2. ioctl：VM每批256次Sub都出现256对DMA提交/等待请求；两接口合计平均8.173μs/op。裸机相同拦截入口零捕获，仍保留覆盖限制。
3. 本轮：VM对Runtime使用的BAR-copy能力查询明确返回不支持；裸机返回支持。

公开Runtime参考代码中，[CheckSupportPcieBarCopy](https://github.com/hicann/runtime/blob/93b7ec22fb1141fa30c9c746b7dfa9cab5f53e55/src/runtime/driver/npu_driver_mem.cc#L3010)正是通过 `halMemCtl(CTRL_TYPE_SUPPORT_FEATURE)` 查询这些掩码。[H2DCopyMgr::Init](https://github.com/hicann/runtime/blob/93b7ec22fb1141fa30c9c746b7dfa9cab5f53e55/src/runtime/core/src/pool/h2d_copy_mgr.cc#L89)在默认策略下，当BAR-copy可用且大小合适时采用BAR；否则转入DMA，再按条件决定异步或同步路径。

因此，“VM小参数拷贝未能采用BAR快速路径，进入DMA提交/完成等待”已成为有多层证据支撑的解释。尚未直接记录私有copy policy、参数字节数及裸机的实际BAR写入，不能宣称整个调用链已逐函数验证完毕。

这与“相同BAR写指令在VM上单纯变慢”不是同一个解释。本轮证据显示软件能力与可选路径本身就不同。已有直通、大页和隔离配置，不自动保证驱动向Runtime开放相同的参数搬运路径。

## 4. 后续修复顺序

### 先判断容器是否加载了旧驱动库

在**虚机操作系统本身，容器之外**执行以下只读命令，与本次VM JSON对照：

```bash
cat /usr/local/Ascend/driver/version.info
sha256sum /usr/local/Ascend/driver/lib64/driver/libascend_hal.so
```

这一步是选择修复层级，不是再做性能采样：

- 如果Guest操作系统已经是目标驱动版本，但容器仍看到25.5.0/旧HAL，优先修正容器驱动目录挂载或容器内用户态包，使其与Guest实际驱动配套。目录和库的来源需保持一致。
- 如果Guest操作系统本身也是25.5.0，则将Guest完整驱动栈按受支持组合对齐；裸机26.1.2可作为明确的候选验证目标，先核实Ascend910B4-1、Guest OS及物理卡固件的配套。不能只从裸机复制一个HAL库到旧Guest驱动上。

官方虚拟化指南要求Guest驱动与物理卡固件符合配套关系，参见 [Atlas系列虚拟机配置指南](https://www.hiascend.com/doc_center/source/zh/Atlas%20200I%20A2/24.1.RC2/re/virtualmachineconfiguration/%E8%99%9A%E6%8B%9F%E6%9C%BA%E9%85%8D%E7%BD%AE%E6%8C%87%E5%8D%97-24.1.RC2.pdf)。该指南包含Atlas 800T A2等场景，但不是当前26.1.2的兼容性证明；具体目标组合仍需采用对应版本配套表。

### 对齐后以能力与实际调用作为验收

重新启动测试进程，重新执行现有只读查询，输出到新文件，例如：

```bash
python3 query_copy_capability.py --device 0 --out results/vm_copy_capability_after.json
```

观察合并请求 `0xA` 是否返回可用位：参考Runtime接受 `output & 0xA != 0`。返回完整0xA表示两个能力均支持；仅一个位支持仍可能满足对应路径条件，实际是否采用要结合分配和调用验证。

- 如果能力恢复，再运行现有固定小算例，检查两类DMA请求是否消失或显著减少，并比较**无探针基线**与裸机。能力变真但耗时不变，说明还存在实际策略、分配回退或其他成本。
- 如果驱动栈对齐后仍为0，优先交由虚拟化/驱动层核实该版本在此直通组合下的BAR-copy/WC能力提供链路。此时单纯版本差异已降低优先级。

公开参考驱动的 [devmm_is_support_wc_scene](https://github.com/hicann/driver/blob/9b9ad87cb8099fd741c93c93419a904ff05a60ce/src/sdk_driver/svm/v2/master/comm/svm_master_dev_capability.c#L127)在虚拟环境读取 `devdrv_get_bar_wc_flag` 并检查BAR4的bit4；相关能力还受设备能力和部分映射条件影响。这个门控是明确的核实对象，现场应以对应版本实现为准。本轮没有读到该内部标志，不能宣布它已确定为0，也不能强制置位来替代受支持的映射能力。

最后使用原相同8并发数据集验证业务E2E。无探针小算例的上一轮差距为13.194μs/op；8.173μs是有探针窗口里的接口成本，不能直接当作能回收的净差值或业务收益。

## 5. 可以直接交给驱动/虚拟化负责人的问题描述

> Ascend910B4-1，CANN9.1.0、torch_npu2.10.0.post6。裸机实际HAL所属包记录26.1.2，halMemCtl支持特性查询0x2/0x8/0xA分别返回0x2/0x8/0xA；VM实际HAL所属包记录25.5.0，同样查询均成功但全部返回0。VM提交窗口内每256次Sub稳定出现256对DEVMM_SVM_SUMBIT_CONVERT_CPY和WAIT_CONVERT请求，平均合计8.173μs/op。请确认该Guest驱动/容器用户态库/物理固件/虚拟化组合是否支持参数BAR-copy，并提供配套升级或BAR4 WC能力发布方案。验收是Runtime得到有效能力、实际减少DMA请求，并改善无探针下发时间。
