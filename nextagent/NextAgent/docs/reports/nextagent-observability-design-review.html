NextAgent
可观测方案设计

面向电信网络智能体的统一观测体系：以权威运行事实为基础，在可信范围内完成安全关联、异步投影和多形态输出，让单次问题可定位、整体趋势可度量、关键操作可追溯，同时不把观测故障带回业务主链路。

Executive summary

一个事实入口，五种受控视图

NextAgent 不让每个业务模块分别“打日志、记指标、写审计”。请求时间线、模型与能力调用等权威事实，先收敛为统一的安全观测事件，再按各观测面的用途与安全策略生成派生输出。这样既减少口径冲突，也避免日志、审计、指标和 Trace 互相回放、互相污染。

1主链路不被观测阻塞：投影、落盘或上报失败只形成有界降级证据。
2业务事实保持唯一：时间线与领域事实是权威源，观测结果不能反向改写业务状态。
3安全在入口完成：进入异步队列前同步校验和脱敏，投影器看不到原始禁止内容。
4部署形态只换出口：LOCAL 与 REMOTE 共享指标、事件和安全语义，只替换 sink/exporter。
01 / CONTEXT

背景、目标与范围

可观测方案要同时服务网络运维、平台运维、研发集成和合规治理，但不能因此把提示词、模型输出、客户数据或工具载荷复制到更多系统。

网络运维视角

回答“任务是否在推进、哪里失败、结论经过哪些安全阶段”，支持告警分析、故障定位和变更验证。

平台运维视角

回答“服务是否健康、哪个依赖退化、延迟和调用量是否异常”，支撑值守、容量和恢复。

治理与集成视角

回答“谁在什么智能体范围内执行了何种受控动作、结果如何”，形成可关联的审计证据。

设计目标

可定位

使用稳定业务引用贯通请求、模型、能力、网关、沙箱和终态，形成单次运行的问题定位骨架。

可度量

以低基数指标表达成功率、耗时、Token 用量、首个可见内容延迟、依赖健康和观测自身降级。

可追溯

对关键治理事实生成稳定审计事件；审计是派生证据，不替代业务事实和领域记录。

可安全运行

先脱敏后异步，限制字段、大小、标签和队列；任何观测故障不得改变请求结果。

范围与非目标

类别本方案包含本方案不包含
运行观测结构化日志、运行时诊断、指标、Trace、健康检查、执行轨迹骨架新的业务状态机、第二套运行时间线、用日志重建业务真相
合规治理安全审计事件生成、write-only sink、Agent/Owner Scope 关联企业级审计检索门户、法规留存年限的最终裁定
解释能力安全阶段、选择结果、原因码、耗时、用量和终态的可复盘骨架原始思维链、完整提示词、模型原文、工具入参与结果正文
平台集成OTLP、W3C Trace Context、LOCAL 文件与 REMOTE 注入边界外部 APM 的仪表盘样式、告警规则运营和数据湖建设
02 / PRINCIPLES

设计原则

原则的核心不是“记录更多”，而是保证记录有来源、有边界、有容量上限，并在失效时保持业务正确。

事实优先

已存在持久化时间线事实时必须从该事实派生；只有缺少权威事实的边界，才允许使用窄类型适配器补充观测。

同源异投

同一个已脱敏观测事件可被多个观测面消费，但每个观测面拥有独立 coverage、schema、sink 与失败策略。

先安全、后排队

字段分类、shape 校验和脱敏在统一入口同步完成；异步队列和投影器只接触安全快照。

核心无 SDK 污染

业务 contract 不暴露 tracer、meter、provider、exporter、traceId 或 spanId；OpenTelemetry 只停留在观测实现和装配边界。

低基数、有限容量

指标标签使用固定枚举；文本、字段、队列、文件、保留期和去重集合均有明确上限。

降级不改事实

日志写失败、审计 sink 不可用、指标非法、Trace 导出失败或观测队列饱和，都不能改写请求、终态或健康判断。

一句话理解

NextAgent 的可观测系统是“权威事实的安全派生器”，不是业务数据库，也不是把所有内部数据复制到日志平台的旁路。

STEP 01取得可信事实

优先消费时间线；没有权威事件时，由明确 owner 的适配器生成同形事实。

STEP 02同步准入

STEP 03异步投影

按 coverage 生成日志、审计、指标和 Span；某一投影失败不影响其它投影。

STEP 04独立输出

LOCAL 使用分离文件族，REMOTE 使用部署入口注入的网关或 OTLP exporter。

统一观测模型与关联方式

统一事件只携带能够跨观测面安全复用的最小事实；surface-specific 字段由各投影器生成，而不是塞入业务契约。

核心字段

其中 Owner Scope 与 Agent Scope 来自可信身份、持久化记录或可信系统装配；客户端、模型与 Capability 参数不能覆盖。

边界名和 operation 必须是稳定低基数 token；不允许用动态 URL、自由文本原因或 provider 原始标识充当分类。

05 / SURFACES

五类观测面设计

每个观测面解决不同问题。共享输入不等于共享输出：日志用于定位，审计用于治理，指标用于趋势，Trace 用于链路，健康用于即时可服务性判断。

观测面回答的问题主要输出失败语义不是
LOG这次运行发生了什么，卡在哪里结构化 JSONL operational log丢弃 / 降级证据，不阻塞请求业务真相、审计库、指标样本
AUDIT谁在何种范围内执行了什么治理动作稳定 AuditEvent → write-only gatewaydegraded / failed_closed，不伪造成功运行时间线、业务记录
METRIC成功率、延迟、用量和退化趋势如何Counter / Histogram 聚合非法标签或 sink 故障被拒绝单次请求明细、内容检索
TRACE一次请求跨边界的耗时关系如何受控 Span、W3C 传播、OTLP traces保留进程内能力或安全关闭 exporter业务关联主键、正文存储
HEALTH当前是否可响应、关键路径是否可服务/health 与 /health/deep超时或异常显式 DOWN/DEGRADED被动日志回放、真实写操作
LOG

结构化日志：一套物理 writer，两类语义 surface

observation_derived 表达由权威事实派生的请求轨迹；runtime_diagnostic 表达队列、调度、恢复、提交私有阶段和基础设施维护等本地诊断。两者共享唯一 operational writer，但不互相生成。Developer hook trace 等开发者 artifact 仍保持独立，不混入 operational log。

默认定位骨架受理、模型开始/结束、能力开始/结束、终态，以及实际发生的上下文、策略、Hook、沙箱等安全里程碑。
写入保护单 entry 最大 16 KiB；每 destination 异步 buffer 4 MiB；饱和时丢弃新条目，不等待 drain。
本地默认info，文件启用，单段 100 MiB，固定每日轮转，gzip，保留 7 天。
AUDIT

审计：治理事实的派生证据

只有 AuditProjector 可以生成 AuditEvent 并调用 writer。事件包含可信 Owner/Agent Scope、事件名、结果、稳定引用、安全原因码和受控属性。LOCAL gateway 写独立 NDJSON 文件族；REMOTE 只消费部署入口选定的审计网关，不回退到本地文件、SQLite 或 operational log。

覆盖重点请求受理/拒绝、终态、治理类模型失败、能力拒绝/安全失败/策略阻断及其他明确审计事实。
本地实现write-only；4 MiB buffer、100 MiB 单段、每日/gzip、7 天。不是生产合规查询库。
一致性审计失败不能撤销已成立的终态；必须报告降级，不能把未写入伪装成成功。
METRIC

指标：21 个当前代码级 descriptor，固定标签白名单

生产 registry 预创建 OTel instruments，不保留原始样本历史。写入前校验 metric name、类型、有限非负数值、标签和值域，并按稳定事实键去重。requestId、runId、sessionId、tenantId、路径、prompt、provider 原始标识和自由文本原因禁止成为标签。

TRACE

Trace：受控执行层级，而不是按代码调用栈随意展开

Trace 由 timeline lifecycle 建立权威 request / model / capability / workflow node spans，并由 TraceProjector 补充 allowlist 内的 system、gateway 和 request diagnostic spans。跨进程传播采用 W3C Trace Context，远端导出对齐 OTLP traces。

父子关系Request 为根；本地 workflow node、直接 model 和 Tool Loop capability 是 request 的直接子级。
避免双计Workflow 内部模型或能力调用复用节点 span，不再额外生成 MODEL/CAPABILITY 生命周期。
安全降级exporter 凭据/初始化/发送失败不阻断启动；禁止输出 endpoint、凭据、service name 和 raw error。
HEALTH

健康检查：轻量存活与关键路径可服务性分离

GET /health 只验证 runtime authority，当前超时为 250 ms；GET /health/deep 顺序执行 gateway、model provider 与 capability 的最小只读检查，当前各探针 1,000 ms。聚合 UP 返回 200，DOWN 或 DEGRADED 返回 503。

Primary有界、轻量、不触发真实模型调用或业务写入。
Deep探针支持 AbortSignal、timeout 和 critical 语义；只返回状态、原因码、摘要与耗时。
降噪成功探针不逐次写 operational log；状态转换和子系统失败才形成诊断。
PATH

智能体执行轨迹：安全骨架，而非原始推理记录

首版复盘覆盖上下文装配、能力选择、沙箱执行、模型首个可见内容与请求终态。轨迹只允许稳定引用、低基数原因码、有界耗时/用量和安全摘要；完整复盘仍以 canonical timeline 与领域事实为准。

明确边界

不记录 raw chain-of-thought，不保存 prompt、模型原文、工具参数/结果、stream delta，也不为轨迹另建平行 event bus。

6.2 LOG 数据结构与事件目录

2 类 surface · 4 级 level · 开放但受治理的 event vocabulary

“日志种类”在 contract 层固定为两类 surface，而不是固定数量的 event 枚举。每个 owner 可以增加稳定、code-owned 的诊断 event，但必须遵守 catalog、唯一 owner、禁止重复权威事实和安全字段规则。

observation_derived

由 timeline 或窄类型 observation 经 StructuredLogProjector 生成，承载请求、模型、能力、策略、Hook、上下文、附件、沙箱和终态的安全轨迹。

runtime_diagnostic

由 component-scoped RuntimeLogger 直接生成，承载调度、恢复、提交私有阶段、基础设施、维护和执行根异常等本地诊断。

审计判定原则

审计不是运行过程的逐步镜像，而是回答“谁在什么时候，基于什么权限，对什么对象执行了什么受治理操作，结果和证据是什么”。普通生命周期、内部 Hook、重试和技术异常由日志、Trace 或 Metric 承担；只有形成权限、配置、数据、决策、外部副作用或风险责任的事实才进入审计。

07 / SECURITY

安全、隐私与数据治理

可观测系统扩大了数据传播半径，因此 NextAgent 选择“默认不进入、按字段批准”的模型，而不是事后在多个 sink 上各自补救。

禁止进入正式观测主线

  • raw prompt、thinking、模型输出与 stream delta
  • Tool / Capability 参数、结果与附件正文
  • provider / gateway raw body、raw error 与 stack
  • secret、credential、认证 token、绝对路径
  • 自由文本原因和开放式高基数字段
  • traceId、spanId 等 SDK 标识进入业务契约
→

批准后可投影

  • 可信 Owner Scope / Agent Scope
  • 稳定业务引用和低基数 operation/outcome
  • 安全原因码、错误类别和有界摘要
  • 非负有限耗时、计数与 normalized Token usage
  • 枚举化阶段、状态、大小/数量 bucket
  • 经 allowlist 批准的诊断候选字段

安全控制链

1. 可信来源

身份与 Owner Scope 来自 channel/auth；Agent Scope 来自 app composition、hosted selection 或已持久化 session/run。

2. 同步净化

统一入口在排队前执行 shape validation、字段分类和 redaction，禁止内容不会进入异步内存。

3. Surface 减法

每个 projector 再按用途缩减字段；指标拒绝高基数，审计只留治理属性，健康只留机器可读安全摘要。

4. Fail closed

缺失可信 owner/time、字段分类非法或净化失败时，不猜测、不补值，直接拒绝并留下有界降级证据。

受控例外：仅限本地 runtime diagnostic

Tool 执行的 toolInput/toolOutput 以及执行异常的 rawExceptionData 是明确、窄化的本地诊断例外：normal/debug 下均受字段数、递归深度、字符串和 16 KiB entry 上限约束，并对 credential/认证 token 做窄匹配脱敏。它们不得进入 observation-derived log、audit、metric、trace、health、timeline、SafeError 或公共 DTO。Debug 模式也不等于关闭脱敏。

过载与故障策略

队列饱和

ProjectorHost 丢弃新 observation，并为各 surface 记录有界 degraded 结果；业务调用已经同步返回，不等待队列恢复。

单投影器异常

捕获异常并返回 PROJECTOR_FAILED，继续执行其余投影器；不会因 Trace 失败跳过日志、审计或指标。

Writer 饱和

新日志条目 drop，记录饱和计数桶和一次状态转换；不复制 dropped payload，不让一个 sink 关闭另一个 sink。

关闭顺序

01停止生产者

先阻止新的运行事实进入，避免边关闭边增长。

02有界 drain

在超时约束下排空 ProjectorHost 队列。

03分别 finalise

关闭 audit，metrics forceFlush/shutdown；任一失败不跳过后续步骤。

04最后关闭日志

记录 shutdown completed 后再 flush/close operational writer。

容量评审关注点

当前上限可以证明“内存和文件不会无界增长”，但尚不能替代电信级容量结论。生产准入仍需用目标并发、平均/峰值 observation 数、最慢 sink 和深度健康检查频率完成基准，验证 1,024 队列及串行 deep probe 的余量。

审计责任分层

语义完整性 · NextAgent

确定哪些操作必须审计，为每类动作校验 actor、action、target、authority、outcome、scope 和 evidence refs，并生成稳定 auditId。

投递完整性 · Gateway 边界

明确 PaaS 接收确认、超时、重试、at-least-once、按 scoped auditId 去重、积压与缺口检测；不得把“已入队”误报为“已留存”。

留存与保护 · PaaS

由审计服务承担法规/客户要求的留存期、防篡改、加密、访问控制、查询、导出、legal hold 和删除治理。LOCAL 文件不承担该责任。

LOCAL 模式边界

LOCAL audit 的 NDJSON、轮转、压缩和有限保留用于本地运行、开发验证与短期排障，能够证明“可记录完整行”，但不构成生产合规审计库，也不承诺跨主机完整性、长期保留、不可抵赖或监管查询能力。

10 / OPERATIONS

典型运维使用路径

设计价值最终要落到排障、容量和审计流程。以下路径说明各观测面如何协作，同时保持权威事实与派生证据的边界。

单次请求失败定位

  1. 从用户会话或告警取得 request/run 稳定引用。
  2. 查看 observation-derived 日志定位失败阶段与安全原因码。
  3. 使用 Trace 比较 request、model、capability、gateway 耗时关系。
  4. 必要时回到 canonical timeline 核对权威终态。

性能与容量异常

  1. 从请求结果、duration、TTFT、Token 和 capability/gateway 指标判断趋势。
  2. 用 health/deep 区分入口存活与关键依赖退化。
  3. 查看 observability_degradation_total 排除“观测系统自身失真”。
  4. 抽取代表性 request run 做 Trace 细化定位。

安全与审计复核

  1. 从 PaaS 审计服务按可信 Owner/Agent Scope、动作族和目标对象筛选审计证据。
  2. 核对 actor、action、target、authority、outcome 与稳定证据引用。
  3. 需要正文或最终状态时访问授权业务系统，不从审计恢复敏感载荷。
  4. 使用 auditId、投递状态和 PaaS 接收证明确认是否存在审计缺口。
观测自身也必须可观测

projector_projection_total 记录各 surface 的 emitted / skipped / degraded / failed_closed；observability_degradation_total 记录 projector、sink、registry、serialization、required field 和 metric label/value 等失败。恢复/降级只在状态转换时输出 operational milestone，避免正常高频噪声。

12 / DECISIONS

主要风险与评审决策

核心架构风险已经通过边界和有界机制控制；剩余风险主要集中在生产治理参数、外部平台责任和容量实证。

R-01
审计动作覆盖与 PaaS 交付契约尚未闭环

LOCAL 文件本就不是生产合规库，有限留存不是架构缺陷。当前真正缺口是 26 个技术事件尚未收敛为受审计动作目录，正常外部副作用、人工监督、配置变更、敏感数据操作和风险事件覆盖不足；PaaS 接收确认、重试、去重与缺口检测也尚缺验收证据。

建议决策

沿用现有 AuditEventRecord envelope，以七类动作和 required-field profile 冻结语义完整性；由 PaaS 审计服务明确投递确认、留存、防篡改、访问控制、查询和导出 SLA。LOCAL 仅作为本地模式的有限记录能力。

R-02
Trace 采样尚未形成稳定契约

OTLP 与 W3C 路径已具备，但 NextAgent 当前没有对外暴露采样配置。Feature 文档中的“错误 100%、正常 10%”同样是候选值。

建议决策

优先在 collector/平台侧确定 head/tail sampling 与错误保留策略；如需 runtime sampler，先通过 OpenSpec 冻结语义、配置与容量验证。

R-03
SLO、告警与仪表盘不在核心实现内

指标 inventory 能描述事实，但没有统一成功率、P95/P99、TTFT、观测降级与依赖健康阈值，就不能形成有效值守闭环。

建议决策

由部署/运维平台基于现有 21 项 inventory 定义分环境 SLO、告警去抖、窗口与升级路径，并保持标签白名单不变。

R-04
有界不等于已证明容量充足

1,024 observation 队列、4/8 MiB buffer、16,384 dedup 和串行 deep probes 都是明确上限，但仍缺目标规模下的饱和点与恢复时间证据。

建议决策

在容量门禁中覆盖峰值并发、最慢 exporter、磁盘抖动和三探针超时；用 drop/degradation 指标证明业务主路径无回归。

R-05
规格基线仍需治理收口

operational hardening 已勾选完成但尚未归档，Feature 文档中部分建议值与实现默认不一致，容易在对外文档中形成错误承诺。

建议决策

严格校验并归档已完成 change；同步 Feature/Function 文档，把“实现值、候选值、生产策略”三类信息明确分栏。

R-06
Trace 标识与治理边界冲突

当前 trace-aware timeline store 会把 traceId、spanId、traceparent 等 snapshot 写入 inlinePayload.trace，TraceProjector 还在 trace.span.emitted runtime diagnostic 中写入 spanId；仓库级约束则声明 Trace SDK 标识不得进入 runtime timeline 或 operational log。两者不能同时作为长期权威规则。

建议决策

由 OpenSpec 明确选择唯一方案：升级治理边界并给出安全/持久化目的，或移除 timeline snapshot 与成功 Span 日志；同步 contract、event catalog、安全测试和跨进程传播设计。

建议本次评审形成的六项结论

  1. 确认“权威事实 → 统一安全 Observation → 独立观测面”的总体架构。
  2. 确认正式观测面禁止原始提示词、模型/工具正文，并保留窄化的本地 Tool runtime diagnostic 例外。
  3. 确认 LOCAL 与 REMOTE 只替换输出实现，不得改变指标/事件语义或新增静默 fallback。
  4. 确认七类审计动作目录及 PaaS 审计服务的投递、留存、完整性保护、查询和导出责任。
  5. 将容量基准、故障注入、OpenSpec 归档和 push 前语义检视作为生产准入条件。
  6. 关闭 timeline trace snapshot 与仓库治理约束的冲突，形成唯一可实施的 Trace 相关性规则。
13 / CONCLUSION

结论

NextAgent 已形成边界清晰、可替换、可降级且安全默认的可观测基础。其价值不在于增加更多日志，而在于让同一可信事实以适合不同角色的方式被消费。

设计完整性

日志、审计、指标、Trace、健康与执行轨迹都已获得明确 owner、输入、输出和失败语义，未污染核心契约。

电信级适配性

双 scope、安全脱敏、低基数、有界队列、独立文件族、非阻塞降级和可重复门禁符合高可靠运行的基本要求。

生产成熟度

核心能力可以进入集成与验证阶段；审计动作覆盖与 PaaS 审计服务、采样、SLO/告警和容量证据必须在生产准入前闭环。

最终建议：PASS WITH FOLLOW-UP

通过方案设计评审，按 R-01 至 R-06 建立可验收 follow-up。不得通过扩大敏感数据采集或引入高基数标签解决问题；普通观测写入不得阻塞业务主链路，审计强约束操作如需 fail-closed，必须由风险策略与 OpenSpec 显式定义。
