# NextAgent 测试特性文档规划

## 1. 文档目标

测试特性文档面向功能测试、集成测试和验收测试人员，回答以下问题：

1. 当前交付版本中，用户可以观察到什么行为；
2. 正常、失败、取消、降级等分支分别如何呈现；
3. 配置差异会改变哪些可见结果，如何配置并使配置生效；
4. 如何用 Skill、测试数据和受控 adapter 构造可重复场景；
5. live 执行与 history 重建分别应该断言什么；
6. 哪些内容已有当前实现证据，哪些内容尚未进入可执行测试文档。

本文规划的是一套按系统功能逐步扩展的测试文档，不把“对话交互”当作最终范围。首批只发布已经具备相对成熟实现、稳定观察面和可重复测试入口的对话交互专题。

## 2. 与其他文档的关系

| 文档类型 | 主要回答 | 不承担的职责 |
|---|---|---|
| [测试特性树](./NextAgent测试特性树.md) | 系统有哪些能力领域，历史规格如何追溯 | 不作为当前 UI、API 或配置事实源 |
| 测试特性专题 | 当前版本如何表现，正常/异常如何断言，如何配置与构造数据 | 不展开内部类、函数和持久化实现 |
| `openspec/specs/` 与 active change | 产品契约和正在交付的规格增量 | 不直接替代测试人员的操作手册 |
| `docs/developer/` | 架构、开发、部署和调试方法 | 不负责按用户观察面组织黑盒分支 |
| 用户配置和使用指导 | 用户或集成方怎样使用功能 | 不穷举异常分支和测试覆盖矩阵 |
| `docs/ucd/` | 交互设计意图、组件规范和场景设计 | 不能单独证明当前代码已经实现 |

专题文档可以链接开发文档和 OpenSpec 作为证据，但正文只保留测试需要理解的边界。

## 3. 当前事实的判定顺序

每次新增或刷新专题时，按以下顺序校准：

1. 当前 `main` 的产品代码、默认配置和运行时 schema；
2. 当前 `main` 的自动化测试、Skill fixture、场景数据和可重复手测入口；
3. stable OpenSpec；若 `main` 已包含 active change 的实现，则同时核对对应 active change；
4. 开发、部署和用户文档；
5. UCD、roadmap 和历史报告仅用于发现候选范围，不作为“已实现”证据。

代码、测试、规格或文档互相冲突时，专题不得静默选择一个结论。维护者必须在专题中写明基线和限制，并同步修复已确认过期的测试说明。

## 4. 专题准入状态

| 状态 | 含义 | 是否进入测试专题正文 |
|---|---|---|
| `可执行` | 当前代码已实现，正常/异常观察面明确，存在真实环境、Skill 场景或受控 fixture 路径 | 是 |
| `部分可执行` | 核心行为已实现，但部分分支缺少稳定构造方式或 history 证据 | 只写已证实部分，并列出限制 |
| `证据待补` | 代码可能存在，但缺少可重复验证入口或当前规格互相冲突 | 否，只进入维护待办 |
| `规划中` | 仅存在 roadmap、UCD 或未落地规格 | 否，不描述目标行为 |
| `历史快照` | 旧版本曾记录，尚未按当前 `main` 复核 | 否，只保留追溯链接 |

专题中的“文档已发布”只表示当前实现已有可执行说明，不等于功能覆盖了所有未来需求。

## 5. 每份测试特性专题的固定结构

每份专题至少包含：

1. 适用版本、代码基线和范围边界；
2. 用户可见对象和状态词汇；
3. 正常主流程；
4. 异常、失败、取消、降级和边界分支；
5. 配置项、默认值、覆盖规则、生效方式和非法配置结果；
6. live 与 history 的相同点和差异；
7. Skill/fixture 的数据准备、调用顺序、预期和能力边界；
8. 可直接转换为测试用例的覆盖矩阵；
9. 自动化证据和人工检查点；
10. 当前限制、未纳入范围和下一次刷新触发条件。

测试预期使用“用户看到/看不到什么”表达。只有定位失败或解释配置边界所必需的 event 名称才进入正文。

## 6. 发布节奏

下表是文档建设节奏，不是产品交付承诺；后续批次只有满足准入条件后才创建专题正文。

| 批次 | 候选专题 | 本批目标 | 当前文档状态 |
|---|---|---|---|
| 第一批 | 对话交互 | 输入、执行过程、答案、工具成功/失败、三档配置、live/history | 已进入专题 |
| 第二批 | 会话与运行控制 | 新建/切换会话、重试、编辑、取消、并发提交、历史恢复 | 待逐项复核 |
| 第三批 | 补充输入与长任务 | AskUserQuestion、pending input、Cron、后台任务及恢复 | 待逐项复核 |
| 第四批 | 附件与富内容 | 附件、Markdown、Mermaid、PIU、Expand Panel | 待逐项复核 |
| 第五批 | Workflow 与多 Agent | Workflow 过程、子 Agent、路由和失败投影 | 待逐项复核 |
| 持续批次 | 配置、安全与 DFX | 权限、容量、降级、恢复、可观察性和兼容性 | 按成熟度拆分 |

每个批次可以拆成多份专题，不要求一份文档覆盖一个完整系统领域。

## 7. 发布与刷新门禁

### 7.1 新专题发布门禁

- 记录核对日期和 `main` commit；
- 每条用户可见结论至少有一处代码或自动化测试证据；
- 正常路径和至少一个异常/边界路径可重复执行；
- 配置项使用当前 schema 的真实名称和合法值；
- 场景数据明确标注是 Skill、真实依赖数据还是受控 adapter fixture；
- history 结论必须经过 reload/history-load 证据验证，不能由 live 表现推断；
- 不引用规划能力作为当前预期；
- 文档链接、配置片段和相关定向测试通过检查。

### 7.2 刷新触发条件

以下任一项合入 `main` 后，应刷新受影响专题：

- 用户可见 event、状态、文案或交互变化；
- 默认配置、配置 schema、内置规则或生效方式变化；
- Skill fixture、场景数据或受控 adapter 预期变化；
- live、replay、history bootstrap 或持久化投影变化；
- 正常/异常分支的安全错误映射变化；
- 相关 OpenSpec change 归档或基线发生冲突修复。

### 7.3 维护要求

- 专题顶部的基线只在实际复核后更新；
- 删除已失效步骤，不保留“兼容写法”误导测试；
- 新能力先进入候选清单，达到准入条件后再进入正文；
- Skill 无法安全构造的依赖失败必须使用受控 adapter 或集成测试 fixture，不能用文本模拟；
- 缺陷导致的暂时表现不能写成产品预期，应在测试执行记录中单独管理。
