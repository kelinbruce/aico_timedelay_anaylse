NEXTAGENT · CONTEXT MANAGEMENT

给每次回答，准备一张可靠的工作台

上下文管理不是“把所有聊天记录都塞给模型”，而是在安全边界内，挑出当前真正需要的指令、历史、工具、附件和预算，再整理成模型能正确理解的一份输入。

一句话理解：它像一位会整理材料的值班工程师

模型的上下文窗口有限，就像值班台的桌面有限。上下文引擎负责在每次调用模型前重新整理桌面。

▤

不是“记住一切”，而是“这一次摆对东西”

当前问题必须在桌上；相关历史按完整轮次放好；超长日志只放摘要和取件单；工具和附件先过权限检查；还要为模型回答预留空间。最终得到的不是数据库原文，而是一次性的、受治理的“模型工作台”。

作用域校验

使用可信的租户/用户、Agent、Session、Request、Run 坐标取数据，避免串租户、串用户或串 Agent。

会话历史

完整轮次选择

优先保护当前问题；历史只按完整 Turn 纳入，丢弃残缺工具调用、隐藏替换结果与不可见消息。

模型窗口

Token 预算

根据所选模型的窗口大小，扣除回答预留，再决定系统提示、历史、工具和附件各能占多少。

容量治理

多层压缩

通用工具和历史 RAG 使用两套独立微压缩规则；之后处理单个超大内容，必要时再摘要更早对话。

大内容

外置与按需读回

超长日志等内容存入受控工作区，模型只看到预览和引用，需要时通过 Read 分页取回。

提示工程

Prompt 装配

按用途、语言、Agent 版本和运行变量组装系统提示，并划分稳定区与动态区以支持缓存。

能力治理

Tool / Skill 可见性

只披露当前 accepted Agent 被允许使用的能力；拒绝列表具有最终排除权，Capability 生成消息也只能在受控位置与大小限制内插入。

模型路由

选择与 Fallback

选择受治理且可用的模型；切换到不同窗口的备用模型后，会重新做整套装配和预算。

输入材料

附件处理

解析文本、Blob、二进制和不可用附件，纳入预算；正文、路径与原始字节不进入普通诊断。

最终边界

Render 与协议校验

批量加载所选引用，重放 RAG/通用微压缩和大内容替换，校验 Tool Call/Result、附件及 Provider Options，形成统一模型输入。

长期知识

记忆协作

核心 Context Engine 不自行检索记忆；应用层可在首轮调用前按绑定条件召回 L1/L2 记忆和用户特征，经补充预算准入后一次性注入。

连续性

Fork 与 Retry

Fork 取目标点之前的规范历史，不复制运行中状态；Retry 排除已被替换的旧回答。

可诊断

证据与安全降级

Observed Context Engine 投影选中、省略、降级、压缩和模型选择证据；压缩前后 Hook 可扩展，可选 Context Monitor 观察演进且不阻断主路径。

输出：RenderedModelInput

  • 整理后的 messages
  • 允许使用的 tools
  • 模型信息与受控 options
  • 不会携带数据库对象或客户端越权字段

内容太多时，如何保证“装得下”

系统先计算可用输入空间，并保护当前请求。不是粗暴地从字符串中间切断，而是按语义和风险逐层处理。

当前用户请求和最小安全上下文是硬保护项；实在放不下时明确失败，不静默丢掉关键问题。

为什么要重新计算

不同模型的上下文窗口不同。若主模型失败并切换到更小的备用模型，旧预算立即失效。NextAgent 会重新选择 Prompt、历史、能力、压缩策略和最终输入。

1A

通用 Micro-compact：收起旧工具输出

只处理 Bash、Read、Grep、Glob、Write、Python 白名单。候选超过 10 条时保留最近 5 条，把更旧结果换成有界占位；不调用模型。

规则：历史白名单 Tool Result > 10，keepRecent = 5
1B

历史 RAG Micro-compact：全部换成占位

扫描当前请求之前所有 canonical 已完成历史轮次，把其中每一条 Rag Result 都替换成确定性有界占位；不受“超过 10 条”或“保留最近 5 条”影响。当前请求内的 RAG 始终保持完整。

目的：保留历史问答结论，不让旧检索正文持续占满窗口
2

Large-content：预览 + 引用

单个 Tool Result 太大时只留有限预览，原文保存到受控位置；模型可用 offset / limit 按需分页读取。

适合：数 MB 日志、超长命令结果、二进制附件
3

Summary compression：总结更早对话

接近模型窗口上限时，把更早的完整 Turns 生成可追踪 SUMMARY，同时保留最近历史原文；提交带版本校验和幂等键，并清理已失效的 micro-compact state。

适合：经历很多轮仍需继续的长会话

真实执行顺序

选择完整历史 → 通用 + RAG Micro-compact → Large-content 替换 → Token 预算 → 必要时 Summary compression → Render 时确定性重放

RAG 压缩与通用微压缩在同一个 micro-compact 阶段执行，但资格规则完全独立；它不是 RAG 检索本身，也不会删除 canonical 历史。

它负责什么，又不负责什么

边界清楚，才能理解为什么上下文管理不是“所有与聊天有关的功能”。

Context Engine 负责

  • 为本次模型调用选材料
  • 窗口、Token 与压缩策略
  • Prompt 和能力披露
  • 附件与大内容的安全投影
  • 形成最终模型输入

它不拥有

  • 请求生命周期与调度（agent-runtime）
  • 长期记忆生命周期（agent-memory）
  • 模型厂商 SDK（agent-model）
  • Web 会话投影（agent-channel-web）
  • 数据库驱动与持久化细节（gateway-local）

看懂代码前，先认这几个词

展开即可查看通俗解释。

Context Assembly 是什么？

一次“装配决定”的结果：选了哪些消息、哪个模型、哪些能力、采用什么 Prompt、预算如何分配。它还不是最终发送给模型的完整文本。

RenderedModelInput 是什么？

Render 阶段把 Assembly 指向的材料重新批量加载、校验并转换后得到的最终模型输入，包含 messages、tools 和受控模型选项。

Active Context 是什么？

某个 Session 当前可用于继续对话的规范上下文快照。历史选择只从同一个快照出发，避免边读边变导致前后不一致。

Turn 是什么？

一次完整对话轮次，通常从用户问题开始，中间可能包含工具调用与结果，最后以 Assistant 回答或 Summary 结束。残缺 Turn 不会被拆碎后塞给模型。

Owner Scope 与 Agent Scope 是什么？

Owner Scope 回答“这是哪个租户/用户的数据”；Agent Scope 回答“这是哪个 Agent 的配置与数据”。主路径读取需要同时满足两层隔离。
