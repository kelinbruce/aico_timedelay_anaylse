# 算子下发 ioctl 结果分析

分析日期：2026-10-29。已从 `8fcca8ad` 快进更新至远端 `da852c37`，新增 `result/bare_ioctl.tar.gz` 和 `result/vm_ioctl.tar.gz`；保留原始包及已有本地修改。

**本次新增的直接证据：虚机的提交窗口稳定出现两类DMA接口调用，分别是拷贝提交和完成等待，合计平均8.173μs/op；裸机在相同探针入口没有捕获到调用。定位重点已经收敛到Runtime的拷贝路径选择，尤其是BAR-copy与DMA参数搬运的差异。**

尚未证明裸机确实选择BAR-copy，也没有测到两边实际copy policy及拷贝字节数。因此“虚机参数搬运退回DMA”是目前有运行数据和源码相互支持的优先解释；不能把它扩展为所有差距的完整根因或业务可回收时间。

## 1. 本轮结果有效，编译器问题已经关闭

两侧都找到cc/gcc/clang并编译成功；生成的探针库SHA256完全一致，源码和runner哈希与已发布的 `f91a8784` 一致。

每侧都完成了无探针基线和有探针两个独立进程。四个进程均为Sub INT32 `[8]`、设备0、queue0、20轮×256次调用，正确性和亲和性均通过。共复核80轮原始计时，JSON、CSV与摘要统计一致。

两侧torch、torch_npu均为2.10.0+cpu、2.10.0.post6，基准主体和placements哈希一致，已记录的11个CANN/torch_npu用户态库逐项哈希一致。相关已记录环境变量除新增探针路径外匹配，原jemalloc预加载保留。

## 2. 无探针仍有约13.19μs/op差距

以下为各自20轮的中位数，单位μs/op：

| 指标 | 裸机 | 虚机 | VM增量 |
|---|---:|---:|---:|
| 无探针整批完成均摊 | 15.613 | 28.807 | +13.194 |
| 无探针提交循环均摊 | 15.381 | 28.521 | +13.139 |
| 无探针末尾同步均摊 | 0.205 | 0.269 | +0.063 |
| 无探针主线程CPU均摊 | 15.601 | 28.692 | +13.092 |

本窗口完成耗时VM/裸机为1.845。依然主要慢在提交循环，末尾单次同步的均摊差距较小。该指标是整批提交后同步的完成均摊，不是每个算子后同步的延迟。

有探针时裸机为15.564μs/op、虚机32.475μs/op。VM探针进程比自身基线慢12.74%，裸机约为-0.31%。两个进程顺序执行，该变化包含探针影响和窗口变化，不能全算成读时钟成本；也不能用有探针VM去和无探针裸机直接计算可优化收益。

## 3. 虚机每批稳定出现256对DMA请求

VM共捕获10240条调用，零丢失、返回值全部成功。每批256次Sub都对应512条调用，严格按9号、10号请求交替，20批均为256对。两类调用均来自：

```text
/usr/local/Ascend/driver/lib64/driver/libascend_hal.so + 0xd8534
fd目标提示：/dev/davinci_manager
```

fd目标在采集后解析，不能单独作为命令语义依据。请求编码与公开驱动定义相匹配：type为'M'、write方向、编号9/10、编码参数大小344字节。

| 请求 | 按公开源码对应的操作 | 次数/op | 平均μs | P50μs | P95μs |
|---|---|---:|---:|---:|---:|
| `0x41584d09` | 已转换DMA地址的拷贝提交 | 1 | 4.941 | 4.870 | 5.669 |
| `0x41584d0a` | 等待上述拷贝完成 | 1 | 3.232 | 2.690 | 4.169 |

两次ioctl时长之和平均8.173μs/op。逐对计算的和的P50为7.600μs；不使用两个独立P50相加。两个调用之间平均另有3.097μs，整对跨度平均11.270μs，其中包含用户态处理和探针返回/记录等成本，不能全部解释为DMA或额外损失。

等待接口的调用墙钟也不等于纯DMA硬件传输时间，其中可以包含系统调用、驱动检查、同步及调度成本。

## 4. 请求语义与Runtime链路已经对上

固定公开驱动提交 `9b9ad87cb8099fd741c93c93419a904ff05a60ce` 的 [svm_ioctl.h](https://github.com/hicann/driver/blob/9b9ad87cb8099fd741c93c93419a904ff05a60ce/src/sdk_driver/svm/v2/command/ioctl/svm_ioctl.h#L676) 将M/9定义为 `DEVMM_SVM_SUMBIT_CONVERT_CPY`，M/10定义为 `DEVMM_SVM_WAIT_CONVERT_CPY_RESLUT`。

同提交的 [devmm_svm.c](https://github.com/hicann/driver/blob/9b9ad87cb8099fd741c93c93419a904ff05a60ce/src/ascend_hal/svm/v2/devmm/devmm_svm.c#L1219) 中：

```text
halMemcpySumbit -> 9号请求
halMemcpyWait   -> 10号请求
```

此前固定Runtime参考源码的 [NpuDriver::MemCopyAsyncEx / WaitFinishEx](https://github.com/hicann/runtime/blob/93b7ec22fb1141fa30c9c746b7dfa9cab5f53e55/src/runtime/driver/npu_driver_mem.cc#L2742) 调用上述两个HAL接口；[H2DCopyMgr](https://github.com/hicann/runtime/blob/93b7ec22fb1141fa30c9c746b7dfa9cab5f53e55/src/runtime/core/src/pool/h2d_copy_mgr.cc#L219) 在DMA策略下提交拷贝，并在完成路径等待。

因此本轮已经从“Launch内部慢”推进到**持续的DMA提交/完成等待接口成本**。由于测试数据和输出均预分配、每批反复提交同一小算子，这与kernel参数搬运路径吻合；仍需实际能力/policy信息完成最后核实。这里是公开源码语义匹配，没有对现场HAL二进制做带符号反汇编验证。

## 5. 裸机零捕获意味着什么

裸机原生库编译和LD_PRELOAD全局绑定检查均通过，20批都正常完成，但提交窗口的拦截计数为0，状态明确标记为 `no_intercepted_ioctl`。

这支持“两边下发路径可能不同”，但不能直接证明裸机没有任何系统调用、没有DMA或一定走BAR-copy。内联syscall、私有入口、内部绑定、其他线程或采集窗口之外的调用可以绕过这个探针。

不能将VM的8.173μs直接当成两边差值，也不能据其占无探针差距的比例宣称能回收约62%。本轮可以确定的是VM已观测到的接口成本；裸机对应路径成本尚未被同样分段。

## 6. 一个此前没有核验的关键层：HAL

此前一致的11个库不包含 `libascend_hal.so`。本次VM实际调用方HAL哈希为：

```text
12de70257ec2fcfcd0407c02bae769aa50c1e384b3e79f2dc7ad0a27c84a064a
```

裸机因没有捕获调用，旧runner没有为它记录HAL哈希。但loaded_maps显示两边HAL布局不同：裸机可执行段长度 `0x1da000`，VM为 `0x1b7000`，后续段文件偏移也不同。这是需要补齐实际HAL身份的强线索；目前不把映射布局或npu-smi工具版本当成完整驱动版本对齐证明。

所以“torch_npu与Runtime一致”不能解释为“HDK/HAL及内核驱动全部一致”。

## 7. 下一步只检查Runtime所依赖的BAR-copy能力

已新增 `query_copy_capability.py`。它无需perf和编译器，初始化一个很小的NPU分配后，读取实际加载的HAL哈希、driver/version.info，并调用公开 `halMemCtl(CTRL_TYPE_SUPPORT_FEATURE=2)` 查询0x2、0x8、0xA三种掩码。只查询，不强制更改能力或映射。

在本目录各执行一次：

```bash
# 虚机
python3 query_copy_capability.py --device 0 --out results/vm_copy_capability.json

# 裸机
python3 query_copy_capability.py --device 0 --out results/bare_copy_capability.json
```

ABI依据是公开 [ascend_hal_define.h](https://github.com/hicann/driver/blob/9b9ad87cb8099fd741c93c93419a904ff05a60ce/pkg_inc/ascend_hal_define.h#L960)；结构体64位feature、32位device，64位环境下大小16字节。失败返回明确保留为unknown，不解释成不支持。

参考Runtime的 [CheckSupportPcieBarCopy](https://github.com/hicann/runtime/blob/93b7ec22fb1141fa30c9c746b7dfa9cab5f53e55/src/runtime/driver/npu_driver_mem.cc#L3010) 检查0x2/0x8；[H2DCopyMgr::Init](https://github.com/hicann/runtime/blob/93b7ec22fb1141fa30c9c746b7dfa9cab5f53e55/src/runtime/core/src/pool/h2d_copy_mgr.cc#L89) 在默认策略下根据能力与大小选择BAR-copy或DMA。0x8对应这里的BAR映射能力，与已配置的1GB hugetlb大页不是同一开关。

| 查询结果 | 修复对象与下一步 |
|---|---|
| 裸机支持、VM不支持 | 优先处理虚机HDK/驱动向Runtime提供的BAR-copy能力；结合实际HAL版本与受支持的WC/映射路径核实，目标是使小参数能够使用受支持的快速拷贝路径 |
| 两边都支持 | 继续核实实际Runtime策略、参数大小或分配/映射失败回退；能力可用不等于策略已采用 |
| HAL哈希/版本不同 | 先核实具体HDK差异及兼容关系，避免继续只对齐torch_npu而遗漏HAL |
| 查询失败 | 依据实际返回码和库版本处理，不能把失败解释为能力false |

公开驱动的 [svm_master_dev_capability.c](https://github.com/hicann/driver/blob/9b9ad87cb8099fd741c93c93419a904ff05a60ce/src/sdk_driver/svm/v2/master/comm/svm_master_dev_capability.c#L127) 在虚拟环境还检查driver维护的BAR4 WC标志，普通BAR能力也受基础页大小等条件影响。这提供了明确的能力传递检查点，但不能在没有现场标志的情况下断言它就是失败条件。QEMU mmap、PCI Prefetchable和resource_wc节点的存在并不自动证明Runtime得到同样能力。本轮也没有直接测得Stage-2属性或每次MMIO退出。

修复验收首先看：受支持的参数快速路径是否实际启用、这对DMA请求是否消失或明显减少、无探针Sub完成时间是否接近裸机。再用原来相同8并发测试验证业务E2E，不能由小算例直接承诺业务收益。

## 8. 日志中的npu-smi异常与探针修正

原始有探针日志两侧都有 `npu-smi info` 超时；无探针进程同命令成功。原runner把探针LD_PRELOAD继承给了外部元数据命令，这个干扰需要修正，超时的确切底层原因本包没有跟踪。

已修正runner：外部npu-smi/lscpu等元数据子进程只移除本探针预加载，保留原jemalloc。新只读能力检查也不使用探针。本轮微基准的正确性与亲和性均通过，可保留运行路径证据，但有探针12.74%的时间变化和元数据异常不能忽略；不需要为了已有计数结论重新跑完整Level2矩阵。

当前16项开发测试通过，包括ioctl透传、采集窗口、元数据子进程环境隔离和只读查询的ABI/错误状态。新能力查询与元数据修正尚未在现场Linux/NPU验证。
