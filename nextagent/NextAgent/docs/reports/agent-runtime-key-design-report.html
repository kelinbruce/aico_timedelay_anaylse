一页结论

智能体运行时的定位不是“聊天接口”，而是承载长链路智能体执行的治理层。它把 Web UI、未来 IM/A2A/AgentLink/事件中心等入口统一成相同的运行时命令，把模型、工具、Skill、InvokedAgent 等执行统一纳入可取消、可恢复、可审计的生命周期。

用户价值

看得见过程，控得住执行

用户能看到流式回答、思考/进度、能力调用步骤和最终结果；同时能取消运行中请求，重试或编辑最近结束的请求。

工程价值

入口不再各自实现状态机

所有入口只做协议适配和事件投影，请求执行状态机、准入、队列、终态提交和恢复都由 runtime 统一承担。

演进价值

为领域智能体二开保留边界

能力、策略、Hook、模板、Assembly 可定制；但不能绕过 admission、session isolation、checkpoint、terminal commit 和 observability。

核心判断：当前设计已经把“用户体验”和“运行时正确性”拆清楚。用户看到的是会话、流、步骤和结果；开发者接入的是命令、事件、能力、上下文、网关和 Hook；系统内部坚持单一事实源和单终态提交。

系统上下文与用户黑盒能力

ADNClaw 智能体运行时为 Web 交互、Agent 执行、能力调用和平台服务提供统一执行底座。Web UI 是用户入口，Runtime 是请求执行治理层，Agent 是被托管的业务执行者；Skill、Tool、InvokedAgent、Model、Context Engine 都是 Agent 执行过程中使用的能力或服务。

不是普通聊天

一次用户请求可能持续较久，期间会调用模型、工具、Skill、远程 Agent、附件和用户确认。

不是前端状态机

取消、重试、编辑、终态结果、历史可见性必须由后端权威状态决定，不能由浏览器本地推断。

不是单进程内存任务

浏览器刷新、服务重启、外部调用返回、终态提交失败都需要可恢复、可审计的持久化边界。

请求处理链路

阶段Runtime 黑盒行为上下游配合输出事实
1. 入口接收 Web 通道把 HTTP 请求转换成 runtime submit 命令。 agent-channel-web 解析身份、会话、附件引用；不直接执行 Agent。 标准化命令进入 RuntimeCommandPort。
2. 准入校验 检查会话归属、输入有效性、附件数量和系统容量。 agent-session 提供会话和所有权；agent-attachment-runtime 校验附件。 非法请求直接拒绝；合法请求进入执行。
3. 创建执行边界 写入用户 root message，创建执行记录和初始工作上下文。 store/gateway 持久化历史消息、执行记录和初始恢复点。 REQUEST_ACCEPTED 过程事件。
4. 有界调度 按全局并发、队列和会话 active/pending 深度调度执行。 SessionLaneService 保证同一会话默认单 active request。 请求进入 queued/executing 状态。
5. Agent 执行 托管 Agent，提供执行记录、工作上下文和事件端口。 Agent 调用 Context Engine 组装模型输入，调用 Model 生成思考/内容，必要时选择 Skill/Tool/InvokedAgent。 LLM_THINKING_DELTA、LLM_CONTENT_DELTA、CAPABILITY_STARTED 等。
6. 能力调用 在模型/能力外部调用前后保存恢复边界，支持取消和避免重复副作用。 Capability SPI 路由到内置工具、Skill、本地脚本或远程平台能力；Gateway 处理平台服务访问。 能力结果事件；需要保留时写入 capability result 历史消息。
7. 终态提交 先持久化最终回答、能力结果、执行状态、终态事件和恢复快照，再允许对外展示终态。 TerminalWriteCoordinator 负责终态提交边界；channel 只投影已提交事件。 REQUEST_COMPLETED / REQUEST_FAILED / REQUEST_CANCELED。
8. 流式投影 把统一过程事件交给通道投影策略。 agent-channel-web 转换为 SSE/WS StreamEnvelope；断线后按 sequence replay。 浏览器看到状态、步骤、内容和最终结果。

核心设计：Runtime 如何保证请求正确执行

运行时的核心不是某一个类，而是几类事实源和控制边界的组合。它们共同保证同一个请求只有一个生命周期解释、一个终态结果、一个恢复路径。

核心事实源与诊断视图

历史事实

SessionMessage

用户输入、最终助手输出、需要保留的 capability result。历史展示默认读取它。

生命周期

执行记录 Run Execution Record

一次请求执行尝试的标准运行记录；代码名为 RequestRun，包含 runId、状态、版本、重试次数、终态提交状态和锁信息。

工作内存

RequestContext

一次 run 的 requestContextId、messageRefs、activeStepId、executedCapabilityTraces。

恢复快照

RequestContextCheckpoint

模型/能力外部调用前后和终态边界的可恢复快照，防重复副作用。

过程事实

RunTimelineEvent

流式展示、关键步骤、降级、用户输入暂停、终态结果的 canonical event。

诊断视图

ExecutionTrace

聚合一次请求的模型、能力、降级、耗时与结果，服务排障和复盘。

为什么不能混用事实源

错误做法风险正确边界
把 token 增量长期存成历史历史恢复依赖流缓冲，重连和清理复杂。增量默认 live-only；最终历史写入 SessionMessage。
让 session 负责执行状态历史查询与执行锁混在一起，重试/编辑容易错。执行记录管生命周期，session 管历史和 latest 投影。
让 Agent 直接提交终态消息失败重试、重复 terminal、可见性替换难以统一。Agent 返回业务结果，runtime 做终态提交。
用 checkpoint 做聊天历史checkpoint 是恢复工作态，不适合用户历史展示。checkpoint 只服务恢复和幂等。

主流程

1. 入口适配Web REST 接收输入和附件引用，转换为 runtime command。
2. 准入与建模验证身份、会话、附件、latest 规则，创建 root message 与执行记录。
3. 有界调度全局并发、队列、会话 active/pending 控制，默认单会话串行。
4. Agent 执行Agent 调用 Context Engine、Model、Capability，并发出中间事件。
5. 终态提交写最终消息、run 状态、终态事件、checkpoint，再投影给客户端。

事件流与历史显示的关系

数据用途持久化策略
LLM_CONTENT_DELTA / LLM_THINKING_DELTA运行中实时渲染答案和思考/进度。默认 live-only，可放入有界 replay buffer。
CAPABILITY_STARTED / CAPABILITY_COMPLETED展示工具、Skill、Agent 调用步骤。按 key-step 策略可持久化。
REQUEST_COMPLETED / FAILED / CANCELED / SUPERSEDED唯一终态解释。终态必须持久化并在 durable commit 后投影。
SessionMessage历史打开和上下文组装。持久化；默认只返回 visible 历史。

可靠性、恢复与治理机制

电信运维场景要求失败可解释、执行可取消、外部副作用不重复、过载不拖垮系统。运行时通过有界执行、checkpoint、单终态提交和低基数监控来满足这些要求。

有界执行

并发与队列

默认 globalExecutionConcurrency=50、globalQueueCapacity=100、perSessionActiveExecution=1、perSessionPendingDepth=3，使用虚拟线程执行模式。

取消与替换

Latest Request 规则

取消只作用于非终态请求；重试/编辑只作用于最近已结束请求；同会话新请求可 supersede 队列中或安全边界上的旧请求。

恢复

Checkpoint before / after side effect

模型或能力外部调用前保存幂等边界，返回后保存结果引用；终态提交失败进入 pending terminal commit，由恢复路径幂等补交。

重连

SSE / WS Replay

客户端携带 lastSeenSequence，服务端从 replay buffer 连续补发；缺口过大时刷新最近可见 SessionMessage。

生命周期 Hook

Hook 是受控治理边界，不是旁路监听器。系统 Hook 可承担 checkpoint-before-side-effect 等不可禁用的安全门；自定义 Hook 可做治理、审计、参数收窄或结果投影，但不能直接改变 Runtime 状态机。

BEFORE_REQUEST_ACCEPT准入、配额、请求元数据
BEFORE_PLANNING规划提示、上下文装配 hint
BEFORE_MODEL_INVOKE模型输入、安全门、参数策略
AFTER_MODEL_RESULT模型结果投影、tool-call 约束
BEFORE_CAPABILITY_INVOKE能力参数、权限、checkpoint
AFTER_CAPABILITY_RESULT结果净化、摘要、持久化前投影
BEFORE_AGENT_TERMINAL终态消息、最终审计、提交前保护
执行顺序：SYSTEM → CUSTOM → order → hookId 结果语义：CONTINUE / BLOCK / DEGRADED / SKIPPED 变更方式：BoundaryMutation

监控口径

层级监控重点约束
Runtime请求接受、拒绝、排队、终态、取消、重试、编辑、恢复。以执行记录和 canonical lifecycle 为准。
Core / Modelprompt 长度、首字/首 token 时延、chunk 间隔、总耗时、模型失败。不泄露 prompt、thinking 或模型原文。
Capability工具/Skill/InvokedAgent 成功率、失败类别、超时、耗时。不把 raw args/result 放进聚合标签。
Channel投影、投递、慢客户端、重放缺口、断连恢复。不把通道异常解释成 runtime 执行失败。

设计结论： ADNClaw Runtime 将智能体执行从“会话中的一次回答”提升为“可控、可恢复、可审计的一次运行”。它通过清晰接口隔离 Web 体验、Agent 业务循环、能力执行和平台网关，为多入口接入、托管部署和领域智能体二次开发保留稳定边界。
