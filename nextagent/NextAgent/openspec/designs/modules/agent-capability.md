# agent-capability

## 职责

承载 capability registry/execution boundary，统一 Tool、Skill、Agent 等能力类型的 startup provider contribution assembly、provider config normalization、discovery、catalog governance、disclosure、invocation、result adapter、replay policy disclosure 和 recovery 边界。最小内核启用通用 capability descriptor/invocation 形态下的内置 `read` 和 `bash` capability。Capability 也是 execution file access 的 tool-facing owner：通过 resolver-backed `WorkspaceFilePort`、sandbox request preparation、Skill resource projection 和 cleanup jobs 管理 `workspace/`、`.nextagent/`、`temp/` 的能力侧访问。

本模块拥有 ToolSearch 输入校验、受治理 deferred descriptor 查询、安全结果投影和 request-local activation patch；不直接执行搜索命中的能力，也不披露 provider 私有事实。

## 非职责

不直接拥有 request lifecycle、Web transport、model provider SDK、runtime recovery classification、terminal lifecycle、audit sink、memory lifecycle 或 app composition。不把 read 文件访问 hardcode 到 `agent-core`；未启用或不可解析 capability 必须 safe rejected。不拥有 execution workspace resolver 实现、runtime workspace root 派生、gateway sandbox adapter 执行、provider-private memory lifecycle 或 app-level ready gate。它不读取 raw system config，也不把 provider contribution snapshot、discovery/executor internals 或 `WorkspaceFilePort` 暴露给 `agent-app`。

## 依赖

允许依赖 `@nextagent/agent-common` 和 `@nextagent/agent-contracts/capability` public subpath。不依赖 runtime/core implementation、Web channel、model implementation、gateway adapter 或 gateway contract。

## 核心设计落点

- `GovernedCapabilityInvocationPort` 是同参自动 retry、input/output schema validation、result normalization 和单结果容量的唯一 owner。`maxRetries` 缺省 1、有效域 0..5；只对 `IDEMPOTENT` descriptor 的 retryable `UNAVAILABLE`/`TIMEOUT` 最终事实重试，父取消优先且中间 attempts 不可见。
- 所有 first-party Tool 和扩展 Capability 必须交付同一个严格 `CapabilityInvocationResult`。`DEGRADED` 只表达复合目标的可用部分成功；合法空结果、声明上限截断、非零进程退出、pending control 或仅触发 fallback 不构成降级。
- 成功与失败共用 `256000` UTF-16 code unit 容量、完整 violations 和大结果外置回读路径；容量内诊断不截断，raw exception、非法输出、路径、credential 和 provider response 不跨出执行边界。

- 落实 `architecture/core-contracts.md` 和 `architecture/capability-spi.md` 的 capability descriptor、provider config、catalog、invocation request/result 和 generated message/context patch 边界。
- 拥有 `createCapabilitySubsystem({ ... })` 的 capability composition entrypoint。该入口接收 validated provider configs、external owner providers、plugin providers 和 trusted resolver/gateway/adaptor options；内部先创建 internal owner-owned providers，再合并 external owner providers 和 plugin providers，最后把 validated provider configs 转换为 config-driven providers。config-driven 转换必须在 internal/external/plugin provider facts 已知后执行，以拒绝用户配置复用 framework/reserved、owner-contributed 或 plugin-contributed provider id。随后 subsystem 验证/freeze provider snapshot，创建 catalog discovery 集、executor lookup、capability provider facts、startup validation/report hooks 和 cleanup jobs；返回 `catalog`、`invocationPort`、`capabilityProviders`、`validateStartupRegistration()`、`collectSkillScanReport()` 及 cleanup/maintenance jobs，不返回 provider snapshots、discovery/executor instances、provider configs、standalone diagnostics 或 `WorkspaceFilePort`。
- 接收 trusted startup plugin composition materialized 的 plugin providers，并把它们作为普通 provider 纳入同一 provider assembly、catalog governance 和 invocation path。首版 plugin provider 必须是 `CUSTOM + providerType=nextagent-plugin-tool`，只允许 `TOOL` descriptor，且必须通过 Agent `capabilityBindings` 显式启用后才可见、可搜索、可执行。
- plugin provider id 必须由插件作者显式声明，`agent-app` 不从 `pluginId` 派生 provider id；provider id 必须满足既有 safe id vocabulary，且不得复用 framework reserved provider、owner provider、SkillHub provider、system/local Agent provider 或其它插件 provider id。首版 plugin provider 每个插件最多 4 个，remote plugin provider discovery、SkillHub-delivered plugin provider、Agent-package-delivered plugin provider、plugin-provided `SKILL` / `AGENT` descriptors 均为 deferred scope。
- 对 plugin provider 使用统一 wrapping：校验 provider identity、discovery identity、descriptor schema、duplicate capability id、required dependency、config override、executor lookup、discovery result、descriptor provider/kind/type consistency 和 output envelope；EAGER discovery 在 startup/readiness 阶段进入 candidate baseline，SEARCH discovery 在 request-scope catalog query/resolve 中按 trusted criteria 延迟调用。SEARCH discovery 必须有 timeout/cancellation、safe error mapping、diagnostic 和 result validation，且只接收 safe owner/request context、`agentId`、`agentVersion`、`agentAssemblyRef` 和 requested capability narrowing。插件 provider 的 diagnostic 只能包含 plugin/provider/capability/agent/assembly stable ids、reason code、bounded summary 和 low-cardinality outcome。
- plugin provider visibility 不由 plugin registry membership 决定。缺失 matching enabled `AgentAssembly.capabilityBindings` 时，plugin Tool 不得进入当前 Agent 的 `listAvailable`、search、resolve 或 invocation path；matching `enabled=false` 必须隐藏该 Tool。Provider/condition selector 可以授权 SEARCH provider 被搜索，但返回 descriptors 仍必须经过 conflict resolution、availability/model visibility、exact disabled binding 过滤和 invocation eligibility 检查。
- 内部创建可信 builtin provider contribution `builtin-tools`，通过 `ToolCatalog` discovery、catalog governance 和 `BuiltinToolExecutor` 暴露最小内核内置 `read` 与 `bash` capability：`read` 提供 workspace-relative 单文件 line slice；`bash` 提供 workspace-scoped、只读诊断型 shell 执行入口，并只拥有 deterministic tokenization、timeout/output bound 和 malformed quote 修正提示，不拥有 shell built-in / shell composition / executable deny 的最终政策判断；命令已进入 sandbox 且以非零 exit code 结束时返回 bounded `DEGRADED` structured result 供后续模型步骤消费，而 policy rejection、sandbox unavailable、platform unsupported、timeout、invalid response shape 和 output overflow 仍保持 safe failed/timed-out outcome；quoted syntax malformed 时，Bash 必须在 sandbox 前以 `COMMAND_NOT_ALLOWED` + `BASH_COMMAND_UNCLOSED_QUOTE` safe reason 拒绝，帮助模型修正而不自动补全命令；未启用、依赖缺失或不可解析 capability safe rejected。
- 保留 Tool、Skill、Agent 作为 Capability 类型的统一执行边界，不形成平行执行机制。
- 拥有 `architecture/skill-manifest-contract.md` 定义的 Skill manifest parser、descriptor mapper、safe diagnostic production 和 `CapabilityDescriptor.metadata -> SkillMetadata` typed accessor 实现；parser-only `SkillFrontmatter`、metadata value normalization 和 validation intermediates 留在本包 implementation boundary。`SKILL.md` 字节解码在 discovery（`parseMetadataViewFromFile`）和 invocation（`loadCanonicalBodyViewFromFile`）两路径共用同一 BOM 感知 decode 助手：UTF-8（含 BOM，剥离）接受，UTF-16/GBK/二进制以 `SKILL_MD_UNSUPPORTED_ENCODING` 拒绝且不进入 catalog；`readSkillFrontmatterSourceFromFile` 公共导出作为架构边界标记保留。Skill Tool `validateInlineBody` 拒绝含 `U+FFFD` 的 canonical body，返回 `EXECUTION_FAILED`（`category=VALIDATION`），作为编码兜底。
- 拥有 `LocalSkillDiscovery` adapter：`local-skills-system + LOCAL_DIRECTORY + EAGER` 消费 app composition 合成的 `configRoot/skills` trusted source fact；`local-skills-agent-owned + LOCAL_DIRECTORY + SEARCH` 通过 trusted Agent package source locator 定位当前 Agent 的 `configRoot/agents/{agentId}/skills`。两类 local source 均复用标准 `SKILL.md` parser/mapper，不创建 local-only manifest schema、DTO、catalog 或 invocation contract。
- 拥有 remote Skill content source behavior 和 provider-private installed index / loading facts；但远端 list/search 与 content fetch 只能通过 app-injected remote access boundary 完成，并且 access port 返回 normalized staged Skill folder，而不是 endpoint、package bytes、archive kind 或 service-private payload。`agent-capability` 只做 staged folder intake validation、root `SKILL.md` validation、managed install publication、catalog governance 和 provider-neutral content consistency 记录，不能直接 import HTTP client、fetch SDK 或 remote adapter private implementation。
- Discovery adapter 只返回 candidate descriptors/facts；catalog 负责 Agent binding gate、availability verdict、conflict extension point 和 `listAvailable`/`resolve` 一致治理。
- Discovery SEARCH criteria 只包含 trusted owner/request context、`agentId`、`agentVersion`、`agentAssemblyRef` 和 optional requested capability narrowing，不消费 runtime-facing `AgentAssembly`、`capabilityBindings`、`boundCapabilityIds`、availability verdict、routing policy 或 conflict result。
- Agent discovery 复用统一 Capability Catalog。`agent-capability` 通过 app-injected `AgentDiscoverySource` 读取已编译 `AgentAssembly` safe facts，并投影为 `CapabilityDescriptor(kind="AGENT")`；`builtin-agents + EAGER` 表示 builtin Agent，`local-agents + EAGER` 表示顶层 local Agent，`local-subagents + SEARCH` 表示 parent-scoped local subagent。Agent descriptor 不携带 raw package path、agent.yaml、prompt/Skill body、provider-private loading fact 或 execution authority。
- Agent descriptor 的可见性由 catalog governance、Agent binding、availability、conflict 和 descriptor metadata 共同决定。`agentInvocation="NONE"` 的 assembly 不可作为 delegation target；`PARENT` subagent 只能在 parent Agent scope 下作为 SEARCH candidate 暴露；top-level user invocable Agent 与 model-invocable delegation 是不同治理维度。
- Catalog 将 builtin EAGER、system local EAGER 和 default-enabled Agent-owned local SEARCH candidates 纳入 request-scope 默认候选；非 reserved SEARCH provider 仍按 explicit enabled binding 触发。Explicit disabled binding、availability、conflict/shadowing、model visibility 和 invocation eligibility 对所有候选统一生效。
- 冲突裁决采用统一 governed algorithm：同一 provider scope 下无法证明为 stable duplicate 的同名 candidate 必须整体 reject；跨 scope 同名 candidate 按 explicit binding > agent-scoped > bundled > system-local > external priority 选出唯一 winner，其余 candidate 进入 shadowed/rejected 诊断，不得形成多个 model-visible entry。
- Agent-owned local Skill 在同一 Agent scope 内优先于 system local Skill；本地 Skill 不覆盖 `BUNDLED` builtin capability；同一 local source scope 内重复 `capabilityId` 必须 safe rejected 而不是 silent overwrite。
- Source-owned loading facts 只保留在 provider/source implementation boundary；descriptor、metadata、diagnostic、model context、stream、安全错误、Web/API response 和 audit detail 不得包含 raw local path、Agent package internal layout、full Skill body、loading key 或 content loading authority。
- Executor 按 catalog-resolved descriptor 的 `provider.providerId + kind` 分派，只返回 `CapabilityInvocationResult`，不直接写 runtime timeline、session messages、checkpoints、audit sinks 或 terminal commits。
- capability invocation boundary 本身允许被同一模型 round 并行消费，但公共 contract 不变：仍然只接受 `CapabilityInvocationRequest`、返回 `CapabilityInvocationResult`。若 provider 或受控依赖拥有可变状态、副作用或外部资源，它们必须自行保证重叠调用下的一致性，而不能依赖 core 串行化。
- capability implementation 不拥有 risk policy truth。Tool/Skill/Agent executor 只提供 restricted-operation safe summary、消费 runtime/app-composed policy outcome 并在不允许时停止目标执行；不得在 builtin Tool、Skill 或 Agent implementation 内各自实现第二套 policy DTO、authorization store 或 `POLICY_APPLIED` 写入路径。
- `Edit` builtin Tool 与 `Read` / `Write` 复用同一个 `workspaceFiles` dependency、同一 run-scoped full-read snapshot authority 和同一 cleanup lifecycle；Tool 自身不得绕过 `WorkspaceFilePort` 直接触达 host filesystem。
- request-directed `targetSkill` 仍然必须通过同一个 catalog resolve + invocation path；capability 不拥有 user-trusted routing decision，只提供 governed descriptor visibility、availability 和 execution facts。
- directive-derived `targetSkill` 和 acquisition-produced Skill descriptors 也必须通过同一个 catalog resolve + invocation path。Capability 不解析 `$skill:`/`$workflow:` 文本，不拥有 routing decision；它只提供当前 Agent Scope 下受治理的 descriptor visibility、availability、kind/type 和 execution facts。
- `Workflow` builtin Tool 通过标准 Tool catalog/invocation path 调用 app 注入的 `WorkflowExecutionToolPort`；它只接受当前 Agent Scope 可见的 `WORKFLOW` recipe，映射完成、失败、取消或等待结果为安全 `CapabilityInvocationResult`，不拥有 routing-level workflow dispatch、resume、recipe store 或节点执行。
- Capability descriptor 必须暴露 `CapabilityReplayPolicy` 或等价 replay classification；runtime 用该事实决定 pending invocation 在 recovery 中 fail closed、skip、reuse result 或 safe replay。
- Capability invocation 必须接收 runtime 构造的 stable idempotency context/key 和 cancellation context；provider 不得自造 owner/agent/request scope。
- capability invocation audit 通过 executor safe fact -> runtime/observability canonicalization 路径集中派生。具体 capability implementation 不直接调用 `AuditEventWriter`，也不决定 audit schema、terminal uniqueness 或 sink retry。
- Tool authoring 使用 provider-neutral `ToolMetadata`、`ToolDefinition` 和 `defineTool`；builtin Tool 只能通过 owned builtin Tool list 显式注册，后续新增 builtin Tool 时必须导出 `ToolDefinition` 并加入该 list，不得扫描目录、依赖 import side effect、自注册或从配置创建 Tool。
- Memory tools 使用同一 provider-neutral Tool SPI，但 `memory-tools` provider contribution 由 `agent-memory` 通过 public factory owning。`agent-capability` 可以接收 `agent-app` 传入的 external memory provider contribution，但不得导入 `agent-memory`、memory gateway ports、`LongTermMemoryToolPort`、memory extraction/aging implementation 或 memory-specific dependency names。Memory tools 的 exposure gate 由 app composition、AgentAssembly binding 和 frozen `MemoryConfig` 共同决定。
- Capability result 的 request-local context patch 只使用 canonical `modelId` 与 closed `ModelInferenceOptions`；`providerOptions` 只允许来自已接受的受治理 Skill metadata。Capability 输出不得携带 provider identity、access config 或平行模型选择事实。
- 内置 Agent tool 是 `Capability(kind="TOOL")` 的一个 Tool entry，不是 Agent kind 的平行执行通道。它通过 `RuntimeCapabilityResolver` 解析 governed `AGENT` descriptor，校验 `{ agentId, prompt }` 输入，拒绝 self-invocation 和未授权 delegation，再通过 `SubagentExecutionPort` 调用 runtime-owned child request lifecycle。`SubagentExecutionPort` contract 归 `agent-contracts/capability`，默认 runtime implementation 由 `agent-runtime` 提供并通过 `agent-app` 注入，避免 capability 依赖 runtime subpath。
- 拥有 `ToolCatalog` / `BuiltinToolCatalog`、`BuiltinToolExecutor`、Tool metadata/config/dependency validation、Tool descriptor projection、provider-aware executable lookup、safe failure mapping 和 `CapabilityInvocationResult.structuredPayload` wrapping。
- `ToolSearch` 是 builtin query Tool，不拥有 provider discovery、capability authorization 或 conflict resolution。它只能搜索当前 request 中 governed visible Tool / Skill metadata，并把 Tool activation 收敛到 request-local `allowedTools`，把 ToolSearch-deferred Skill loading 收敛到 request-local `discoveredSkills`。
- `TodoWrite` 是 builtin Tool list 中的普通 Tool entry。它通过 `todoState` dependency 做 full replacement 写入，缺少 dependency 或 config 模式禁用时 descriptor 必须 unavailable，不得退化为 runtime in-memory map。TodoWrite 不拥有 Web API、session lifecycle、terminal commit 或 observability schema；它只执行 schema validation、safe result mapping 和 gateway-backed state replacement。
- `ApiCall` 是 builtin Tool list 中的隐藏 Tool entry（`modelInvocable=false`、`disclosurePolicy=HIDDEN`），只供非 agentic Skill 编排路径程序化调用，不经模型直接调用。它通过 `defineTool` 创建，`requiredDependencies` 为 `["skillSources", "apiCallPort", "parameterExtraction"]`，缺少任一 dependency 时 descriptor 必须 unavailable。`ApiCall` tool 内部完成 Swagger 2.0 `api/<name>.yaml` 解析（`js-yaml` + 自定义提取函数构造 `ApiDoc`，不引入第三方 swagger 库、不做缓存）、模型提参（通过 `ParameterExtractionPort` 单次 `complete()`）、参数合并、HTTP 调用（通过 `ApiCallPort`）和流式/非流式响应处理。非流式响应原样放入 `structuredPayload` 不截断（绕过 `maxCapabilityResultMessageChars`）；流式响应通过 `emitResultDelta` 原样转发 SSE data。失败返回稳定 safe error code（`API_DOC_LOAD_FAILED`、`PARAMETER_EXTRACTION_TIMEOUT`、`PARAMETER_EXTRACTION_FAILED`、`UNAUTHORIZED`、`TIMEOUT`、`UNAVAILABLE`、`API_STREAM_INTERRUPTED`、`MISSING_REQUIRED_PARAMS`），不暴露 endpoint、credential、请求体、响应体、模型输出、prompt 或文件路径。跨模块装配、拦截和恢复事实见 `architecture/skill-driven-api-call.md`。
- Skill acquisition service 归本 package owning。它消费 trusted owner/agent scope、provider id、可选 requested capability id 和 bounded query，调用同一 SkillHub source install/index/governance 实现，返回 `ACQUIRED_REQUIRES_REPLAN`、`NOT_FOUND`、`UNAVAILABLE`、`REJECTED`、`INSTALL_FAILED`、`UNAUTHORIZED` 等安全结果。成功结果只能包含 safe descriptor summary、provider id、skill id 和 bounded consistency summary。
- Runtime-generated local Skill discovery 与 SkillHub source 保持分离。`generated-skills/<skill-name>/SKILL.md` 是 execution-scope local source，可在后续 capability resolution/model step 可见；它不得写入 SkillHub managed install/index，也不得触发 SkillHub publish/search/fetch。
- CLIP-backed API Tool source 可以被 trusted composition 配置为 `tool-search` deferred disclosure。此时 provider-private discovery 仍留在 source boundary，`ToolSearch` 只负责把命中的 deferred CLIP Tool 投影为 safe `available-clipc` 元消息并沿既有 `allowedTools` 路径激活具体普通 Tool descriptor。
- `AskUserQuestion` 是 builtin pending-input producer Tool。canonical descriptor 的 model-facing `questions` 固定为 1–3 项，并明确提示模型只询问当前必要问题；question prompt、option value 和 option label 继续使用 500 字符可见文本上限。descriptor 必须说明 text、single-select、multi-select 和 custom option shape，不得向模型暴露 20 题兼容上限、answer schema、identity、idempotency、timeout 或 producer coordinates。Tool 只校验受限 question payload、创建 runtime-owned `QUESTION` pending input 请求并返回 producer outcome；不得在 Tool handler 内等待用户回答、保存 resume state、拥有恢复/终态或创建 capability-owned pending facade。4–20 题的 count-only 兼容校验和 21+ 纠正属于 `agent-core` tool-call 编排，不得写回 capability catalog、context rendering 或 provider tool schema。
- builtin `rag` Tool 只依赖 public `RagRetrievalGateway` contract，返回 bounded safe retrieval results；显式 `indexes` 始终优先于 app-composed 默认 logical indexes，只有省略 `indexes` 时才消费默认列表；本地 fallback provider 的 authority 只来自 trusted owner + workspace scope，不得直接 import local governance、SQLite/FTS5、workspace host path 或 provider-private client/config。`ragOutputSchema` 允许顶层额外字段和任意字段的 `diagnostics` 对象，不对结果项或诊断对象施加封闭字段集、长度、格式、数值范围或必填字段约束；Tool 保留既有提供方结果校验、状态映射、字段投影和按 `topK` 截取的结果数量边界。
- `ToolCatalogConfig` 只是 trusted framework config object，不是最终用户配置文件 schema，也不进入 `agent-contracts/app`；未知 Tool config 必须 fail fast，invalid per-tool config 或缺 required dependency 必须产生 unavailable descriptor 且不进入 executable lookup。
- 拥有 Tool-facing `WorkspaceFilePort` 和 `SandboxExecutionPort` interface。`WorkspaceFilePort` 是 builtin file tools 和 Skill resource projection 的中心 path interpreter 与 filesystem enforcement boundary，负责从 `ToolExecutionContext` trusted facts 解析 run `ExecutionWorkspaceView`，执行 path normalization、execution-view-default target selection、root authorization、realpath containment、read/write/glob/grep、system-only projection、run temp cleanup 和 safe diagnostics。
- `WorkspaceFilePort` 对 `workspace/`、授权 `.nextagent/skills/<skillProjectionKey>/<skill-name>/...`、`temp/`、`generated-skills/` 与 LOCAL `shared-data/` 先应用 known-root 选择；bare workspace path（不以已知 root 前缀开头的相对路径）作为对应 `workspace/...` 的输入别名解析到同一物理文件和同一 canonical file identity。directory policy 使用完整 root-qualified canonical 逻辑路径匹配（装配编译已把 `.` 归一为 `workspace`、普通无前缀目录归一到 `workspace/...`），随后仍执行 root access mode、Skill projection authorization、link containment 与 extension policy；`"."` 授权不得扩大只读或系统管理 root 权限。文件工具成功结果只返回 root-qualified canonical path，不返回输入别名或物理路径。
- Glob/Grep 的缺省搜索由 `WorkspaceFilePort` 展开为 effective workspace Read authority：只覆盖当前 Agent 获得读取授权的 workspace 范围，不隐式扫描 Skill、临时、共享或系统管理 root；其他逻辑 root 只能通过显式、已授权的 root-qualified path 搜索。全部目标复用同一 traversal，并共享单一排序、读取、结果与容量预算；所有匹配文件路径返回 root-qualified canonical path。
- Grep executor 从已规范化的调用模式生成必填 canonical `output_mode`。`files_with_matches` 只允许非空项进入 `filenames`，`content` 只允许非空项进入 `matches`；合法零匹配仍保留实际模式。output schema 拒绝缺失或未知模式、模式专属数组矛盾和额外字段，consumer 不得重建模式。
- `WorkspaceFilePort` 允许 root-aware consumers 读取 `workspace/`、授权 `.nextagent/skills/<skillProjectionKey>/<skill-name>/...` 和 `temp/`；普通 write/edit tool、sandbox、Skill script 和 generated code 不得写 `.nextagent/`，需要跨 run 保留的产物应显式写入 `workspace/`。
- Skill projection 的只读 authority 来自当前 execution scope 内身份和完整性有效的 committed projection；显式有效 `.nextagent/skills/...` 路径的读取与搜索独立于 workspace `readDirectories`（不因缺省、为空或仅授权 workspace 被错误拒绝），且不进入默认搜索；`WorkspaceFilePort` 以 scope 的 trusted system-resources root 发现和验证该事实，可跨 run 或进程重建恢复，且不接受历史路径、当前 Skill availability 或 run-local reauthorization 作为 authority。
- `WorkspaceFilePort` 还允许 LOCAL execution view 中的 read-only `shared-data/` root。Read/Glob/Grep 可以在显式授权路径下读取该 root，但缺省搜索不隐式纳入它；Write/Edit、Skill scripts、generated code and sandbox writes must fail closed or be read-only-enforced. `workspacePolicy.files.readDirectories/writeDirectories` 使用 execution-view-relative 语义，不能覆盖 shared-data 的只读 access mode。
- oversized textual `CAPABILITY_RESULT` 的 externalize 目标是 execution workspace 文件 `workspace/tool-results/<refId>.txt`。app-composed `LargeContentExternalizerPort` 使用 trusted `runtimeWorkspaceRoot`、`ExecutionWorkspaceResolver` 和 `AgentAssemblyRegistry.workspacePolicy` 写入该路径；`agent-app` 不直接创建、持有或调用 `WorkspaceFilePort`。模型可见形态为携带 `file_path` + access instruction 的 `PERSISTED_PREVIEW`，后续读回通过普通 `read` Tool 和 capability-owned `WorkspaceFilePort` enforcement 完成。`tool-results/` 是约定的 capability-result readback 目录，本期不为其引入普通 write/edit/sandbox 的 reserved-dir 禁写规则。
- `read` 工具经 `workspaceFiles.readText` 读回 `tool-results/<refId>.txt` 时按普通 workspace 文件处理（owner-scope 经 workspace resolver、行级 `offset`/`limit`/`truncated`/`nextOffset`、自管 `maxLines`/`maxTextBytes`）。`read` 不新增参数；当默认读取或显式范围过大、无法在单次响应文本预算内完整返回时，`read` MUST 返回安全的 paging-required 错误，提示模型用显式 `offset`/`limit` 分页，不得静默截断成看似完整的页。越界 `offset` 返回空页 + `truncated=false`/无 `nextOffset`，不抛错；跨 scope / 文件缺失 / 不可读返回 `FILE_UNAVAILABLE`，不泄漏原始内容。
- `read` 工具豁免 large-content externalization：其输出始终是 bounded page，永不 externalize，打断 读回-超限-再 externalize-再读回 循环。
- Skill Tool 成功加载 governed body 后调用 `WorkspaceFilePort.projectSkillResources(...)`。projection 只处理 active Skill 顶层 `scripts/`、`references/`、`assets/`，使用 `skillProjectionKey`、filesystem lock、staging directory 和 committed marker 提交到 `.nextagent/skills/<skillProjectionKey>/<skill-name>/`；projection 成功后在同一 hidden generated message 中先注入 resource root location，再附加原始 Skill body。
- Skill Tool 的 `args` input validation 只校验既有 JSON object、可序列化、字节数和嵌套深度边界，不按字段名全局拒绝 task data；`mode`、`path`、`directory`、`provider`、`providerId`、`timeout`、`budget`、`timeoutMs`、`timeout_ms`、`childBudget`、`child_budget` 和 `providerOverride` 等治理同名字段与其他字段名使用相同规则。实际 timeout、child budget、provider selection 等执行治理只来自可信 runtime context、policy 和受治理 metadata，不从 `Skill.args` 读取。model-facing descriptor 指示模型把 `args` 用作 task data，并说明 `args` 字段不会改变可信 runtime 执行治理。
- Skill Tool 在 `readSkillMetadata` 之后检查 `extension._naie_agentic_loop_flag`。值为 `"false"` 时，Skill Tool 仍通过 `loadCanonicalBodyView` 加载 body 解析 ` ```api ` 代码块中的 API 命令（api name、hiro value），但不 inject body、不做 resource projection，返回带 `nonAgenticApiCall: true` 信号的 `CapabilityInvocationResult`。值为 `"true"` 或 extension 缺失时走现有 inline body 注入路径，行为完全不变。API 命令解析失败返回 `API_COMMAND_PARSE_FAILED` safe error。`api_header_params`/`api_request_params` 由 Skill tool 从 extension 读取后放入返回结果 `structuredPayload`，供编排层获取。非 agentic 路径的编排拦截、`ApiCall` tool 执行和恢复事实见 `architecture/skill-driven-api-call.md`。
- `ToolDependencyName` 和 `ToolDependencies` 承载受控 Tool 依赖类型，包括 `workspaceFiles`、`todoState`、`cronTasks`、`subagentExecution`、`apiCallPort` 和 `parameterExtraction`。`ApiCallPort` 和 `ParameterExtractionPort` 接口归 `agent-contracts/capability`，由 `agent-capability` 通过 `tool-spi.ts` re-export 消费；生产实现分别在 `agent-platform-gateway-local`/`agent-platform-gateway-remote` 和 `agent-runtime`，由 `agent-app` composition 注入。`agent-capability` 只暴露 Tool-facing 接口，不实现 HTTP 执行或 model invocation。
- `SkillSourceDiscovery` 在 body loading 边界旁提供 governed `listSkillResources(...)` / `readSkillResource(...)`。provider 只返回 safe metadata 和按项 content stream；manifest path、artifact ref、frontmatter hash、source path、registry loading key 等 private facts 留在 provider 内部。
- Sandbox port 使用同一 `ToolExecutionContext` 和 runtime resolver 派生 `SandboxExecutionRequest.filesystem`，映射 `workspace/` read-write、授权 `.nextagent` projection subtree read-only、`temp/` read-write。`bash`、`python`、Skill script execution 和 generated code staging 必须走 sandbox gateway boundary，不得直接启动 host process。
- `agent-capability` 还通过 public export 暴露 `WorkflowSandboxExecutionPort`，作为 Workflow Python 节点直接执行 recipe 预定义脚本的窄 sandbox port。该 port 只暴露 `runPython`，由 `createWorkflowSandboxExecutionPort(sandbox)` factory 从同一 trusted startup `SandboxExecutionPort` 装配，内部复用 `SandboxExecutionPort.runPython`，不经过 capability executor、capability catalog 或 nl2py guardrail。`agent-app` composition 在 sandbox gateway 可用时创建该 port 实例并注入到 `createWorkflowNodeCatalog`，使 Workflow Python 节点直接通过 sandbox boundary 执行预定义脚本，不触发 `python` capability 路径上的 nl2py fail-closed。port MUST NOT 暴露 `runShell`、`runShellStreaming`、`runShellBackgroundable`、`startBackgroundShell`、`WorkspaceFilePort` 或 sandbox gateway internals；app composition MUST NOT 直接创建、持有或调用 `SandboxExecutionPort` 或 `WorkspaceFilePort`。
- Sandbox filesystem preparation passes `shared-data/` as read-only only when resolver output includes the LOCAL sharedData root. It must not add shared-data to executable search paths, `PATH`, `PYTHONPATH` or Python import authority.
- Capability owns cleanup jobs and cleanup policy for Skill projection directories、projection staging directories、stale projection locks and LOCAL run temp directories。`agent-app` 只注册这些 jobs，gateway adapter 只负责 deployment-mode-specific scheduling/execution。
- Tool execution context 只能由可信 invocation/runtime facts 构造；Tool 不接收 workspace root、host path、host process API、gateway-local 私有实现或 capability invocation envelope。
- `ToolExecutionContext` 新增可选 `attachmentRefs` 和 `attachmentPaths` 字段，由 runtime 在 tool loop 前预解析当前 request 的全部 attachments 并通过 `BlobStoreGateway.materializeBlob` 物化到 run-scoped `temp/attachments` 目录后注入。`attachmentRefs` 含 `attachmentId`、`fileName`、`mediaType`、`sizeBytes`、`storageRef`（非 model-visible）；`attachmentPaths` 含物化后的可读文件路径数组。两者都非 model-visible：不出现在 system prompt、user message、tool call arguments、stream payload 或 safe error 中。Skill tool 同步读取 `attachmentPaths`，sandbox 通过 `FILE_PATHS` 环境变量传递同一 JSON 数组。无附件时两者均不出现。`storageRef` 只作为 gateway 输入，绝不作为工具路径或 model-visible 内容。
- Tool execution context 可以提供可选的安全 result delta emitter，供普通 Tool 在单次调用内发出累计可见状态；该 emitter 不改变单次终态 `CapabilityInvocationResult`、不生成平行 invocation protocol，也不允许 Tool 直接写 runtime timeline。

## Agent discovery 子模块

`agent-capability` 拥有 Agent capability discovery adapter 和 descriptor projection，不拥有 Agent package loading。adapter 消费 app-injected `AgentDiscoverySource`，把已编译 `AgentAssembly` facts 投影为 `builtin-agents`、`local-agents` 和 `local-subagents` provider 下的 governed `CapabilityDescriptor(kind="AGENT")` candidates。

Builtin/top-level Agent descriptors 进入 EAGER candidate set：builtin 使用 `builtin-agents`，top-level local 使用 `local-agents`。Parent-local subagents 是 `local-subagents` SEARCH candidates，按 trusted parent `agentId/agentVersion/agentAssemblyRef` 限定；不得预先 materialize 成全局 descriptor 或 synthetic capability binding。`agentInvocation="NONE"` assemblies 可以产生 unavailable/non-callable diagnostics，但不能成为 model-invocable delegation target。`agentInvocation="BOUND"` 需要普通 binding/catalog governance。`agentInvocation="PARENT"` 只在 owning parent Agent scope 下可见。

Descriptor projection 必须安全且最小。它可以使用 `agentId` 作为 `capabilityId`，使用 `agentVersion` 作为 descriptor `version`，并投影 safe display name/description、provider identity、availability、replay/model visibility facts。它不得把 raw `agent.yaml`、source path、prompt body、Skill body、child assembly object、loading key、workspace path、credential、provider-private config、`userInvocable` 或 `agentInvocation` 复制到 public descriptor metadata。

## Agent tool 子模块

内置 Agent tool 是通过同一 builtin Tool framework 暴露的 Tool-kind entry。它接收 governed target Agent id 和 prompt，使用 `additionalProperties=false` 校验 schema，拒绝 self-invocation，通过 `RuntimeCapabilityResolver.resolveCapability({ kind: "AGENT", capabilityId })` 解析 target，然后调用 `SubagentExecutionPort`。

Tool 不拥有 subagent lifecycle。它不直接调用 `RuntimeCommandPort.submit()`，不创建 session/run，不等待 timeline，不读取 child messages，不构造 terminal commit，不决定 scheduler priority，也不解析 `AgentAssembly`。这些职责属于 `SubagentExecutionPort` 的 runtime implementation。Capability 的职责是提供从 model tool call 到 subagent execution request 的安全 adapter，再把 `SubagentExecutionResult` 映射回 safe `CapabilityInvocationResult`。

Agent tool failure semantics 必须适合 model loop 继续修正。Invalid input、target unavailable、self-invocation、timeout、abort 和 child execution failure 通常应变成 failed/timed-out capability results，让模型可观察并调整。只有 runtime lifecycle owner 判定 parent run 已无法继续时，parent request 才应终止。

## 验证关注点

- Tool、Skill、Agent 不得形成三套平行执行机制；Tool 不得新增 public `ToolDescriptor`、`ToolInvocationRequest`、`ToolInvocationResult` 或 `ToolSource`。
- capability invocation 必须保留 timeout、cancel、audit、safe error、checkpoint、idempotency 和 replay policy 边界。
- pending capability recovery guard 必须使用 descriptor replay policy 和 runtime-provided invocation anchor；provider 不得决定 runtime recovery eligibility。
- Skill source 必须复用统一 manifest parser/mapper/accessor；不得为 builtin/local/agent-scoped/SkillHub source 定义第二套 manifest field policy、metadata DTO 或 diagnostic code。
- Skill manifest source metadata array support 只允许 `exclusiveWith`、`compatibleWith` 和 `tags` 三个 key，且只作为 safe `SkillMetadata.sourceMetadata` 保存；agent-capability 不得从这些数组推导互斥、兼容性过滤、标签检索、routing 或 availability。
- Runtime/core/context/recovery 不得 import 或调用 local Skill discovery、filesystem scanner、Agent package locator 或 manifest parser；它们只能消费 compiled assembly facts 和 Catalog governed view。
- Runtime/core/context/recovery 不得自行扫描 builtin/local/subagent Agent packages；Agent 能力可见性只能消费 compiled assembly facts 和 Catalog governed Agent descriptors。
- Agent tool 失败必须映射为 `CapabilityInvocationResult` 的安全失败/超时/取消结果，供模型按 tool result 修正或继续；只有 lifecycle owner 判断为不可恢复的 runtime failure 才终止整个 request。
- 用户 capability source configuration 不得生成 framework/reserved provider；`local-skills-system`、`local-skills-agent-owned`、`local-agents` 和 `local-subagents` 只能来自 trusted capability startup provider contributions。
- plugin provider 不得通过 synthetic binding 默认暴露；没有显式 Agent binding 的 plugin Tool 不得出现在 `listAvailable`、`resolve` 或 invocation path。
- shell、python、脚本和动态可执行内容必须通过 sandbox gateway boundary；Tool-facing `SandboxExecutionPort` 负责从 resolver-backed run view 准备 sandbox filesystem layout，不实现 gateway adapter，也不绕过 gateway contract 直接启动宿主进程。
- file tools、Skill resource projection 和 sandbox request preparation 不得捕获 app 启动期静态 `workspaceDir`，不得扫描 Skill source directories 或解析 provider-private layout，不得维护绕过 runtime execution workspace resolver / `WorkspaceFilePort` enforcement 的独立 root allowlist。
- read/glob/write/python/bash capability 必须通过 execution file access policy 处理 logical paths；host absolute path、drive-qualified path、parent traversal、URL-like path、wrong scope、unauthorized Skill resource、write `.nextagent` 和 oversized/binary unsupported content 必须 safe rejected。
- non-idempotent pending capability 在 startup recovery 中必须 fail closed 或复用 durable result，不得重复执行。
- AskUserQuestion descriptor 必须以 3/4/20/21 characterization 锁定 model-facing 3 题与内部兼容边界；扩大任一边界时必须同时评审 core 兼容校验、runtime pending-input 防御和 Web answer projection 容量。
- memory tools 不得扩展公共 `ToolDependencies` SPI；后台 extraction/aging 不得通过 capability invocation 或 model-facing memory tools 执行。

## Bash Command Ownership

The Bash Tool capability owns only input shape: it tokenizes the model-supplied command into a deterministic `executable` token and argument vector, enforces schema/timeout/output budgets, and requires the sandbox dependency. It MUST NOT own an executable allowlist or command-specific argument authorization; executable allow/deny decisions belong to the sandbox gateway policy. `clipc` is resolved as a governed executable by the restricted local sandbox through its trusted executable locator; the model MUST NOT provide or override the executable path, endpoint, credential, or environment variable.

Bash input supports two mutually exclusive modes. In command-string mode the model supplies only `command` as a complete shell command string and omits `args`; the existing `parseBashCommandForModelCorrection(command)` tokenization path applies unchanged. In argv mode the model supplies `command` as a single executable token plus an optional `args` string array; each `args` entry is submitted to the sandbox gateway as an independent argv entry without shell tokenization, string concatenation or auto-escaping, so JSON, Gremlin, SQL, regex, natural-language and path parameters that contain double quotes, spaces, brackets or backslashes are preserved verbatim. When `args` is present, `command` MUST resolve to a single executable token; if `command` still carries a script path, flags, pipes or any other token, Bash MUST reject the input before sandbox submission with a retryable `CAPABILITY_INPUT_INVALID` whose safe details include reason code `BASH_STRUCTURED_ARGS_COMMAND_NOT_EXECUTABLE_ONLY`, and the safe hint MUST instruct the model to choose one of the two modes, MUST forbid splitting one command between `command` and `args`, and MUST state that `env` currently supports only `PYTHONPATH`. Structured `args` does not bypass `prepareBuiltinExecutableFacts` or the sandbox execution boundary; `python` and `python3` with structured `args` still route through the Python sandbox dependency.

## Category Question Resource Discovery

`CategoryQuestionResourceDiscovery` 位于 `agent-capability/src/local/`，负责从 trusted agent package root 下的 `resource/` 目录加载分类问题 JSONL 文件到内存。与 `LocalSkillDiscovery` 同形同策：复用 `AgentPackageSourceLocator` 定位 agent package root，产出 readiness evidence，数据在内存中按 `agentId` + `locale` 维度隔离。

与 `LocalSkillDiscovery` 的差异：
- 不实现 `CapabilityDiscovery` 接口，不进入 capability catalog——分类问题不是 capability（不是 Tool/Skill/Agent）。
- 解析 JSONL 格式（非 `SKILL.md` frontmatter），一级分类的 `questions` 和 `records` 可共存（mixed mode），二级分类的 `records` 被忽略。
- 每个问题计算 SHA-256 hash 作为内部标识，供未来高频问题组件和输入联想能力持久化用户活动时使用，API 不暴露 hash。

JSONL 校验规则：
- 空行静默跳过；单行 JSON 解析失败跳过 + evidence。
- 一级分类 `category` 缺失/空/非字符串 → 跳过整行 + evidence。
- 一级分类 `questions` 和 `records` 同时为空/不存在 → 跳过整行 + evidence。
- 二级分类 `category` 缺失/空/非字符串 → 跳过该二级分类 + evidence。
- 二级分类 `questions` 为空/不存在 → 跳过该二级分类 + evidence。
- 二级分类 `records` 存在 → 忽略，不拒绝。
- question `question` 缺失/空/非字符串 → 跳过该 question + evidence。
- question `fixed` 缺失/非布尔 → 跳过该 question + evidence。
- 一级分类下所有 questions 和 records 均无效 → 跳过整行 + evidence。

内存 Catalog 不持久化，应用生命周期内不可变，文件变更后需要重启应用才能生效。

## Cron 日历求值

`agent-capability` 拥有五段本地时间 Cron 表达式求值入口 `nextCronRunMs` 和 `findNextOccurrence`。Cron 日历时区为 Node.js 进程本地时区，进程生命周期内固定；未配置任务时区时不从 locale、请求内容或浏览器环境推断。`nextRunAt`、到期比较和持久化时间使用 UTC epoch milliseconds。

`findNextOccurrence` 清零输入秒和毫秒后使用本地 `Date` setter 推进游标，并在字段全部匹配时执行严格 epoch 顺序门禁：仅当 candidate 的 `getTime()` 严格大于不可变 `originEpochMs` 时返回，否则沿用现有本地分钟推进继续搜索，达到搜索上限仍无未来 candidate 时返回 `null`。该门禁利用 ECMAScript `Date` 对 DST 春季缺口的前向归一化和对 DST 秋季重叠的较早 offset 选择，保证下一次日历命中始终位于起点之后。DST 春季缺口中不存在的本地分钟被跳过；DST 秋季重叠中同一本地日历分钟只采用较早 offset 一次，candidate 不晚于起点时继续查找下一个不同日历命中，不返回较晚 offset 的重复分钟。

Cron 求值不改 parser、搜索上限、scheduler、gateway、持久化或依赖；`LocalCronTaskScheduler` 只消费注入的 `computeNextRunAt` 并以 UTC epoch 判断到期。
