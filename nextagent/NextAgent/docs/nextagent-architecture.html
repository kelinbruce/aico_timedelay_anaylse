NextAgent 系统架构

1 评审焦点

本页聚焦当前已实现架构的四个决策，不将规划能力或参考 adapter 推断为已交付能力。

CORE

什么必须稳定？

请求生命周期、会话事实、Agent 执行、上下文、模型与能力治理组成逻辑最小内核。

EXTENSION

什么可以替换？

Agent Assembly、Capability、Plugin、Channel、Gateway、Model 和观测 exporter 都通过明确边界装配。

FRONTEND

前端如何交付？

同一浏览器应用制品支持独立托管或一体化托管，三种宿主复用同一 Chat Workspace 和后端契约。

SERVICE

如何服务化？

内核 owner 保持进程内协作，北向由 Channel 服务化，南向平台能力通过 async port 本地或远端实现。

一句话架构 Channel / Frontend → agent-app 启动装配 → 最小内核 → Gateway / Provider port → LOCAL adapter 或 REMOTE 平台服务。

2 总体架构

入口、内核和平台实现之间只通过公开契约协作。Channel 不拥有生命周期，Gateway 不反推业务语义，前端不持有服务端事实。

NextAgent 当前架构全景

唯一生命周期

agent-runtime 是 RequestRun 与 canonical timeline 的唯一 owner。

唯一装配路径

agent-app 在 ready 前完成配置、Plugin、Provider 与宿主装配。

可替换实现

入口、UI 和平台实现可替换，但不能改变内核 contract 与状态语义。

3 最小内核

最小内核不是“最少 package 数量”，而是不可被 Channel、Plugin、Gateway 或 UI 复制的一组运行语义。

两个概念必须分开 逻辑最小内核保持核心语义；OpenSpec ts-minimal-agent-kernel 描述的是加入 Web Channel、SQLite Gateway、观测实现和 composition host 后的最小可运行产品切片。

Composition root、配置冻结、ready gate 与 lifecycle host；装配 owner，不拥有业务语义。

Channel / Gateway

提供入口和平台实现；可替换，但不能获得 lifecycle 或 canonical truth。

Frontend / Observability

投影 UI 或既有运行事实；不能反向改变请求结果、权限与持久化。

4 后端可扩展点

扩展遵循“先声明、后装配、再授权”。不同扩展面有唯一用途，不互相模拟。

扩展点适用场景载体与接入方式边界
Agent AssemblyAgent 身份、Prompt、模型授权、能力绑定、runtime settings、Hook/Policy 激活agent.yaml、prompts/ 与资源，由 agent-app 编译只声明与激活，不能携带可信身份、物理部署路径或运行期状态
Capability新增领域 Tool、Skill、子 Agent 或 RecipeProvider → agent-capability catalog；Recipe → agent-workflow必须经过 binding、schema、风险、Sandbox、审计与结果治理

Channel新增 Web、Task 或其他北向协议agent-channel-web、agent-channel-task 或后续同形 package只拥有 transport、schema、可信身份接入与 DTO/stream projection
Gateway / Model替换持久化、RAG、Sandbox、Workflow、平台 API 或模型 ProviderLocal/Remote provider 通过 public async port 注入不能改变 DTO/Record、Scope、幂等、terminal commit 或 Runtime 状态机

5 前端服务

agent-channel-web 是后端 Channel adapter，不是前端服务。前端服务由浏览器应用制品与可选静态托管组成。

组成Owner职责
前端源码frontend/agent-webReact Chat Workspace、组件交互、local view state，以及 local / immersive / collaborative 三种宿主投影
正式前端制品@nextagent/agent-web构建后的 HTML、JavaScript、CSS、PIU assets 与 hosting manifest；版本与根产品版本一致
静态托管 adapteragent-app-frontend-hosting注册静态资源 route 与 SPA fallback；不定义 API 或前端业务状态
后端 APIagent-channel-webREST、SSE、WebSocket、bootstrap 与 public DTO projection
一体化入口agent-app/entrypoints/with-frontend在 ready 前接入正式前端制品与静态托管 adapter
前端服务的两种正式部署方式
三种宿主，一套业务语义 local、immersive、collaborative 复用同一 Chat Workspace、后端 bootstrap/transport contract 与 canonical history；差异仅在容器、主题、语言、宿主上下文与布局。
开发服务不是生产形态 dev:watch 的 Vite dev server + backend-only proxy 只服务源码开发，不构成第三种正式前端架构。
  • 前端拥有浏览器渲染、组件交互与临时 view state。
  • 后端拥有 request lifecycle、trusted identity、Owner/Agent Scope、canonical stream/history、Capability authority 与 persistence。
  • URL、localStorage、浏览器环境变量与 UI 控件不能成为服务端事实的权威来源。

6 服务化方式

当前原则是“内核进程内模块化，平台能力端口服务化”，不是把每个 npm package 直接拆成微服务。

北向：Channel 服务

Web / Task Channel 暴露 HTTP、SSE、WebSocket、callback 等协议，并负责可信身份接入与 public projection。

南向：平台服务

Model、RAG、Sandbox、Workflow、Persistence 与客户系统通过 async Gateway / Provider port 接入。

形态进程 / 制品边界适用场景保持不变
LOCAL backendbackend-only 启动后端，前端独立托管独立 API 服务、前后端分离、本地部署Runtime lifecycle、Scope、timeline 与 terminal commit 在同一 composed app
LOCAL integratedwith-frontend 增加正式静态资源托管一体化安装包与 backend-only 使用同一内核和 API
REMOTE / hybridagent-remote-deployment 装配远端 Gateway / Model client，当前仍组合部分本地 providerPaaS、平台服务或客户系统集成只替换 port 后实现，不改变 Channel contract、Assembly 与 Runtime 状态机
Embedded host产品宿主调用 agent-app public factory 并注入受信 contribution产品内嵌、定制认证与平台壳集成agent-app 仍是唯一 composition root
REMOTE 不等于天然分布式 远端 adapter 只证明某些平台能力可移出进程，不证明全部持久化、scheduler、lease、same-session lane、terminal composite write、timeline 接续与 recovery 已具备多实例一致性。多实例交付必须提供独立规格与验证证据。
何时需要新的 OpenSpec 若要把 agent-runtime、agent-core、agent-session 或 agent-context-engine 独立成网络服务，必须重新定义网络失败、幂等、一致性、取消、恢复与安全语义，不能仅把 package 调用替换成 RPC。

7 评审结论

当前架构以稳定内核承载通用运行语义，以明确扩展面承载领域与部署差异。

内核收敛

Runtime、Session、Core、Context、Model、Capability 与公共契约形成唯一主路径，不存在平行 lifecycle owner。

扩展受控

加载、激活和执行分层；Channel、Plugin 与 Gateway 各有唯一职责，不能越权替代。

交付一致

前端宿主与 LOCAL / REMOTE 部署复用同一 contract、Scope、timeline 与 terminal 语义。

推荐评审基线 任何新增能力都先回答三个问题：谁是唯一 owner？通过哪个 public contract 接入？它是否改变 RequestRun、Scope、terminal commit 或 canonical history？若改变，先建立 OpenSpec；若不改变，选择现有扩展面。

边界检查清单

  • Channel 只处理协议、可信身份和公开投影，不拥有请求生命周期。
  • Frontend 只处理浏览器投影和本地 view state，不拥有服务端事实。
  • Plugin 必须经过启动期校验、Agent Assembly 激活和 owner 治理。
  • Gateway / Model provider 只替换端口实现，不改变核心 contract。
  • LOCAL / REMOTE 与宿主差异不改变 Agent Scope、Owner Scope 和 terminal 一致性。
