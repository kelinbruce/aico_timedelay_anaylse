Prompt Shaping 设计讲解

add-ts-context-prompt-shaping · 面向不熟悉该模块的开发者

一、它解决什么问题？

用户说了一句话——"查一下 BTS-001 的告警"。从这句话到真正发给大模型，中间要经过好几步处理：选历史消息、算 token 预算、压缩太长对话、处理大附件。这些步骤各自负责自己的事，但它们输出的都是"决策结果"——比如"选中了消息 A、B、C"、"用这个模板"。

但大模型需要的不是决策结果，而是一个格式严格的请求：一个消息数组（每条有角色标记）加一个工具定义列表。把决策结果变成这个格式严格的请求，就是 Prompt Shaping 要做的事。

打个比方
前面的步骤像厨师备菜——洗菜、切菜、配料。Prompt Shaping 像摆盘：把备好的菜按正确的顺序和格式摆到盘子上，端给顾客（大模型）。菜品选得再好，摆盘乱了，顾客也看不懂。

二、它在系统中的位置

整个系统由多个模块组成，Prompt Shaping 住在 agent-context-engine（上下文引擎）里面，是上下文引擎流水线的最后一站：

模块关系与数据流向

数据怎么流的：

  1. agent-core 说："用户说了 X，帮我准备好模型输入"
  2. agent-context-engine 选历史、算预算、做 Prompt Shaping，输出完整的模型输入
  3. agent-core 拿到结果，转成调用请求，交给 agent-model
  4. agent-model 调大模型，返回结果

三、两个阶段，两份产出

Prompt Shaping 的工作拆成两步。第一步决定"用什么"，第二步决定"怎么排"：

两阶段流程 — 从决策到成品

第一阶段的产出叫 ContextAssembly（一份"订单"，写满了选了什么、用了什么）。第二阶段的产出叫 RenderedModelInput（一份"成品"，模型可以直接吃）。

打个比方
餐厅点菜：装配 = 服务员记下客人点了什么菜、忌口、偏好（一张订单）；渲染 = 厨房根据订单做出实物菜品、摆好盘、配上餐具（一桌成品）。订单写的是"宫保鸡丁 × 1"，但顾客需要的是真正的菜。

为什么要拆成两步？因为"订单"可以被审计和追溯（"为什么选了这些消息？用了哪个模板？"），而"成品"是干净的——不包含任何决策元数据。模型不需要知道你是怎么选的，它只需要看到最终的对话内容。

四、系统提示怎么拼？

系统提示（System Prompt）是大模型最先看到的内容，告诉它"你是谁、你该怎么做"。我们把它拆成多个段落（section），按固定顺序拼接：

系统提示段落排列

为什么要分"稳定层"和"动态层"？大模型服务商通常会缓存提示的前缀部分——如果前缀不变，下次调用可以复用缓存，省钱又快。所以我们把不怎么变的内容（身份、语言、领域知识）放前面，经常变的内容（能力清单）放后面，中间用一条分界线隔开。

模板从哪来？

系统提示的核心内容来自提示模板，按优先级加载：

  1. 运行时指定：当前配置明确说了用哪个模板 → 用那个
  2. Agent 配置：这个智能体注册了模板列表 → 用第一个
  3. 系统内置：都没有 → 用系统自带的兜底模板

加载后要过三道安全检查

  1. 长度检查：模板不能太长（不超过模型可用输入的 30%），否则留给对话的空间就没了
  2. 注入检测：检查模板里有没有类似"忽略之前的指令"这样的注入攻击语句
  3. 语言匹配：如果用户选了中文交互，但模板只支持英文，就拒绝使用

五、能力怎么展示给模型？

我们的智能体有各种"能力"：工具（Tool）、技能（Skill）、子智能体（SubAgent）。它们告诉模型的方式不同：

能力类型展示方式通俗理解
Tool（工具） 变成工具定义，放在消息数组旁边的 tools 列表里 给模型一个"工具箱"，告诉它每个工具叫什么、能干什么、要传什么参数
Skill（技能） 写一段简短描述，放进系统提示的能力清单段落 告诉模型"你会这个技能"，详细说明书等真正要用时再加载
SubAgent（子智能体） 写一段简短描述，放进系统提示的能力清单段落 告诉模型"你可以把某类任务委派给这个助手"
为什么工具和技能/子智能体的展示方式不同？
工具是模型可以直接调用的（像函数调用），所以需要精确的参数定义；技能和子智能体更像是"知识"，模型知道有它们就行，需要时再深入了解。这也节省了提示的空间。

渲染阶段把装配结果变成模型能直接吃的消息数组。排列顺序固定如下：

角色映射

系统内部存储消息时用的角色名和发给模型时用的不完全一样：

系统内部角色发给模型的角色说明
USERuser直接传递
ASSISTANT（纯文本）assistant直接传递
ASSISTANT（调用了工具）assistant + 工具调用列表附带"调了哪个工具、传了什么参数"
CAPABILITY_RESULTtool工具执行结果，通过 ID 关联到对应调用
SUMMARYsystem（默认）对话摘要，放在历史消息前面
工具调用必须成对出现
如果助手的消息说"我调用了查告警工具"，那后面必须紧跟一条工具结果消息。就像你说"我打了个电话"，对方一定会问"然后呢？对方说了什么？"——大模型也需要看到完整的"调用 → 结果"配对，否则会困惑。渲染阶段会检查这一点，发现不配对就直接报错，不会把不完整的输入发给模型。

八、端到端示例：最终发给模型的请求长什么样？

用一个具体场景把上面所有概念串起来。

场景
用户在一个电信运维智能体里，用中文问："BTS-001 基站最近有什么告警？"。之前用户已经查过一次 BTS-002 的告警。

装配阶段做了什么：

  1. 从数据库里找到这个会话过去的对话，选了最近几轮（history selection）
  2. 检查总 token 数没超预算，不需要压缩（budget check）
  3. 加载智能体的提示模板 alarm-analyst-v2，安全检查通过
  4. 拼出系统提示：身份（"你是电信运维分析师..."）+ 语言（zh-CN）+ 领域知识 + 能力清单

渲染阶段做了什么：

  1. 把系统提示拼成一条 SYSTEM 消息
  2. 读取历史对话，映射成 USER / ASSISTANT / TOOL 消息
  3. 确认工具调用和结果配对完整
  4. 把当前问题作为最后一条 USER 消息
  5. 把 GetAlarms 工具的完整参数定义放进 tools 列表

最终发给模型的完整请求：

{ "model": "qwen-max", "temperature": 0.7, "max_tokens": 4096, "messages": [ // ── [0] 系统提示：稳定层 + 缓存分界线 + 动态层 ── { "role": "system", "content": " ## 身份与工作规则 你是电信运维分析师，负责分析基站告警、定位网络故障... 你必须基于工具返回的真实数据回答问题，不得编造。 ## 语言与格式 交互语言: zh-CN。日期格式: YYYY-MM-DD。保留电信术语原始英文。 ## 领域知识 告警级别: CRITICAL > MAJOR > MINOR > WARNING 网元类型: BTS(基站), BSC(基站控制器), MSC(移动交换中心)... <!-- cache_boundary --> ## 可用能力 ### 技能 - alarm-analysis: 告警根因分析，支持多告警关联和根因定位 ### 可委派智能体 - field-ops-agent: 现场运维操作，支持远程重启和配置下发" }, // ── [1..N] 历史消息（按时间顺序）── { "role": "user", "content": "帮我看看 BTS-002 的状态" }, { "role": "assistant", "content": "好的，我来查一下 BTS-002 的告警信息。", "tool_calls": [ { "id": "call_abc123", "type": "function", "function": { "name": "GetAlarms", "arguments": '{"neId": "BTS-002"}' } } ] }, { "role": "tool", "tool_call_id": "call_abc123", "content": '{"alarms": [{"level": "WARNING", "type": "高温告警", "time": "2026-05-29 14:30"}]}' }, { "role": "assistant", "content": "BTS-002 目前有一条 WARNING 级别的高温告警，发生在昨天下午 14:30。建议关注散热系统状态。" }, // ── [N+1] 当前用户输入（永远在最后）── { "role": "user", "content": "BTS-001 基站最近有什么告警？" } ], // ── 工具定义列表（Tool 类型能力渲染在这里）── "tools": [ { "type": "function", "function": { "name": "GetAlarms", "description": "查询网元告警信息", "parameters": { "type": "object", "properties": { "neId": { "type": "string", "description": "网元 ID，例如 BTS-001" }, "level": { "type": "string", "enum": ["CRITICAL", "MAJOR", "MINOR", "WARNING"], "description": "告警级别过滤" } }, "required": ["neId"] } } } ] }

模型看到这个请求后，会理解：

  • 自己是一个电信运维分析师（身份）
  • 要用中文回答（语言）
  • 之前用户查过 BTS-002，助手调了 GetAlarms 工具并得到了结果（历史上下文）
  • 现在用户要查 BTS-001（当前问题）
  • 可以调用 GetAlarms 工具来查询（工具箱）

于是模型会输出：调用 GetAlarms(neId="BTS-001")，由系统执行后把结果返回给模型，模型再基于结果生成自然语言回答。

九、几个关键设计决策

Q: 为什么 Prompt Shaping 内部拆成三个组件？

因为模板加载、系统提示拼接、消息渲染这三件事的输入、输出和变化频率都不同。模板加载逻辑可能因为新增配置源而改变，但不影响消息排列规则。拆开之后改一个不会牵连另外两个。

Q: 为什么模板内容不写死在代码里？

不同的智能体需要不同的提示风格（告警分析智能体 vs 网络规划智能体，身份指令完全不同）。外置之后，改提示词不需要改代码、不需要重新部署。

Q: 为什么诊断信息不进入模型输入？

模板选择结果、token 估算等诊断信息是"内部工作记录"。就像餐厅出菜单上有桌号、服务员编号——这些信息是给餐厅管理用的，不应该出现在顾客面前的菜品上。模型看到这些东西会困惑，还浪费 token 预算。

Q: 为什么 ContextAssembly 和 RenderedModelInput 是两份不同的数据？

ContextAssembly 是"决策结果"，可以被审计和追溯（"为什么选了这些消息？"）。RenderedModelInput 是"最终成品"，是干净的。模型不需要知道你是怎么选的，只需要看到最终的对话内容。
