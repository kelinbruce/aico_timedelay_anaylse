## FN-7.8 上报 AI 日志

### 目标与规范依据

本 Function 的目标是向 CloudSop 外部合规审计系统上报 AI 日志，记录每次对话请求的用户输入和系统输出，满足电信网络智能体的合规审计要求。CloudSop 审计人员通过该日志进行事后审计和内容溯源。

#### 本 Function 的目标 Requirements

- canonical spec：`ai-log-reporting`
- `ADDED`：`OperationLogGatewayPort 是 AI 日志上报出口`
- `ADDED`：`所有终态都上报 AI 日志`
- `ADDED`：`detail 字段按 locale 选择模板`
- `ADDED`：`通过 timeline 事件监听收集模型名和 km 标记`
- `ADDED`：`CloudSop 审计通道是受控脱敏例外`
- `ADDED`：`terminalIP 从请求头捕获`

### 当前实现

- `postTerminalCallback` 已存在于 `RequestLifecycleDependencies`（`agent-runtime/src/lifecycle/submit.ts:245`），以 fire-and-forget 方式执行（`void Promise.resolve().then(...).catch(...)`），已用于附件清理和推荐问题预计算。闭包中有一段 `if (status !== 'COMPLETED') return` 用于跳过非 COMPLETED 终态的推荐问题预计算。
- `runTimelineEventListeners` 已存在于 `RequestLifecycleDependencies`（同文件 :220），接受 `readonly ((event: RunTimelineEvent) => void)[]`，在 composition 层注册。`MODEL_INVOCATION_COMPLETED` 事件的 `inlinePayload` 包含 `modelId`；`CAPABILITY_COMPLETED` 事件的 `inlinePayload` 包含 `capabilityId`、`status` 和 `nodeType`（workflow 事件通过 `attachWorkflowFields` 注入）。
- `extractRequestHeaders` 已存在于 `agent-channel-web/src/routes/requests.ts:2004`，提取 `x-user-id`、`x-user-name`、`sessionId`、`conversationId`、`chatId`，但不捕获客户端 IP。
- `messageStore.listCurrentRequestMessages` 已存在于 `SessionMessageStoreGateway`（`agent-contracts/gateway`），可获取当前 request 的 USER 和 ASSISTANT 消息。
- 部署环境变量 `OSS_LANG`（下划线格式如 `zh_CN`、`en_US`）优先决定审计 locale，未设置时降级到 `command.locale`（`SubmitRequestCommand.locale`，'zh-CN' / 'en-US'）。`OSS_LANG` 的下划线分隔符归一化为连字符。此约定与常规 opLog 的部署语言决策一致。
- `command.identityContext` 携带 `tenantId` 和 `displayName`。
- `command.inputVariables.requestHeaders` 已用于传递请求头信息到 runtime。
- 现有 `opLog` 声明机制（`fastify-oplog.ts` + 各路由 config + `opLogIdentity`）只有声明层，无消费 hook、无 sink、无 HTTP client。

### GAP 分析

| 规范目标 | 当前事实 | GAP |
|---|---|---|
| 向 CloudSop 上报 AI 日志 | 无 AI 日志上报通道 | 缺少 port 接口、entry 类型和上报逻辑 |
| 所有终态都上报 | postTerminalCallback 的 COMPLETED early-return 在推荐问题之前 | 需在 early-return 前插入 AI 日志逻辑 |
| 收集模型名和 km 标记 | timeline 事件已有 modelId 和 capabilityId，但无人消费 | 需注册 listener 按 runId 在内存 Map 中收集 |
| 捕获 terminalIP | extractRequestHeaders 不捕获 IP | 需扩展捕获 x-real-client-addr / x-forwarded-for / request.ip |
| 多实例安全 | 无跨实例状态传递 | 内存 Map 是 process-local，recovery 场景 resourceName 为空（可接受降级） |
| 安全受控例外 | redaction-policy 禁止外部边界包含 prompt 和模型输出 | 需定义 CloudSop 通道为受控例外 |

### 修改方案

#### 1. Contract 定义（`agent-contracts/gateway`）

新增 `OperationLogGatewayPort` 接口和 `OperationLogEntry` 类型：

```ts
export interface OperationLogGatewayPort {
  writeAiLog(entry: OperationLogEntry, signal?: AbortSignal): Promise<void>;
}

export interface OperationLogEntry {
  readonly operation: string;
  readonly source: string;
  readonly target: string;
  readonly detail: string;
  readonly level: 'MINOR' | 'RISK';
  readonly result: 'SUCCESSFUL' | 'FAILURE';
  readonly tenantId: string;
  readonly userName: string;
  readonly terminalIP: string;
  readonly logType: string;
  readonly systemLang: string;
  readonly show: boolean;
}
```

`writeAiLog` 返回 `Promise<void>`，因为 AI 日志是 fire-and-forget — `postTerminalCallback` 被 runtime 包在 try-catch 中，上报失败只记 warn，调用方不消费返回值。

Port 不进 `GatewayBindings`、不加 `GatewayAdapterKind`。理由：`GatewayBindings` 是 config-driven adapter 选择的聚合点，AI 日志不需要选择 — 只看 REMOTE 模式就启用。通过 composition 层直接注入到 `postTerminalCallback` 闭包，比走 `GatewayBindings` 少四层间接。

`OperationLogGatewayPort` 的 HTTP 实现（CloudSop API 调用、认证、请求体序列化、超时控制）由另一个 repo 直接实现接口。另一个 repo 依赖 `agent-contracts` 获取 `OperationLogGatewayPort` 和 `OperationLogEntry` 类型，实现 `writeAiLog` 方法。本 repo 不提供 factory 骨架。

#### 2. 辅助函数（`agent-app` composition）

辅助函数放在 `agent-app` composition 层（`ai-log-helpers.ts`），供 `postTerminalCallback` 闭包组装 detail 字段使用。`agent-app` 不直接依赖 `agent-platform-gateway-remote`；`OperationLogGatewayPort` 实例由外部 entrypoint 注入到 composition contracts，闭包只消费注入的 port。中英文模板直接 hardcode 在 `formatAiLogDetail` 中：

- `truncate(text: string, maxLen: number): string` — 超过 maxLen 截取前 maxLen 个字符，空值返回空字符串。
- `buildResourceName(items: readonly string[], locale: string): string` — 从去重列表构建 resourceName，用对应语言版本分号分隔。
- `formatAiLogDetail(locale: string, chatId: string, resourceName: string, question: string, answer: string): string` — 选模板、填充参数。
- `resolveAuditLocale(envValue: string | undefined, fallback: string): string` — `OSS_LANG` 优先（下划线归一化为连字符），未设置或空值时返回 `fallback`（`command.locale`）。

中文模板：`创建对话资源访问详情：\n对话id：%s；\n事件类型：sys_input_output；\n被访问的资源名称：%s；\n系统接收的输入内容：%s；\n系统产生的输出内容：%s`

英文模板：`Create chat resource access details:\nchat id: %s;\nevent type: sys_input_output;\nname of the accessed resource: %s;\ninput received by the system: %s;\noutput generated by the system: %s`

截断按 Unicode 字符数（`String.prototype.slice(0, 1024)`），不按字节。

#### 3. terminalIP 获取（`agent-channel-web`）

`extractRequestHeaders` 扩展，捕获客户端 IP：

```ts
const terminalIP = singleHeader(request.headers['x-real-client-addr'])
  ?? singleHeader(request.headers['x-forwarded-for'])?.split(',')[0]?.trim()
  ?? request.ip;
```

`terminalIP` 存入 `requestHeaders` JSON 对象，通过 `inputVariables.requestHeaders` 传入 runtime。

#### 4. Composition wiring（`agent-app`）

AI 日志逻辑完全在 `agent-app` composition 层的 `postTerminalCallback` 闭包中实现。不修改 `RequestLifecycleDependencies` 接口、不修改 `agent-runtime`。

**Port 注入**：REMOTE 模式下接收外部注入的 `OperationLogGatewayPort` 实例（由另一个 repo 实现），在闭包中被捕获。LOCAL 模式下 port 为 undefined，跳过 AI 日志上报。

**模型名和 km 标记收集**：通过 `RequestLifecycleDependencies.runTimelineEventListeners` 注册一个 listener，按 `runId` 在内存 Map 中收集：
- `MODEL_INVOCATION_COMPLETED` → 取 `inlinePayload.modelId`，加入该 runId 的模型名 Set。
- `CAPABILITY_COMPLETED` → 判断 km 标记：`capabilityId === 'Rag' && status === 'SUCCEEDED'`（agent loop），或 `nodeType === 'KNOWLEDGE_SEARCH' || 'KNOWLEDGE_QA' && status === 'SUCCEEDED'`（workflow）。

内存 Map 在 `postTerminalCallback` 取出后清理对应 runId 的条目。listener 在 port 为 undefined 时不注册。

**多实例降级**：内存 Map 是 process-local。recovery 场景下新实例没有原始事件，resourceName 为空字符串。这是可接受的降级。

#### 5. AI 日志组装（`postTerminalCallback` 闭包）

`postTerminalCallback` 闭包在 run 到达终态时组装 AI 日志 entry：

1. 检查 `OperationLogGatewayPort` 是否存在 — 不存在则跳过。
2. 从 `command.identityContext` 获取 tenantId 和 displayName(userName)。
3. 从 `OSS_LANG`（优先，归一化为连字符格式）或 `command.locale`（降级）解析审计 locale，决定中英文模板和 `systemLang`。
4. 从 `command.inputVariables.requestHeaders` 获取 terminalIP。
5. 从 `run.sessionId` 获取 chatId。
6. 从内存 Map 取出该 runId 的模型名和 km 标记，构建 resourceName，然后清理。
7. 从 `messageStore.listCurrentRequestMessages` 获取 USER message content（question）和最后一条 ASSISTANT message content（answer，截断至 1024 字符）。无 ASSISTANT 消息时 answer 为空字符串。
8. 使用 locale 对应的模板填充 detail。
9. 组装 `OperationLogEntry`，result 按 run 终态决定。
10. 调用 `writeAiLog(entry)`，fire-and-forget。

AI 日志逻辑 MUST 在 `if (status !== 'COMPLETED') return` early-return 之前执行。所有终态都上报：COMPLETED → "SUCCESSFUL"，FAILED/CANCELED → "FAILURE"。

#### 6. 流程接入

**上游**：request lifecycle → terminal commit → terminal timeline event 发布 → `postTerminalCallback` 触发。AI 日志上报发生在 terminal commit 之后，不阻塞 terminal commit。

**下游**：CloudSop 外部合规审计系统，通过 `OperationLogGatewayPort.writeAiLog` 调用。结果不回流到 NextAgent。

**guardrail blocked round**：走 COMPLETED 路径，answer 是拒绝消息，resourceName 为空字符串，无需特殊处理。

## 风险与取舍

- 多实例 recovery 场景下模型名和 km 标记可能缺失。接受此降级以换取零新依赖和架构简单性。AI 日志仍会上报，resourceName 为空字符串。
- AI 日志上报用户原始输入和模型输出，与 `redaction-policy` stable spec 的约束存在表面冲突。论证如下：

  `redaction-policy` 声明"本地 operational runtime log 是唯一受控例外，不得扩散到外部边界"。该约束的适用范围是 **observability 投影面**（StructuredLogProjector、AuditProjector、metric、trace、SafeError、Web API、SSE、WebSocket 等）——它管的是经过 `ObservabilityObservationEvent` sanitization pipeline 的下游消费。

  AI 日志通道 **不经过任何 observability 投影路径**。它是一个独立的合规审计通道，通过 `OperationLogGatewayPort.writeAiLog` 直接向 CloudSop 外部系统上报，路径上没有 projector、没有 sink、没有 `ObservabilityObservationEvent` 消费。因此 `redaction-policy` 的"唯一例外"和"不扩散到外部边界"约束管的是 observability 面，而 AI 日志走的是独立通道，不属于该约束的适用范围。

  AI 日志通道有自己的安全边界：只上报 USER message content（原始用户输入）和 ASSISTANT message content（最终输出，截断至 1024），MUST NOT 上报 prompt 全文、stream delta、tool 调用细节、reasoning、provider raw body、路径、credential 或其他 special field。它是电信合规审计的受控业务例外，不是 observation redaction bypass。
- `OperationLogGatewayPort` 只在 REMOTE 模式创建，LOCAL 模式跳过上报。
- AI 日志组装逻辑在 `agent-app` composition 层 `postTerminalCallback` 闭包中实现，通过注入的 `OperationLogGatewayPort` 上报，不修改 `agent-runtime`、`agent-core` 或 `agent-capability`。
- `OperationLogGatewayPort` 的 HTTP 实现在另一个 repo，本 repo 不提供 factory。两个 repo 的集成点在 composition 层注入。
