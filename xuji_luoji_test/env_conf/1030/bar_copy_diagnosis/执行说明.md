# 当前版本 BAR-copy 定位与修复验收工具

目标：保持当前 HAL、驱动和 Runtime 版本，确定 BAR-copy 能力在哪里变为零；对可以受控验证的修复给出明确结果。此包在 `env_conf/1030/bar_copy_diagnosis`，可独立传输，不依赖仓库其他目录。

**本轮先在虚机执行，裸机不是前置条件。** 新进程初始化一个很小的 NPU 分配，查询 0x2、0x8、0xA 三项能力并采集初始化证据。不要与同设备的业务压测同时运行；业务服务可保持存活，方便检查其实际 PID。

必须区分两个结论：

- “定位到了能力关闭层”不等于“修复已经成功”。
- “BAR-copy 能力恢复”不等于“Runtime 已实际走 BAR-copy”，也不等于业务性能差距全部消失。

**无法保证当前厂商构建一定开放内部诊断字段。** 如果字段缺失，脚本会明确列出缺什么、由哪一层补充，给出 `INSUFFICIENT_EVIDENCE`；不会输出没有证据的“无法修复”或“必须厂商补丁”。仅凭版本、零掩码、历史日志或缺少接口，无法作出这种结论。

## 1. 执行环境和依赖

| 操作 | 执行环境 | 依赖 |
|---|---|---|
| 传输工具 | 本地 Mac → 虚机操作系统 | scp 或已有传输通道 |
| `guest` 首轮诊断、A/B/A | **虚机内原 torch/torch_npu 测试容器** | 64 位 Linux、Python 3.9+、原 torch/torch_npu、当前分配给测试的 NPU |
| `kernel` | **虚机 Guest 操作系统，容器外** | Python 3.9+；sudo 用于读取内核日志，缺少权限会记录状态 |
| `analyze`、`verify` | Mac 或任意装有 Python 3.9+ 的机器 | 标准库，不访问 NPU |
| `performance/run.py` | **虚机原测试容器** | 原环境、原生 cc/gcc/clang；固定设备 0 和已核对的 vm144 CPU/NUMA 配置 |

本包的 `kernel` 命令不是在 KVM 宿主机执行。它读取的是 Guest 内核。首轮不需要登录裸机，也不需要在 KVM 宿主机改配置。

可选的 `strace` 存在时自动用于一个独立的 TRACE 子进程，仅跟踪 mmap/mremap/munmap/brk；没有安装或权限不足时记录不可用，不自动安装。能力采集与 A/B/A 无需 strace、perf、编译器或加载内核模块。

角色名 `--role vm-container` 是操作者声明；容器内不一定能可靠识别底层是 VM 还是物理机，必须按本表选择机器。

## 2. 准备工具

### 2.2 【虚机系统，容器外】解包并进入目标容器

```bash
# 执行位置：虚机 Guest 操作系统，容器外
BAR_RUN=$(mktemp -d /tmp/barcopy1030.XXXXXX)
unzip /tmp/bar_copy_diagnosis_1030.zip -d "$BAR_RUN"
BAR_TOOLS="$BAR_RUN/bar_copy_diagnosis"
BAR_CONTAINER='<虚机上的原torch_npu测试容器名>'

cd "$BAR_TOOLS"
sha256sum -c SHA256SUMS
docker cp "$BAR_RUN" "$BAR_CONTAINER:/tmp/"
docker exec -it --workdir "$BAR_TOOLS" "$BAR_CONTAINER" bash
```

最后一条命令后，已进入虚机容器内、工具目录。外层 Guest 的 `BAR_RUN`、`BAR_TOOLS` 和 `BAR_CONTAINER` 变量仍保存在外层终端，不会自动进入容器。

工具包应与 Mac 的 ZIP SHA256 一致；包内 `sha256sum -c` 应全部通过再执行。

## 3. 【虚机容器内】首轮完整诊断

保持当前版本和业务配置，执行：

```bash
# 执行位置：虚机原 torch_npu 测试容器；当前目录是工具包目录
python3 bar_copy_diag.py guest \
  --role vm-container \
  --device 0 \
  --test-as-limit \
  --out /tmp/bar_copy_vm_before_1030
```

若当前容器实际运行着业务 worker，可以在上面命令中追加 `--worker-pid <实际worker的PID>`。PID 必须是**该虚机容器可见的业务 worker PID**，不能填 KVM 宿主机的 QEMU PID。这个参数只读取进程限制、相关库映射和选定环境变量，不修改或附加到业务进程。

如果微基准容器和业务容器不同，本轮先诊断微基准容器；业务是否存在同样问题还需进入实际业务容器另跑。不要把新建测试进程的限制自动当作业务 worker 的限制。

脚本依次执行：

1. `A0`：新测试进程初始化 NPU，记录 HAL/Runtime 等已加载库的 SHA256、Guest 内核、页大小、进程资源限制、库映射；读取内核提供的 `/proc/svm/dev0/feature` 节点（若有），查询能力。
2. 应用日志仅在测试子进程开启：`ASCEND_GLOBAL_LOG_LEVEL=0`、`ASCEND_SLOG_PRINT_TO_STDOUT=1`，移除该子进程中的 `ASCEND_MODULE_LOG_LEVEL` 覆盖。完整 stdout/stderr 保存为 `A0/process.log`。这些设置不保证厂商构建输出所有驱动或内核字段。
3. 若 A0 能力为零、继承的 RLIMIT_AS 软限制有限且当前硬限制允许更大值：`B1` 仅把**测试子进程**软限制提高到现有硬限制；`A1` 重新使用原限制复测。没有改业务进程、父 shell 或系统硬限制。
4. 若安装了 strace 且 A0 能力为零：单独启动 `TRACE`，记录地址映射失败。TRACE 不是性能测试，也不能直接把它的 errno 当作已证实根因。
5. 自动生成 `结论.md`、`结论.json`、`驱动诊断交接清单.md` 和 `SHA256_MANIFEST.json`。

如果 RLIMIT_AS 已无限制，或软硬限制相等，脚本会跳过此项 A/B/A。跳过不代表所有配置修复都无效。需要提高硬限制的情况应在明确失败原因后，由负责服务启动配置的人处理，不由采集器修改。

设备编号沿用原始编号：`ASCEND_RT_VISIBLE_DEVICES` 非空时停止，不自动清除设备隔离或猜测映射。每个输出目录必须新建，重复执行改用新名称。默认每个子进程最多 120 秒、日志最多 32 MiB；超时/截断会记录，不能用该轮宣告修复。

**本轮使用 Python 查询 NPU0 的能力，不证明其他 7 张卡状态相同。** 需要逐卡验证时，对实际分配给测试的原始设备编号分别执行，每张卡使用不同输出目录。

## 4. 如何读“能不能修复”的结论

| 判定代码 | 能得出的明确结论 | 下一步做什么 |
|---|---|---|
| `AS_LIMIT_FIX_VERIFIED` | 当前记录的软件栈中，放宽测试进程 RLIMIT_AS 后能力恢复，恢复限制后又为零，A/B/A 验证通过 | 核对业务进程是否有同样限制；调整真正施加该限制的启动配置，重启业务后验收 |
| `HAL_FALLBACK_IDENTIFIED` | 日志显示 Guest 内核输入能力非零，HAL 使用 malloc 模式，最终能力为零 | 处理 SVM 地址映射失败；根据同进程地址、长度和 errno 确认具体限制或冲突。尚未证明修复成功 |
| `GUEST_DRIVER_GATE_IDENTIFIED` | HAL 初始化拿到的内核能力已经为零 | 继续查 Guest 驱动的原始设备能力、WC flag、禁用状态及页大小；不能直接断言是 Stage-2 或必须补丁 |
| `HAL_CAPABILITY_MISMATCH` | 内核输入非零、未记录 malloc 回退，但查询结果为零 | 查当前 HAL 的缓存、设备映射和实际实现，不能套用参考源码强行解释 |
| `CAPABILITY_AVAILABLE` | 当前测试进程已经报告支持，本轮未复现“能力为零” | 若业务仍慢，核对业务 worker 是否一致，并查实际 copy policy、参数大小、分配回退与性能 |
| `INSUFFICIENT_EVIDENCE` | 只能确认能力为零，缺少判定关闭层的字段 | 停止重复相同测试，按报告补指定字段；这不是“不可修复”结论 |
| `INVALID_COLLECTION` | 查询、初始化、返回值一致性或日志有效性不满足要求 | 先处理采集错误，不进入根因判断 |

例如，`HAL_FALLBACK_IDENTIFIED` 的下一步可能是修复进程的映射限制，也可能是当前 HAL 的地址空间适配；不能只看 `ENOMEM` 就断言物理内存不足。

内核 `/proc/svm` 节点只读。其值已包含驱动条件和可能的禁用状态，读取零不能区分原因。本工具不写 `1` 强制开启能力，不写 BAR，不使用硬编码私有结构偏移，也不加载诊断内核模块。

## 5. 【虚机系统，容器外】补充 Guest 内核快照并汇总

出现 `GUEST_DRIVER_GATE_IDENTIFIED`、`HAL_CAPABILITY_MISMATCH`、`INSUFFICIENT_EVIDENCE` 时执行这一节。首轮也可以一并采集，减少往返。

先在容器中退出，返回第 2.2 节外层 Guest 终端：

```bash
# 执行位置：虚机容器内；退出后返回原来的 Guest 终端
exit
```

然后执行：

```bash
# 执行位置：虚机 Guest 操作系统，容器外；沿用第 2.2 节的变量
BAR_RESULTS=$(mktemp -d /tmp/barcopy1030-results.XXXXXX)
docker cp "$BAR_CONTAINER:/tmp/bar_copy_vm_before_1030" "$BAR_RESULTS/guest"

sudo python3 "$BAR_TOOLS/bar_copy_diag.py" kernel \
  --device 0 \
  --out "$BAR_RESULTS/kernel"

sudo python3 "$BAR_TOOLS/bar_copy_diag.py" analyze \
  --input "$BAR_RESULTS/guest" \
  --kernel "$BAR_RESULTS/kernel" \
  --out "$BAR_RESULTS/review"

cat "$BAR_RESULTS/review/结论.md"
```

新开了终端时，先把 `BAR_TOOLS`、`BAR_CONTAINER` 设置为之前记录的真实值。这里没有任何命令需要在 KVM 宿主机执行。

内核快照包含当前能力节点、内核/模块版本信息、所需符号是否可见、dmesg 和 npu-smi。接口缺失或权限不足都记录为 unavailable；dmesg 是本次启动的历史日志，不自动当作 A0 初始化的同步证据。分析器核对启动周期、内核和设备编号；容器的逻辑编号与外层物理编号仍需现场核对。

如果报告要求原始 `bar_wc_flag` 等字段而当前版本没有导出接口，交接清单会明确要求：返回码、完整 flag、BAR4 的 0x10 位、赋值者/初始化时序、原始设备能力、禁用状态。此时需要当前驱动维护方提供这些**具体证据**，不能直接把“缺诊断接口”转写成“必须修改驱动”。

## 6. 只有定位到具体限制后，才实施修复

本包不自动更改生产配置。各分支对应的修复责任如下：

| 已有证据 | 实施修复的位置 | 要做的事 |
|---|---|---|
| RLIMIT_AS A/B/A 通过，业务 worker 也存在相同限制 | 实际启动业务的 shell、服务单元或容器启动配置 | 调整对应地址空间限制，保证新 worker 继承正确值，保留原值用于回退 |
| HAL SVM 映射失败及回退已定位 | 虚机业务进程/当前 HAL 初始化 | 根据具体失败地址、长度、errno 处理冲突、限制或初始化适配，不能仅增加物理内存或大页数量 |
| 驱动原始能力正常，但显式禁用或能力发布不正确已证实 | Guest 驱动配置/虚拟化能力提供层 | 按当前版本受支持方式消除错误禁用或修复传递；未核实映射前不强制改能力位 |
| 已证实对应 BAR4 有效映射不满足要求 | KVM 宿主平台维护方 | 评估并提供适配当前构建的 KVM/VFIO 修复及回退；首轮脚本本身不能证明该结论 |

例如，怀疑业务地址空间限制时，先在相应环境只读核对来源：

```bash
# 执行位置：实际运行业务 worker 的虚机业务容器
BAR_WORKER_PID='<该容器内的真实worker PID>'
cat "/proc/$BAR_WORKER_PID/limits"
```

```bash
# 执行位置：虚机 Guest 操作系统，容器外；Docker 部署时
BAR_CONTAINER='<真实业务容器名>'
docker inspect --format '{{json .HostConfig.Ulimits}}' "$BAR_CONTAINER"
```

Docker 的 ulimit 配置为空也不等于业务进程无限制，最终以实际 worker 的 `/proc/<PID>/limits` 为准。具体服务启动/重启命令取决于现场部署方式，本包不猜测服务名。

## 7. 【虚机容器内】修复后复测，再验证是否真的恢复

已实施一个明确修复后，在相同测试环境、相同设备上执行。重建容器时先按第 2 节重新复制工具；修复前目录应先导出保存。

```bash
# 执行位置：修复后的虚机原 torch_npu 测试容器，工具目录
python3 bar_copy_diag.py guest \
  --role vm-container \
  --device 0 \
  --mmap-trace off \
  --out /tmp/bar_copy_vm_after_1030
```

将修复前后结果放到同一机器，然后执行：

```bash
# 执行位置：Mac 或 Guest；以下两个目录均为本机已保存的结果
python3 bar_copy_diag.py verify \
  --before '<修复前guest结果目录>' \
  --after '<修复后guest结果目录>' \
  --change-note '<本轮实际修改的配置或补丁，不能只写已优化>' \
  --out '<新的验收结果目录>'
```

`verify` 会先校验文件 SHA256，检查三种能力查询是否有效且一致，比较设备、HAL/Runtime 等已加载库、版本记录、内核及启动周期。

- `CAPABILITY_RESTORED_SAME_STACK`：记录的软件栈和启动周期相同，修复后能力从零恢复。单组前后结果仍不证明唯一因果，优先重复或回退复测。
- `CAPABILITY_RESTORED_COMPARABILITY_LIMITED`：after 已支持，但重启、容器身份或软件栈差异限制归因。保留已恢复的观察，不能宣称已经证明当前版本某一配置是原因。
- `REPAIR_NOT_VERIFIED`：查询无效、能力没恢复或不满足前后条件，不能宣告修复成功。

## 8. 【虚机测试容器】能力恢复后的路径和性能验收

包内 `performance` 复用了此前已使用的无 perf ioctl 工具。它固定 NPU0、Sub INT32[8]、queue0；必须先核对 `performance/placements.json` 的 vm144 绑定与当前环境相符。若诊断的是其他 NPU，不用这个固定设备 0 的算例替代该设备验收。

修复前、修复后分别在各自环境执行一次，使用不同目录，并在应用日志调试设置关闭的原性能测试环境执行：

```bash
# 执行位置：虚机原 torch_npu 测试容器，工具目录；修复前
python3 performance/run.py --placement vm144 --out /tmp/bar_copy_perf_before_1030
```

```bash
# 执行位置：修复后的同一虚机测试环境，工具目录
python3 performance/run.py --placement vm144 --out /tmp/bar_copy_perf_after_1030
```

检查 correctness、affinity_consistent、探针丢失、无探针 p50，以及 0x41584d09/0x41584d0a 请求数。零捕获只能说明该探针入口没捕获，不单独证明已走 BAR。需要将能力、实际 Runtime 策略/分配、DMA 请求变化和无探针耗时一起判断。

微基准退出码 2 可能是零捕获或丢失/时钟问题，必须看 `instrumented/ioctl_summary.json`；退出码 3 是预检/编译不可用。不要把诊断子进程的详细日志或 TRACE 窗口当成性能结果。

最后在原压测客户端用同数据集、同 8 并发、同缓存/预热和输出配置，对虚机服务复测 3–5 次。只有能力、实际路径和业务结果共同改善，才确认这项修复对性能差距有贡献；本包不自动把微基准收益折算成整个业务 gap。

## 9. 保存并带回结果

在第 5 节 Guest 外层终端中打包结果：

```bash
# 执行位置：虚机 Guest 操作系统，容器外
BAR_RESULT_ARCHIVE="${BAR_RESULTS}.tar.gz"
sudo tar -czf "$BAR_RESULT_ARCHIVE" -C "$BAR_RESULTS" .
sudo chown "$(id -u):$(id -g)" "$BAR_RESULT_ARCHIVE"
sha256sum "$BAR_RESULT_ARCHIVE"
printf '请带回这个结果包：%s\n' "$BAR_RESULT_ARCHIVE"
```

若修复后结果、性能结果位于容器内，先分别 `docker cp` 到本轮 `BAR_RESULTS` 下，再打包。保留原始目录和 SHA256_MANIFEST.json，避免只发截图或改写 JSON。

工具本身不发送结果、不连接互联网、不修改现场驱动、内核或业务配置。结果包含环境路径、软件身份和日志，按现有实验资料通道传输。

## 10. 退出码与本地验证

主工具退出码 0 表示已生成报告，**不表示已经修复**；3 表示平台/参数/文件/采集无效；2 保留给 argparse 参数错误。结论以 `结论.md` 的判定代码为准。普通失败、超时和日志上限均保存可获得的证据，重复运行必须使用新目录。

开发验证在 Mac 执行，没有连接现场 NPU。测试覆盖错误返回与缺字段、不同设备、日志冲突、HAL 回退和 Guest 能力为零的区分、严格 A/B/A、软件栈变化、超时/日志上限、输出防覆盖、文件完整性及前后验收。

```bash
# 执行位置：本地 Mac 或任意开发环境，工具目录
```
