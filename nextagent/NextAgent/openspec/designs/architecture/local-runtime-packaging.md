# Local Runtime Packaging

## 三类本地运行证据文件

LOCAL package 在 `<paths.logDirectory>` 下维护三个互不复用的文件 family：

- operational：`agent-log` owning envelope和可配置 base，默认 100 MiB、daily、gzip、7 elapsed days；local package默认 console off/file on。
- metrics：`LocalMetricHistoryExporter` owning `nextagent-metrics.<date>.<sequence>.ndjson[.gz]`，60s cumulative collection、单行最多 4 MiB、8 MiB buffer、100 MiB、daily、固定 7 elapsed days。
- audit：gateway-local owning `nextagent-audit.<date>.<sequence>.ndjson[.gz]`，write-only versioned record、duplicate-tolerant append、100 MiB、daily、固定 7 elapsed days；不写 SQLite、不提供 query。

三者分别创建 `agent-local-file-roll` handle，不能共享 active identity、buffer、timer、maintenance lane或 close。Package evidence只能证明 policy、active/closed/archive和选择结果；Workbench只读取 app 注入的 current-active operational segment，不扫描目录或读取 metrics/audit/archive。

## Background

This design owns the stable local single-instance runtime package and package candidate evidence facts. The runtime package defines the distributable artifact, extracted candidate root, fixed directory responsibilities, startup/stop entries, config samples, and release-qualification evidence handoff.

The package boundary does not define release verdicts, runtime lifecycle, model invocation, Web streaming, gateway persistence, health semantics, readiness semantics, or fullstack frontend hosting details.

## Decisions

### D1. Archive Artifact Identifies The Candidate

A local release candidate is identified by one OS-targeted package archive and its manifest. The extracted archive root is the candidate root. Release qualification must not infer candidate identity from source workspaces, build logs, temporary directories, or manual notes.

The package output is target-specific: Windows x64 produces a zip, and Linux x64 produces a tarball. The manifest records platform, arch, node version, candidate identity, version, build time, entrypoint refs, config sample refs, layout version, package profile, package archive ref, and evidence refs.

### D2. Directory Responsibilities Are Fixed

The candidate root contains fixed directories: `bin/`, `config/`, `backend/`, `data/`, `logs/`, `run/`, and `workspaces/`. These names are user-visible contract and must not be replaced by manifest-defined aliases.

Startup resolves these directories from the candidate root. It must not depend on the source workspace, global npm workspace, dev server, build temp directory, or current shell working directory. Stop logic only targets the process state recorded by the same package and may clean process-level state under `run/`; it must not delete `config/`, `data/`, `logs/`, or `workspaces/` content.

### D3. Config Samples Are App Composition Inputs

Config samples must be deterministically processed by app configuration validation and must not contain raw secrets. Credential-bearing fields use grammar-valid example `env:` or `file:` references. The first user configuration surface is Node.js plus `OPENAI_MODEL_NAME`. 随包出厂配置样例 MUST NOT 绑定 `OPENAI_API_KEY` 或 `OPENAI_BASE_URL` 环境变量引用：模型 provider 接入参数（`baseUrl` 和 `credentialRef`）由本机配置 overlay 提供，`openai-compatible` 的 `baseUrl` 与 `credentialRef` 均 optional；缺失时该 provider 未配置，模型目录条目为 `UNAVAILABLE`（`unavailableReason=MODEL_PROVIDER_NOT_CONFIGURED`）、应用 `DEGRADED_READY`、模型调用安全失败。`OPENAI_MODEL_NAME` 不受本约束影响。

Missing required env values fail closed with safe startup/config diagnostics. They must not degrade to fake providers, test providers, default external endpoints, or no-op models.

`agent-router-plugin` artifact 同样是 packaging-only 可用性：backend-only 与 with-frontend staging 都通过 `agent-plugin-sdk` 的 `createAgentRouterPluginArtifact()` 写入 `config/plugins/agent-router-plugin/{plugin.json,index.js}`（API `1.2` factory default export、空 `hostExternals`、自包含 bundle）。与 `developer-hook-trace` 不同，pack flow 不向 packaged `config/default-system.yaml` sample 的 `nextAgent.system.plugins[]` 声明该插件，也不修改默认 Agent `policies[]`；artifact 随包可用不等于启用，operator 需显式配置插件并在 Agent policy 中激活 `agent-router-plugin.auto-routing`。

Developer hook trace artifact availability is packaging-only. A backend-capable local runtime candidate includes `config/plugins/developer-hook-trace/plugin.json` and `index.js`, generated by `agent-plugin-sdk`. For backend-capable local `pack:release` candidates, packaging declares `developer-hook-trace` in the packaged `config/default-system.yaml` sample via `nextAgent.system.plugins[]` with `path: "plugins/developer-hook-trace"` and `required: true`, and activates `developer-hook-trace.loop-raw-boundary` in the packaged `agents/default-agent/agent.yaml` for the supported raw loop boundary stages. This default activation is package-staging scoped: packaging must not modify the repository built-in default Agent source definition, must not change non-packaged development startup defaults, and must not enable `context-monitor` by default.

### D4. Package Profile Delegates Fullstack Details

The manifest may declare `backend-only` or `with-frontend`. `backend-only` provides base API, health/readiness, and release qualification evidence. `with-frontend` frontend package contract, static hosting, route precedence, and frontend version lockstep are owned by `fullstack-packaging-boundary`. This design owns only package profile and base runtime package evidence.

`model-gateway-only` 可与 `backend-only` / `with-frontend` 组合。该模式在 manifest 中声明 `modelProviderProfile="model-gateway-only"`，gateway-only TypeScript build 不把 OpenAI-compatible provider invocation implementation 源文件纳入编译输入，staged package 移除该实现和 `@ai-sdk/openai-compatible` dependency。配置含 `openai-compatible`、staged export 缺文件或依赖闭包不完整时，packaging/self-check 必须在成功候选生成前 fail closed；默认 package 继续包含 OpenAI-compatible provider invocation capability。

### D5. PackageCandidateEvidence Is A Handoff

`PackageCandidateEvidence` is owned by `packages/agent-app/src/packaging/package-candidate-evidence.ts` and exported through `@nextagent/agent-app/packaging`. It owns manifest/layout base evidence, E2E execution refs merge, and handoff validation.

Mandatory evidence includes package manifest, layout check result, `configValidationEvidenceRef`, startup proof, and health/readiness proof. `configValidationEvidenceRef` points to the exact `ConfigValidationEvidence` produced by actual candidate startup. Package validation checks presence and candidate association; it must not define or parse a second config evidence shape.

### D6. Evidence Is Safe

Package manifest refs and evidence refs are package-relative safe refs or opaque refs. They must not expose unredacted absolute paths, temporary build paths, raw credentials, provider payloads, stack traces, or adapter-private filesystem layout.

Package evidence is not request truth, checkpoint, timeline event, memory record, or user-visible history.

### D7. Skip Does Not Skip Candidate Startup Validation

`pack:release -- skip` only skips the expensive release E2E gate. It still validates the package candidate as a user-runnable artifact.

After each local runtime workspace package is staged, the pack flow recursively checks the package `exports` map and requires every runtime `import` / `require` target to exist inside the staged package. The check is package-relative and fails closed for missing nested export files rather than accepting a source-workspace `dist/` directory as evidence.

After the archive is created, the pack flow extracts the candidate into a fresh temporary directory and runs the package self-check from that extracted root. This verifies package-relative ESM resolution, entrypoint layout, and startup preconditions that a source workspace check cannot prove. Temporary extraction directories are cleanup-only implementation detail; failure diagnostics must stay package-relative and safe.

### D8. Dev Workbench Remains A Local Projection

`agent-dev-workbench` owns the dev tooling page and its implementation-local read adapter. The local runtime contribution registers the isolated dev namespace, page assets and query handlers; production composition does not include them. The workbench may choose its own frontend libraries, but it does not add an `agent-web` route, production frontend dependency or long-lived product UI state.

Workbench data is projected from existing scoped facts. The read adapter stays outside stable gateway contracts, and `agent-app` supplies only trusted Agent/Owner scope plus narrow local diagnostic sources. Workbench assembly must not add raw capture decorators, dev buffers or lifecycle hooks around model, capability, gateway, policy or context ports. It does not own a durable `DevWorkbench*Record`, raw snapshot, process graph store or generic workbench fact table. Safe projection schemas stay with the package that owns the producing fact; fields derivable from existing records, stable refs or event pairs are computed at query time rather than persisted again. Missing detail remains `partial` or `unavailable` unless an owning production domain independently defines a schema-validated safe fact.

When local with-frontend includes the workbench, its frontend hosting contribution injects a workbench-owned launcher script. The launcher uses an isolated custom element or equivalent boundary, remains independent of `frontend/agent-web` routes, components, state and bundle dependencies, and persists no position outside the current page lifecycle.

## Owners

- `agent-app`: packaging entrypoints, manifest/layout validation, package candidate evidence, and startup config evidence handoff.
- `agent-platform-gateway-local`: consumes package root data/log/run/workspace roots at runtime, but does not own package manifest or release verdict.
- `agent-channel-web`: provides API/stream/control routes in the candidate, but does not own package profile or frontend hosting evidence.
