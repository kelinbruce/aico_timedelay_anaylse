## 背景与问题（Why）

`agent-app` 已经是唯一 composition root，并已有多个职责命名的 composition 文件，但当前启动装配仍缺少一条稳定、连续且可直接阅读的顶层流程。配置加载、启动准备、模块构造、跨模块依赖绑定、诊断接线、失败清理和生命周期组装不仅分散在同步/异步入口和 `create-app.ts` 主函数，还分散在 local configured auth、with-frontend、local runtime package、local gateway/workbench contribution、test composition 和 launcher 路径中；顶层阶段编排、product/test host preparation 与模块内部装配细节仍然混杂。开发者难以从一个入口判断配置何时冻结、模块按什么依赖顺序装配、每个宿主只允许准备什么 contribution、每个阶段产出什么依赖、真实循环如何绑定，以及部分失败后由谁清理已创建资源。

文件拆分本身不是目标。本 change 要解决的真实问题是装配流程缺乏分层与内聚：顶层流程不能清晰表达完整 app construction 路径，product/test/package host 与 launcher 的边界不完整，单个模块的装配事实也没有全部收敛到该模块的唯一装配入口。该问题会增加功能遗漏、装配顺序错误、同步/异步或多宿主路径漂移、测试注入能力丢失、配置重复读取、失败清理不完整和后续能力接入误放 ownership 的风险，因此需要在继续扩展 `agent-app` 前收敛。

## 变更范围（What Changes）

- 建立唯一的顶层 app composition pipeline。完整 app 构造只表达“可信输入与配置准备 → 启动贡献 → Agent 静态装配 → 平台基础设施 → 执行能力 → 应用服务 → runtime/channel → app lifecycle/host handoff”八个宏观层级；第0层内部明确按 identity/clock → bootstrap metrics → config → plugin snapshot load/validation → product-host defaults → remaining sync/async startup contribution preload 形成 `PreparedCompositionInputs`。模块内部的前后 phase 留在模块权威入口内，不把所有私有步骤提升为顶层阶段。`app.start()` 的 producer 启动、ready gate、recovery 和 listen 执行不属于这八层 composition，本 change 只保持其既有顺序和失败投影。
- 将配置文件读取、覆盖合并、secret resolution、runtime validation、ready gate 和冻结收敛到唯一配置加载入口；配置/preparation 对 cron 只冻结并投影 app-private `DISABLED | LOCAL | REMOTE` deployment selection，其中 `DISABLED` 只规范化现有未启用/缺省状态，不新增 public config 值，并且不检查 scheduler、callback credential 或 callback registration。后续装配阶段只消费同一个 `DefaultSystemConfig` 或由其产生的窄配置投影，不再自行读取配置源或环境变量。
- plugin loading 属于 config 后的入口 preparation，而不是 capability 装配。preparation 对 optional injected snapshot、empty config、sync loader 和 async loader应用同一优先级，完成插件读取、校验和冻结；后续 lifecycle definitions、Agent assembly/request policy、capability 与既有安全诊断路径只消费同一个 frozen snapshot 的 hooks、policies、providers 和 diagnostics，不得重新加载插件或让 capability 阶段取得 loader/config-root ownership。
- 每个存在 app-local wiring 的模块只保留一个职责明确的权威 composition 入口，通常位于该模块现有 composition 文件中，内聚 provider/factory 选择、adapter 构造、可选分支、任务注册及返回依赖。复杂模块可以使用同目录私有 helper，也可以因真实前后依赖暴露少量具名 entry，但不得形成第二条竞争装配路径；文件数量和文件名不是验收目标。
- 模块内聚不是终点。每个权威模块入口还必须呈现唯一、连续且可复核的内部装配流程，明确前置输入、核心决策顺序、typed output、直接消费者、可选分支和失败/cleanup 责任；不能只把原来散落的代码移动到同一个文件中。
- cron 不再保留独立、仅覆盖 REMOTE 的 readiness/preflight 校验入口。平台基础设施阶段只按冻结 selection 选择并构造 cron task gateway；执行能力阶段只消费 selection 与 gateway，产出区分 disabled/enabled deployment 的 typed cron capability composition；runtime/channel 阶段再按该 typed result 构造 LOCAL scheduler 或 REMOTE callback verifier/handler/route。每个阶段只在实际消费点检查自己的必需输入。
- 顶层流程通过显式 typed inputs/outputs 连接模块。完整 public options 只允许由入口 preparation 消费一次；唯一 shared root core 可以整体接收同一个只读 `PreparedCompositionInputs`，但不得复制、重建或把它整体下传。模块入口不得接收 `CreateComposedAppOptions`、`PreparedCompositionInputs`、rest-spread options 副本或含义宽泛的 `trusted options` bag。不引入通用 DI container、字符串 token、自动依赖图、可变 service locator 或第二套配置对象。可通过重排消除的依赖循环必须消除；确实无法消除的循环只通过字段固定、单次绑定且显式定义未绑定语义的 typed deferred binding 表达。既有 optional/default lookup 保持 neutral result，只有依赖必需 target 的非法提前调用 fail closed。
- 统一同步/异步产品入口的执行边界和共享装配核心。现有四个 public factory 只作为兼容 facade，不各自拥有 scope 或 pipeline；它们最终只进入一个 app-private sync runner 或一个 app-private async runner。两个 runner 产出同形 `PreparedCompositionInputs`、调用同一 `composeNextAgentApp(...)` 并分别执行 sync/async rollback；async runner 是支持完整产品 preparation/finalization 能力的 canonical path。
- 将 Local、Remote、Test 定义为三种 host input projection，而非三套 app composition。host 只决定受信任的 contribution/default，配置只决定启用的 capability/deployment adapter，且只有 sync/async product preparation 可以形成 `PreparedCompositionInputs`。shared core 不得接收或分支 `hostKind`、`testMode` 或 `LOCAL | REMOTE | TEST` discriminator。因此总结构是“多个 host preparation surface × 一个 core × 两种执行能力”，不是宿主与 factory 的组合爆炸。
- 将 product host composition 收敛为 runner-owned scope 内的可信 preparation 和 handoff。host selector 固定拆成正交的 channel auth profile（`DEFAULT_WEB`/`LOCAL_CONFIGURED_AUTH`）和 frontend hosting profile（`NONE`/`WITH_FRONTEND`）；local/remote package kind 与 local gateway defaults 只是 host facts/contributions，不得冒充第三种 profile。local configured auth、local/remote gateway 和 workbench extension 继续由各自可信宿主选择，并在 shared core 的同一个 channel stage 完成 server registration。`with-frontend` 不再拥有第三个 hosted runner：它只把字段固定的 `ProductHostCompositionInput` 交给唯一 async runner；该 runner 在 core 返回尚未公开的完整 app 后、scope commit 前，仅对该具体 input 调用唯一 typed finalizer，按既有顺序解析/校验 manifest/version并 await 静态托管注册；成功后才 commit/返回。不得形成第二套 core 或通用 post-core hook，也不得在 commit/public return 后补注册。
- 以黑盒装配职责而不是文件数量建立完整 surface inventory。凡是读取或派生 app configuration、解释完整 app/test options、选择 product host/profile/provider、构造 channel contribution、注册 server/plugin/hook、创建或交接 closable resource、选择 app factory、决定 composition rollback 或组装 test product input 的路径，都必须被 design、tasks、并行边界和验证覆盖。inventory 除 `packages/agent-app/src` 外，还固定覆盖 local gateway public/testing facades、remote deployment、根 process host、dev backend launcher 和 workflow demo host；纯 schema/parser、owner factory 实现、package evidence 映射、safe diagnostic 和无装配决策的 launcher helper 不因文件相邻被改动。
- 将 local configured auth 收敛为显式 channel auth profile：只有 local product dependency graph 下的 app-private `local-configured-auth-channel-contribution.ts` 可以静态 import `@nextagent/agent-channel-web-auth-local` 并实现字段固定的 `LocalConfiguredAuthChannelContribution`；公开 facade 只创建/选择该 contribution、把原始 options 和固定 profile 交给唯一 sync runner。production preparation 逐字段读取 extension/prefix 等 public inputs，shared channel entry 只调用窄 contribution，不 import local-auth package；auth config validation、auth instance/plugin 构造、protected Web/extension registration 和 readiness 都在 channel stage 的 contribution invocation 内按统一顺序完成。facade 不复制完整 options、不捕获宽 options bag，也不拥有独立 server registration 路径。
- 将 local runtime package 明确拆成 package preflight/运行证据与 app construction 两段。package host 只拥有 manifest/layout/config-sample 校验、一次 validated/frozen config 产出、packaged Agent definition、candidate evidence、run-state 以及 `app.start()`/`app.close()` 调用；同时按已冻结的运行日志/trace 契约，在同一 package preflight 中先创建唯一 operational writer、再初始化可选 OTLP trace projector，并把二者作为 app-owned injected handles 一次性交给 runner。它只生成一份含同一 config fact和窄 local gateway/workbench contribution的production input：backend-only与with-frontend均进入同一 app-private async runner，后者只额外携带独立 `ProductHostCompositionInput`，两者进入同一 shared core。package host不再重复读取配置、复制完整options、构造第二套 model/gateway 或通用 observability pipeline，或在 runner 已接管 app-owned resource 后重复 cleanup。直接 local start 与 deployment-dispatch start 必须复用同一 package preparation result。
- package-private runner 返回固定 `ProductCompositionOutcome { app, hostFacts }`；public factory/facade 仍只投影原有 `NextAgentApp`。`hostFacts` 只含 package start evidence 所需的安全 gateway readiness facts 和 app-owned safe start-failure reporter，不暴露 credential、路径、raw provider error、完整 config 或可关闭资源，也不改变 public contracts。local package 通过该 outcome 生成既有 provider/readiness evidence并记录 start failure，不得重建 gateway selection 或直接持有/关闭 operational writer。
- 保留 `local-runtime-bindings.ts` 作为 local host adapter：它只动态提供 local gateway factories和 workbench contribution，不拥有 public factory、prepared root state、server lifecycle 或 composition rollback。channel entry 仍是 contribution invocation、route order、identity projection 和 failure handoff 的唯一 owner。
- 将 `create-test-composition.ts` 和 `testing.ts` 纳入同一个 test-host surface。测试宿主可以创建 isolated config/default Agent、deterministic model、local gateway defaults、observation capture 和 test lifecycle registration，并保留当前全部 37 个顶层测试输入，但只能把固定 test projection 投影为普通 product input 并交给同一 sync 或 async runner，不得直接构造 `PreparedCompositionInputs`、复制产品 module order、配置状态机、channel registration 或 cleanup policy。
- backend-only 与 local-configured-auth entrypoint 保持 launcher-only：只选择公开 factory/profile并调用 `app.start()`；with-frontend 的 executable main 只选择 config/profile并调用 public facade；launcher 不读取或规范化 app config、不构造 provider/defaults、不注册 route/plugin，也不拥有 composition rollback。local/remote runtime package 是显式 package host，不套用 launcher-only 规则。
- local gateway public facade 保持对标准 public options 的固定 local-default 投影及 injected override 优先级；其 testing facade 继续提供 local defaults、audit capture、metrics defaults 和 test wrapper。根 `src/main.ts` 是 process host，继续拥有 fatal boundary 与 `app.start()` failure close；dev backend script 是 local development host；workflow demo 是 test/demo host，继续允许在 `app.start()` 前添加现有 CORS hook。它们都只调用一个 product/test runner，不得编排 module order、创建第二个 config state 或接管 composition rollback。demo hook 不属于产品 route/plugin registration，产品宿主仍禁止 commit/public return 后补注册。
- 保持启动成功、启动失败安全投影、readiness、capability/workflow/memory/question availability、Web/local auth/workbench/frontend hosting/task channel、cron、health、observability、background task、upload cleanup、RAG governance、active Agent assembly refresh、runtime recovery identity、完整 `NextAgentApp` projection 和正常 shutdown 等现有外部行为；补充 public input/output/host fact characterization、integration 和 architecture negative tests，防止功能遗漏和装配职责再次散落。product profile 行为必须保持：backend-only 不加载 frontend artifact；Web/local auth/workbench/task/cron registration 在 core 内完成；with-frontend 的 `productVersion`、`resolveFrontendHostingManifest`、`indexHtmlScripts`、local gateway/workbench defaults、default-workbench script 注入条件、candidate evidence/version validation、异步 hosting registration、route exclusivity、protected prefix、SPA fallback-last 和错误优先级必须同形保持。只把 scope commit/public return 延后到 async runner 的 typed finalization 成功之后；cron 多项非法 prerequisite 的跨阶段优先级按下一条明确修正。
- cron 黑盒分支固定为：`DISABLED` 不创建 cron capability/runtime；`LOCAL` 要求 selected cron task gateway，并在创建 scheduler 时要求 scheduler factory；`REMOTE` 要求 selected cron task gateway，并在创建 verifier 时要求 callback credential reference、在注册 route 时要求 callback registration。缺失依赖继续返回既有 `CRON_TASK_GATEWAY_UNAVAILABLE`、`CRON_TASK_SCHEDULER_FACTORY_REQUIRED`、`CRON_CALLBACK_CREDENTIAL_REQUIRED` 或 `CRON_CALLBACK_REGISTRATION_REQUIRED`。多项依赖同时缺失时按真实阶段/消费顺序失败：selected gateway 先于 LOCAL/REMOTE runtime prerequisite，REMOTE runtime 内 credential 先于 registration。未选中分支的专属输入必须被忽略，task → cron → optional frontend 的 route 顺序和真实 `cronTriggerCallbackRegistration.ready()` lifecycle gate 保持不变。
- 本 change 的黑盒可靠性修正仍只有两项：其一，对“装配过程中已经创建，或按既有契约已接受为 app-owned，但尚未 commit 给最终 app lifecycle 的可关闭资源”补充统一的逆序、至多一次 cleanup，当次唯一 sync 或 async runner 是 scope create/commit/rollback policy 的唯一 owner；caller-owned injection 不得被新增 cleanup 接管；其二，把 background runtime timeline 的非法未绑定调用从静默丢弃改为 typed deferred binding fail-closed。cron prerequisite 从 root 早期预检移到实际 gateway/capability/runtime 消费点属于 ownership 和失败归因校正，不新增可达能力，也不改变成功路径、每个单项缺失对应的 public safe error code/category/retryability、既有 injected/app-owned ownership、`app.start()` 顺序或正常 shutdown 顺序；它只把多个同时无效输入的错误优先级改成真实阶段顺序。非法 REMOTE runtime 配置可以在 frozen config 已被接受后于 cron runtime composition 失败，并必须由同一 failure scope 清理此前已交接资源。
- 本 change 是内部架构重构，不新增或修改 public Web API、runtime command、stream event、`agent-contracts`、gateway schema、持久化数据、配置格式、Agent package 格式、provider contract 或 request lifecycle 语义。
- 本 change 不删除或废弃 sync factory。它们仍是已有 public compatibility surface，但只支持可同步完整准备的输入，不得静默跳过或降级 async-only preparation/finalization。若未来删除 sync API，必须由独立 change 盘点和迁移跨包 public exports、remote/local/testing facades 与存量调用方，不得作为本次内部收敛的顺带破坏性修改。
- 实施必须在 `add-ts-runtime-operational-log-hardening` 与 `add-otlp-trace-export` 的实现完成并形成稳定基线后开始；归档状态可以滞后，但前提是两项剩余工作仅为验证/归档收尾，且在本 change 实施期间不再并行修改 `create-app.ts`、observability composition、app lifecycle 或 local runtime package。本 change 只消费其最终 writer/trace 初始化与关闭语义，不重新定义其 contract。
- `NextAgentApp.start()` 内部 producer/ready/recovery/listen 顺序及 start-phase transactional rollback 不属于本 change；八层 pipeline 在返回完整 `NextAgentApp` 并交接 lifecycle ownership 时结束。所有 launcher 的 start failure 自动 close 一致性应由独立 reliability change 处理，不进入本 change tasks 或 acceptance。
