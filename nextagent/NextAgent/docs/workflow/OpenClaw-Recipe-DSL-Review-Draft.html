1. 背景与目标

当前存在两类规范来源：

  • OpenClaw Workflow / TaskFlow：偏通用工作流编排，强调串行、并行、DAG、审批、断点续跑、批处理和资源治理。
  • Recipe specification：偏对话式 Agent 领域 DSL，强调 RAG、意图识别、问题改写、API/Recipe 选择、Guardrail、PIU 展示与推荐问题。

本次评审目标不是给出最终实现，而是帮助团队先达成规范层的共识：

目标一 明确 OpenClaw 与 Recipe 是否属于同一层规范。
目标二 给出 DSL 格式收敛方向，避免未来继续分叉。
目标三 明确 Recipe 需要补哪些节点能力，哪些不该纳入核心 DSL。
目标四 给出可落地的分层草案，支撑后续规范和实现演进。

2. 评审摘要

评审问题 OpenClaw 与 Recipe 是否应收敛为单一规范，以及 Recipe 是否需要吸收 TaskFlow 风格的编排能力。
核心判断 两者不属于同一抽象层。OpenClaw 更偏通用编排引擎，Recipe 更偏对话式 Agent 领域 DSL。
推荐方向 建立 Recipe Core DSL + Runtime Profile 双层规范，先统一 DSL 格式，再补最小必要节点能力。
本稿定位 评审讨论材料，用于做方向决策，不等同于最终规范定稿或实现设计。
本次评审期待结论 重点不是逐字段定稿，而是先确认是否采用分层模型、DSL 收敛原则和节点补齐边界。方向一旦确认，后续再进入字段和 schema 级细化。

2.1 本次基于 OpenClaw 新引入的重点 NEW FROM OPENCLAW

DSL 补强

runtime 分层

将执行器能力从 Recipe 核心节点定义中剥离，避免资源治理和业务 DSL 混杂。

控制流补强

dependsOn

引入 DAG 依赖表达，支持复杂诊断流和并发取数流，不再只靠 next 跳转。

人工介入补强

approval / suspend

把流程审批和挂起恢复提升为一等能力，不再仅用 user-check 或 interrupt 近似表达。

批处理补强

fan-out

引入批量展开与受控并发能力，更适合批量告警、批量网元、批量工单类场景。

执行控制补强

通用 retry / timeout

把执行控制提升为节点通用语义，避免各节点私有化重复定义。

本稿收敛原则 以当前 Recipe 为基础，不引入整套 OpenClaw DSL，只吸收少量高价值、低侵入、可统一复用的通用编排能力，整体收敛满足 KISS。

4. 建议结论

推荐结论 不建议将 OpenClaw 直接整体并入 Recipe。建议建立 Recipe Core DSL + Runtime Profile 双层规范：前者定义领域编排，后者定义执行器能力。
保留 Recipe 的领域价值 吸收最小必要编排能力 执行器能力不污染核心 DSL 避免一次性破坏式合并

为什么不建议直接合并

  • 两者抽象层级不同。OpenClaw 更像通用编排引擎，Recipe 更像 Agent 领域 DSL。
  • OpenClaw 的优势主要在调度、持久化、审批、资源治理；Recipe 的优势主要在对话编排、RAG、Guardrail 和展示投影。
  • 如果直接合并，规范会同时承载“业务语义、会话语义、执行器细节、资源治理”，很快失控。

建议的收敛方式

  1. 先统一 DSL 骨架和变量/条件写法。
  2. 只补齐 Recipe 缺失但明显属于通用编排的最小能力。
  3. 将资源规格、空闲休眠、后台运行等执行器特性下沉到 runtime profile。

5. OpenClaw 与 Recipe 能力对比

维度 OpenClaw Recipe 判断
核心定位 通用工作流 / 任务流编排 对话式 Agent 领域 DSL 不是同一层规范
编排模型 串行、并行组、DAG、状态机 节点图、条件跳转、局部 loop OpenClaw 更工程化
对话与 RAG 偏通用，依赖 tool/skill 组合 原生支持意图、改写、RAG、API 选择、Guardrail Recipe 更领域化
审批 / 长任务 支持审批、挂起、断点续跑 有 user-check / interrupt，但语义不完整 Recipe 需要补齐
批量并发 支持 fan-out、DAG 并发 loop 能力局部、批量表达弱 Recipe 需要补齐
展示投影 弱 强，具备 output_parser / recommends / REJECT Recipe 应继续保留
资源治理 强，含 resource_spec / idle_sleep / incremental 弱 建议下沉到 runtime profile

6. Recipe vNext DSL 格式草案 OpenClaw 引入点已标识

核心思路：保留 Recipe 的节点图模型，但统一顶层结构、节点骨架和变量/条件语法。

6.1 顶层结构建议

字段 建议状态 说明
name / description / domain / scene / version 保留 继续作为核心元数据。
inputs 新增/强化 显式声明输入契约，方便静态校验。
runtime OpenClaw 新增 承载执行器相关策略，避免污染节点定义。
presentation 新增 承载全局展示配置，与执行逻辑分层。
schema_version 逐步废弃 保留兼容位，但不再作为主建模字段。
expandFields 替换为 metadata 避免无限制扩张。

6.2 节点通用骨架建议

node_id:
  type: llm-router
  description: 节点说明
  when: ${input.enabled == true}
  dependsOn: [node-a, node-b]   # OpenClaw-style DAG dependency
  inputs: {}
  outputs: {}
  retry:
    max_attempts: 2
    backoff: fixed
    delay_seconds: 3
  timeout: 30
  next:
    next-node: true
  presentation: {}

6.3 变量与条件语法建议

  • 统一只保留 ${...} 作为正式引用语法。
  • 普通字段、Prompt 插值、条件表达式都使用同一套引用方式。
  • 建议废弃 {{...}} 与 global_vars.xxx 这类运行时泄漏式写法。
建议写法 输入引用使用 ${input.input_question}，节点结果使用 ${search-knowledge.knowledge_hits}，当前节点输出映射使用 ${node.result.xxx}。

6.4 顶层示例

name: alarm-root-cause-analysis
description: Analyze alarm root cause and generate remediation guidance
domain: telecom
scene: alarm-diagnosis
version: 2.0.0
lang: zh
type: recipe

inputs:
  input_question:
    type: string
    required: true
  alarm_ids:
    type: array
    required: false

runtime:
  profile: taskflow
  timeout: 3600
  incremental: true
  default_retry:
    max_attempts: 2
    backoff: fixed
    delay_seconds: 3

presentation:
  recommends:
    enabled: true

nodes:
  start:
    type: start-event
    next:
      rewrite-question: true

  rewrite-question:
    type: question-rewriting
    inputs:
      source: ${input.input_question}
      context_round: 4
    outputs:
      rewritten_question: ${node.result.rewritten_question}
    next:
      route-intent: true

  route-intent:
    type: intent-recognition
    inputs:
      query: ${rewrite-question.rewritten_question}
    outputs:
      intent_type: ${node.result.intent_type}
    next:
      reject: ${route-intent.intent_type == "HandleUnsupportedIntent"}
      search-knowledge: ${route-intent.intent_type != "HandleUnsupportedIntent"}

  search-knowledge:
    type: knowledge-search
    inputs:
      query: ${rewrite-question.rewritten_question}
      rag_index:
        - index_name: telecom_alarm_knowledge
          priority: 1
    outputs:
      knowledge_hits: ${node.result.knowledge_search_result}
    next:
      summarize: true

  summarize:
    type: llm-router
    inputs:
      prompt_template: |
        请基于以下知识生成根因分析与处置建议：
        ${search-knowledge.knowledge_hits}
    outputs:
      answer: ${node.result.llm_completion}
    presentation:
      output_parser:
        type: TEXT
        message_level: ANSWER
    next:
      end: true

  reject:
    type: display-content
    outputs:
      message: 当前问题不在能力范围内
    presentation:
      tag: REJECT
    next:
      end: true

  end:
    type: end-event

7. 节点范围补齐建议

7.1 应保留为 Recipe 核心特色的领域节点

llm-router question-rewriting intent-recognition guardrail-check knowledge-search knowledge-qa api-choice recipe-choice tool-choice display-content sub-recipe agent translation

这些节点代表 Recipe 的核心领域价值，不建议被过度抽象成通用 workflow 原语。

7.2 建议从 OpenClaw 吸收的最小必要能力 重点评审

能力 建议状态 原因
dependsOn OpenClaw 建议新增 增强复杂诊断流、并发取数流的表达力。
approval OpenClaw 建议新增节点 user-check 偏对话输入，不等于流程审批。
fan-out OpenClaw 建议新增节点 适合批量网元、批量告警、批量工单处理。
通用 retry / timeout OpenClaw 建议提升为通用字段 避免每个节点私有化定义执行控制。
suspend/resume OpenClaw 建议标准化 比现有 interrupt-gateway 语义更完整。

7.2.1 整体收敛建议：以当前 Recipe 为基础

类别 建议引入 暂不引入 原因 KISS 判断
DSL 结构 runtime、统一 ${...}、通用 retry / timeout 执行器内部缓存/资源调度 DSL 前者解决结构混杂和重复定义，后者属于运行时实现细节。 引入少量统一原语，收益高且侵入低。
控制流 dependsOn 优先新增显式 parallel 节点 dependsOn 已可覆盖大部分 DAG 并发依赖场景，原语更少。 先用最少新增能力补足表达力。
人工介入 approval、suspend 继续扩张 user-check 语义 user-check 更像交互输入，不适合作为流程审批的唯一承载。 语义边界更清楚，避免一个节点承载多种责任。
批处理 fan-out 继续用局部 loop 承担所有批量场景 fan-out 更适合批量网元、批量告警、批量工单。 新增一个稳定批处理原语，替代复杂 loop 变体。
资源治理 下沉到 runtime profile resource_spec、idle_sleep、后台降权直接进入 Core DSL 这些能力属于执行器，不应污染领域 DSL。 保留边界，避免 DSL 快速膨胀。

7.3 建议新增节点示例

approve-remediation:
  type: approval
  description: Wait for operator approval
  inputs:
    message: 请确认是否执行处置建议
    approvers:
      - ops-owner
    expire_seconds: 86400
  outputs:
    approved: ${node.result.approved}
    comment: ${node.result.comment}
  next:
    execute-remediation: ${approve-remediation.approved == true}
    reject-remediation: ${approve-remediation.approved == false}

analyze-each-alarm:
  type: fan-out
  description: Batch process alarms
  inputs:
    source: ${input.alarm_ids}
    item_name: alarm_id
    max_concurrent: 4
    body:
      type: knowledge-search
      inputs:
        query: 分析告警 ${alarm_id} 的根因
        rag_index:
          - index_name: telecom_alarm_knowledge
  outputs:
    results: ${node.result.items}
  next:
    aggregate-results: true

wait-external-callback:
  type: suspend
  description: Wait for external callback
  inputs:
    reason: 等待外部系统回调
    resume_token: remediation_callback
    timeout_seconds: 7200
  outputs:
    resumed: ${node.result.resumed}

7.4 不建议直接放进 Core DSL 的能力

建议放入 Runtime Profile，而非 Core DSL

resource_spec、idle_sleep、后台降权、引擎缓存策略、模型实例复用、显存回收策略等，属于执行器实现或 runtime contract，不建议直接扩进领域节点定义。

8. Runtime Profile 分层建议 OpenClaw 核心借鉴

建议把执行器相关能力从 Recipe 核心规范中剥离，形成独立的 runtime profile。这样 Recipe 负责表达业务和编排意图，执行器负责解释和承载运行时策略。

8.1 建议分层

层级 职责 示例
Recipe Core DSL 定义节点图、领域节点、变量引用、条件跳转、最小控制流。 llm-router、knowledge-search、approval、fan-out
Runtime Profile 定义调度、重试、超时、持久化、挂起恢复、资源规格、增量执行等。 profile: taskflow、incremental: true、default_retry

8.2 示例

runtime:
  profile: taskflow
  timeout: 3600
  incremental: true
  persistence:
    checkpoint: true
  default_retry:
    max_attempts: 2
    backoff: fixed
    delay_seconds: 3
  resource_policy:
    class: standard
收益 同一份 Recipe Core DSL 可以运行在不同执行器上；未来如果有轻量执行器与持久化执行器，也可以通过 profile 做能力分级，而不是复制整套 DSL。

9. 兼容性与迁移策略

9.1 迁移原则

  1. 先兼容新增，不做一次性破坏式切换。
  2. 先统一格式，再补运行能力。
  3. 旧节点名和旧字段先保留映射，再逐步废弃。

9.2 迁移阶段建议

阶段 动作 目标
Phase 1 引入 runtime、presentation、统一节点骨架、统一 ${...} 写法 新旧 DSL 共存
Phase 2 新增 dependsOn、approval、fan-out、通用 retry/timeout 补齐最小必要编排能力
Phase 3 将 schema_version、expandFields、{{...}} 标记为 deprecated 清理历史包袱

9.3 建议兼容映射

  • interrupt-gateway 可映射为 suspend。
  • user-check 保留为用户输入型节点，不替代审批节点。
  • 历史 loop 继续保留，复杂批量场景推荐迁移到 fan-out。
风险提示 如果在没有先统一 DSL 骨架的前提下直接引入大量 TaskFlow 能力，最终很可能得到一套同时支持多种变量语法、多种节点骨架、多种控制流入口的混合 DSL，维护成本会显著上升。

10. Recipe 1.0 → 2.0 切换策略

切换策略应遵循“先兼容、再引导、后收敛”的原则，不做一次性整体重写。目标是在不打断现有 Recipe 生产使用的前提下，逐步把 1.0 引导到 2.0。

10.1 版本定位

版本 定位 特点
Recipe 1.0 现有生产基线 保留历史字段、双变量语法、现有节点图模型。
Recipe 2.0 收敛后的目标态 保留领域节点体系，新增最小必要编排原语和 runtime 分层。

10.2 切换原则

  1. 老 Recipe 不强制立即迁移，2.0 先作为推荐新写法。
  2. 同一时期允许 1.0 与 2.0 共存，但新建/大改场景优先使用 2.0。
  3. 迁移优先改“格式收敛项”，后改“控制流增强项”，最后再清理历史兼容字段。

10.3 分阶段切换

阶段 目标 主要动作 对业务影响
Phase A：兼容引入 2.0 能被解析，但不破坏 1.0 引入 runtime、通用 retry/timeout、dependsOn、approval、fan-out、suspend 低，旧 Recipe 无需修改
Phase B：新写法优先 新增和大改 Recipe 默认采用 2.0 规范、模板、样例、校验器全部以 2.0 写法为主 中，新增需求开始按新写法落地
Phase C：定向迁移 把高价值老 Recipe 迁到 2.0 优先迁移复杂诊断流、长周期流、批量处理流 中，按收益逐步推进
Phase D：兼容清理 减少历史包袱 将 {{...}}、schema_version、expandFields 等标记废弃并逐步下线 可控，需要提前公告和校验兜底

10.4 单个 Recipe 的推荐迁移顺序

  1. 先保持业务语义不变，只做格式收敛：统一变量引用、补 runtime、把节点展示能力收进 presentation。
  2. 再识别是否真的需要新增原语：复杂依赖流引入 dependsOn，审批流引入 approval，批量流引入 fan-out。
  3. 最后才替换历史近似能力：如将部分 interrupt-gateway 演进为 suspend。

10.5 兼容策略建议

  • {{...}} 与 ${...} 在过渡期可并存，但规范推荐只写 ${...}。
  • user-check 继续保留，但定位为“用户交互节点”，不再承担审批语义。
  • loop 继续保留，但批量并发类新场景优先使用 fan-out。
  • interrupt-gateway 可通过兼容层映射到 suspend。
推荐切换结论 Recipe 2.0 不是对 1.0 的推倒重来，而是在保持领域节点体系稳定的前提下，做一次“结构收敛 + 最小编排补强 + 执行器分层”的平滑升级。

11. 建议带入评审会的决策项

决策 1： 是否接受 OpenClaw 与 Recipe 不属于同一层规范，而采用 Core DSL + Runtime Profile 双层模型。
决策 2： 是否接受先统一 DSL 格式，再补节点能力，而不是直接扩充节点集合。
决策 3： 是否接受变量引用统一为 ${...}，并逐步废弃 {{...}} 与历史运行时泄漏写法。
决策 4： 是否接受只将 dependsOn、approval、fan-out、通用 retry/timeout 作为最小必要补齐能力纳入 Recipe。
决策 5： 是否接受将资源治理、空闲休眠、后台降权等能力放入 runtime profile，而不是进入核心节点 DSL。
推荐会后动作 如果以上 5 个决策项达成一致，下一步建议产出正式规范初稿，包括：字段定义表、节点 schema、兼容矩阵、迁移指引以及实现承接建议。
