# 虚机与裸机性能差距修复操作指南

日期：2026-10-30。

当前优先处理两项问题：恢复虚机参数下发的 BAR-copy 快速路径，以及验证并消除仍存在的 Host 线程拖后。先完成驱动路径实验，再做线程专核实验，每轮只改变一类因素。

历史记录：同一 8 并发模型测试中，裸机 E2E 为 7987.733 ms，当前虚机为 9403.652 ms，相差 17.73%。10 月 29 日查询中，裸机可见驱动包为 26.1.2、虚机为 25.5.0，实际 HAL 哈希不同；裸机 BAR-copy 查询返回支持，虚机成功返回但支持位为零。10 月 27 日采样发现 Rank 6 拖后，但该现象需要在当前最终配置下重新确认。

本文中的 `vm144`、`bare192`、CPU 池以及 VM 名称来自现有实验。现场拓扑变化时先核对，不能直接套用历史 CPU 编号。文中的尖括号占位符必须替换。命令按执行位置分段，跨机器或新开 shell 后需要重新设置该段变量。

## 1. 准备工具并建立本轮目录

裸机需要同期对照时，将同一个包也传到裸机。若现场使用已有的文件传输通道，可使用该通道传输这个包。

### 1.2 在 Guest 操作系统中复制到业务容器

以下示例使用 Docker，容器名和文件名需要替换；其他容器运行时使用相应文件复制方式。

记录实际目录。重新进入容器后，将以上变量设置为已记录的目录；不要重新生成目录后误用旧结果路径。驱动修复需要重建容器时，先导出修复前结果，再在新容器中重新解包。

## 2. 先确认旧驱动来自 Guest 还是容器

### 2.1 在容器外 Guest 操作系统执行

```bash
VMGAP_GUEST_CHECK=$(mktemp -d /tmp/aico-guest-driver-1030.XXXXXX)
uname -a > "$VMGAP_GUEST_CHECK/kernel.txt"
getconf PAGESIZE > "$VMGAP_GUEST_CHECK/base_page_size.txt"
cat /usr/local/Ascend/driver/version.info > "$VMGAP_GUEST_CHECK/driver_version.txt"
sha256sum /usr/local/Ascend/driver/lib64/driver/libascend_hal.so > "$VMGAP_GUEST_CHECK/hal_sha256.txt"
lsmod > "$VMGAP_GUEST_CHECK/lsmod.txt"
npu-smi info > "$VMGAP_GUEST_CHECK/npu_smi.txt"

cat "$VMGAP_GUEST_CHECK/driver_version.txt"
cat "$VMGAP_GUEST_CHECK/hal_sha256.txt"
```

`version.info` 和 HAL 文件只能说明对应用户态包。Guest 内核驱动构建及物理卡固件仍需依据现场已加载模块和厂商版本信息核对，不能仅凭 `ascendhal_version` 字段判断整个驱动栈一致。

### 2.2 在业务容器内执行

```bash
uname -a > "$VMGAP_RESULTS/container_kernel.txt"
cat /usr/local/Ascend/driver/version.info > "$VMGAP_RESULTS/container_driver_version.txt"
sha256sum /usr/local/Ascend/driver/lib64/driver/libascend_hal.so > "$VMGAP_RESULTS/container_hal_sha256.txt"

cat "$VMGAP_RESULTS/container_driver_version.txt"
cat "$VMGAP_RESULTS/container_hal_sha256.txt"
```

还应检查实际业务 worker 加载的库，避免磁盘文件更新后旧进程仍使用旧库：

```bash
VMGAP_WORKER_PID='<该容器内的实际worker PID>'
awk '/libascend_hal\.so/ {print}' "/proc/$VMGAP_WORKER_PID/maps" \
  > "$VMGAP_RESULTS/worker_hal_maps_before.txt"
cat "$VMGAP_RESULTS/worker_hal_maps_before.txt"
```

### 2.3 根据结果选择修复分支

| 结果 | 要实施的修复 | 完成后检查 |
|---|---|---|
| Guest 已是目标配套，容器仍显示旧包或旧 HAL | 修正容器启动配置中的驱动目录挂载、旧库覆盖及库搜索路径，使实际进程加载 Guest 配套的用户态驱动库；重建容器或重启服务 | 容器版本、实际加载路径和 HAL 哈希符合目标配套 |
| Guest 本身也是 25.5.0 | 按 Ascend910B4-1、Guest OS、物理固件和虚拟化平台的支持组合更新完整 Guest 驱动栈；同步处理容器库来源 | 版本、模块与固件配套正确，NPU 初始化及业务正确性通过 |
| 版本及库来源已经对齐，但能力仍为零 | 进入第 5 节，处理 WC 映射或能力提供链路 | 能力与实际 Runtime 路径发生预期变化 |

裸机 26.1.2 是候选对照版本，尚不是已证明适配当前 Guest/固件的安装目标。准确安装和卸载命令应使用选定驱动包的对应说明，当前没有足够信息写出统一升级命令。不要只复制一个 HAL 文件到旧 Guest 驱动上，也不要把物理固件升级命令放到 Guest 执行。

若需要检查 Docker 挂载，可在 Guest 中执行：

```bash
VMGAP_CONTAINER='<业务容器名>'
docker inspect --format '{{json .Mounts}}' "$VMGAP_CONTAINER" \
  > "$VMGAP_GUEST_CHECK/container_mounts.json"
cat "$VMGAP_GUEST_CHECK/container_mounts.json"
```

本轮先保留 NUMA、CPU 池、大页、OMP 线程数、模型参数和图配置，避免与驱动修复同时改变。

## 3. 保存修复前的能力与无探针基线

在原 torch/torch_npu 测试容器中执行。能力查询和微基准是独立测试进程；不要与业务压测或其他 NPU 测试同时运行。

### 3.1 查询能力

```bash
cd "$VMGAP_IOCTL_DIR"
python3 query_copy_capability.py \
  --device 0 \
  --out "$VMGAP_RESULTS/vm_copy_capability_before_npu0.json"
```

保持原始设备编号，不使用 `ASCEND_RT_VISIBLE_DEVICES` 重排设备，也不要预加载 ioctl 探针运行该查询。脚本检测到这些条件会拒绝执行；不要直接解除可见设备限制后访问原本不属于该测试的卡。此脚本会初始化一个很小的 NPU 分配，并记录实际加载 HAL 的身份。

如 8 张原始编号 0–7 的卡都属于本次测试，NPU0 查询成功后可补查其余卡：

```bash
for VMGAP_DEVICE in 1 2 3 4 5 6 7; do
  python3 query_copy_capability.py \
    --device "$VMGAP_DEVICE" \
    --out "$VMGAP_RESULTS/vm_copy_capability_before_npu${VMGAP_DEVICE}.json" || break
done
```

检查 `status`、各项 `return_code`、`output_mask_hex` 和 `hal_library.sha256`。错误状态保留为未知，不能把查询失败解释为不支持。

### 3.2 保存无探针与 ioctl 对照

```bash
python3 run.py --placement vm144 --out "$VMGAP_RESULTS/vm_ioctl_before"
```

脚本自动检查编译器，依次运行两个独立进程：无探针基线与有探针测量。算例固定为设备 0、Sub INT32 `[8]`、queue0、每批 256 次、20 批，测试进程中设置 OMP_NUM_THREADS=1。它不代表 8 卡业务测试，也不要求将业务的 TASK_QUEUE_ENABLE 或 OMP 设置改成这些值。

裸机同期对照在裸机原容器中运行同一工具包，设置该容器自己的 `VMGAP_IOCTL_DIR`、`VMGAP_RESULTS` 后执行：

```bash
cd "$VMGAP_IOCTL_DIR"
python3 query_copy_capability.py --device 0 --out "$VMGAP_RESULTS/bare_copy_capability_npu0.json"
python3 run.py --placement bare192 --out "$VMGAP_RESULTS/bare_ioctl_control"
```

输出目录和 JSON 文件必须是新的。需要重复运行时使用新名称，例如 `_before_2`、`_after_2`，不要覆盖已有结果。

## 4. 驱动或容器库修复后验收

第 2 节选定的修复完成、NPU 初始化正常、测试进程重新启动后，在同样的测试环境运行：

```bash
cd "$VMGAP_IOCTL_DIR"
python3 query_copy_capability.py \
  --device 0 \
  --out "$VMGAP_RESULTS/vm_copy_capability_after_npu0.json"
python3 run.py --placement vm144 --out "$VMGAP_RESULTS/vm_ioctl_after"
```

如果 before 检查了其余卡，after 也按同样设备编号逐卡查询，使用 `after_npu1.json` 等新文件名。

查看测试结果：

```bash
python3 -m json.tool "$VMGAP_RESULTS/vm_copy_capability_after_npu0.json"
python3 -m json.tool "$VMGAP_RESULTS/vm_ioctl_after/comparison.json"
python3 -m json.tool "$VMGAP_RESULTS/vm_ioctl_after/instrumented/ioctl_summary.json"
```

| 验收项 | 判定方式 |
|---|---|
| 测试有效 | `baseline/summary.json` 与 `instrumented/summary.json` 的 correctness、affinity_consistent 均通过；探针无丢失 |
| 能力变化 | 原来的全零变为有效 0x2 或 0x8 支持位；不要求必须返回完整 0xA |
| 实际路径变化 | 固定算例中的 0x41584d09 / 0x41584d0a DMA 请求减少；若能力变为支持但请求不变，查实际 policy、参数大小和分配回退 |
| 性能变化 | 比较 `comparison.json` 中的 `baseline_total_p50_us_per_op`，以及原始 20 批计时；与修复前和同期裸机对照 |
| 业务变化 | 用原 8 并发业务验证 E2E，不能用单算例耗时直接折算收益 |

历史无探针对照为裸机 15.613、虚机 28.807 μs/op，可作为参照，验收以同期重复结果为准。有探针的 8.173 μs/op 是观测到的两接口累计成本，不是可回收净差值。

裸机或修复后可能返回退出码 2：这可能是没有捕获到 ioctl，也可能是丢失/时钟问题，必须查看 `ioctl_summary.json` 的实际状态。零捕获只说明这个 libc 入口和窗口没有捕获，不能单独证明 BAR-copy 已启用。退出码 3 表示预检/编译不可用，不是性能结果。

## 5. 能力仍为零时的 WC 和 Stage-2 修复分支

此分支由驱动、虚拟化和宿主内核维护方处理，不能靠用户态强制返回 capability 位代替底层支持。

### 5.1 在 KVM 宿主采集当前运行配置

```bash
VMGAP_VM='instance-00000b34'
VMGAP_HOST_CHECK=$(mktemp -d /tmp/aico-host-1030.XXXXXX)

uname -a > "$VMGAP_HOST_CHECK/kernel.txt"
cat /proc/cmdline > "$VMGAP_HOST_CHECK/cmdline.txt"
virsh domstate "$VMGAP_VM" > "$VMGAP_HOST_CHECK/domain_state.txt"
virsh dumpxml "$VMGAP_VM" > "$VMGAP_HOST_CHECK/domain_live.xml"
virsh vcpupin "$VMGAP_VM" --live > "$VMGAP_HOST_CHECK/vcpupin_live.txt"
virsh emulatorpin "$VMGAP_VM" --live > "$VMGAP_HOST_CHECK/emulatorpin_live.txt"
lscpu -e=CPU,NODE,SOCKET,CORE,ONLINE > "$VMGAP_HOST_CHECK/cpu_topology.txt"
```

使用有权查询该 VM 的账号；需要时在相关 `virsh` 命令前加 sudo。确认 VM 处于运行状态，再把 `dumpxml` 当作当前运行配置。

### 5.2 维护方应明确的检查点和修复内容

| 检查点 | 需要的结果 | 对应修复 |
|---|---|---|
| 现场对应版本的 `devdrv_get_bar_wc_flag` | 虚拟场景 BAR4 WC 标志及返回码，明确具体失败条件 | 修复受支持的驱动/虚拟化能力发布与传递；采用支持该组合的版本 |
| Runtime 的 `copy policy`、argsSize、映射/分配返回值 | 解释能力、参数大小及回退如何决定实际路径 | 修复错误回退或参数分配路径，必要时采用匹配的 Runtime 修复 |
| 实际参数映射的 Guest VA→IPA→BAR/offset | 将真实热路径与 Stage-1/Stage-2 属性对应 | 确认哪些设备内存范围需要、且允许 Normal-NC/WC |
| 精确宿主内核构建与 KVM/VFIO 实现 | 是否包含适用的 Normal-NC 支持，厂商是否回合 | 回合经过平台验证的补丁，或升级受支持宿主内核 |

上游相关补丁包括 `c034ec84e879`、`5c656fcdd6c6`、`8c47ce3e1d2c`、`a39d3a966a09`。它们是供维护方核对的参考，不能在厂商 5.10 分支上直接认定可无冲突套用。[上游补丁记录](https://lists.infradead.org/pipermail/linux-arm-kernel/2024-February/908141.html)

负责 Stage-2 的是宿主内核。Guest 使用 6.6，并不能说明宿主 5.10 已具备相关支持。现有宿主日志的 Stage-2 和补丁状态均为 UNKNOWN；接口缺失、Prefetchable、resource_wc 节点以及 QEMU mmap 都不足以单独确认实际属性。

修复应针对受支持的设备内存范围，不能把所有 BAR 或寄存器区域统一改为 WC。维护方完成修复后，重新执行第 3、4 节的能力、路径和无探针性能对照。

## 6. 单独验证 Host 主线程专核

驱动路径实验结束后再做这一轮。保持修复后的驱动版本固定，保留原 NUMA、1GB 大页、IRQ、idle 参数、OMP_NUM_THREADS=10、CPU 池、模型和图配置。若驱动尚不能修复，也可以在原驱动状态独立进行，但不能把两轮结果混为同一个实验。

核隔离和 vCPU 绑定不能保证 Guest 内的业务主线程不与辅助线程竞争。当前工具会在原 CPU 池中为主线程选一个 CPU，保留 ACL 原有单核，并从各 worker 辅助线程的允许集合中排除所选主线程/ACL CPU。[vLLM Ascend CPU 分工参考](https://docs.vllm.ai/projects/ascend/en/v0.18.0/developer_guide/Design_Documents/cpu_binding.html)

### 6.1 先保存 A0 基线，再生成 B 计划

使用当前配置预热并跑一次原 8 并发业务，记录 A0。业务完成后保持服务进程存活，在同一 PID namespace 的业务容器执行：

```bash
python3 "$VMGAP_AFFINITY" plan --plan "$VMGAP_RESULTS/affinity_plan_B1.json"
```

结果处理：

- 正常计划：核对 PID、ACL TID、原 main 集合、拟分配的 main CPU 和 ACL CPU。
- `ALREADY_SEPARATED`：已经完成这种线程分离，跳过本轮。
- `BLOCK`：先处理提示的 worker 数量、未知 ACL、CPU 池或专核冲突，不继续 apply。

容器里有其他模型时可显式选择本服务的 8 个 worker：

```bash
VMGAP_WORKER_PIDS='<PID0,PID1,PID2,PID3,PID4,PID5,PID6,PID7>'
python3 "$VMGAP_AFFINITY" plan \
  --pids "$VMGAP_WORKER_PIDS" \
  --plan "$VMGAP_RESULTS/affinity_plan_B1_filtered.json"
```

两种 plan 方式二选一。后续 apply 的 `--plan` 必须指向实际成功生成的计划。

用第 5.1 节的 live 映射确认：main 与 ACL 对应不同 pCPU，目标核没有 worker/emulator 重叠，CPU 池与 NPU NUMA 位置匹配。计划中的 `POOL_SLOT` 是 CPU 池编号，不能在设备重排后直接当作逻辑 rank。不要根据历史示例把 Rank 6 直接绑定到固定 CPU38。

### 6.2 应用 B1 并验证

以下以非 filtered 的成功计划为例：

```bash
python3 "$VMGAP_AFFINITY" apply \
  --plan "$VMGAP_RESULTS/affinity_plan_B1.json" \
  --state "$VMGAP_RESULTS/affinity_restore_A1.json"

python3 "$VMGAP_AFFINITY" verify \
  --state "$VMGAP_RESULTS/affinity_restore_A1.json"
```

verify 成功后执行原来的 8 并发业务测试，保持与 A0 相同的预热和 prefix cache 规则，计时阶段不开 profiler。业务完成后再次执行：

```bash
python3 "$VMGAP_AFFINITY" verify \
  --state "$VMGAP_RESULTS/affinity_restore_A1.json"
```

两次 verify 都成功才计为有效 B1。出现新线程、进程重启或 affinity 被框架覆盖时，将该轮标记无效。

### 6.3 回退并复测 A1

```bash
python3 "$VMGAP_AFFINITY" restore \
  --state "$VMGAP_RESULTS/affinity_restore_A1.json"
```

显示 `RESTORED` 后重跑原 8 并发业务，记录 A1。再做 B2/A2 时重新生成计划，使用新的 plan/state 文件名。旧 PID/TID 对应的状态不能用于新进程；若进程或线程集合已经变化，按原服务启动配置重启恢复。

原业务压测命令未保存在这些工具中，因此使用现场已经用于 Excel 的同一命令，不另造压测参数。

## 7. 专核无收益时按同窗口证据继续处理

先确认当前配置确实仍有慢 Rank，再定位其拖后区间。历史的 Launch 间隔包含任务准备、计算、锁、等待和调度等成本，不能直接当作被抢占时间。

| 同窗口现象 | 下一步修复方向 |
|---|---|
| 线程处于 runnable，但长期拿不到 CPU | 处理宿主 pCPU 争用、vCPU 超分、IRQ 干扰，以及 vCPU/容器/祖先 cgroup 限流 |
| 线程持续运行，耗时集中于输入准备、tiling、workspace | 优化对应 Host 工作、消除重复准备，采用已验证的框架/Runtime 修复 |
| 时间集中在锁、队列或资源等待 | 修复对应串行点、资源回收或队列反压 |
| 同形状设备 kernel 也同步变慢 | 再检查设备状态、频率、内存访问与实际通信传输，避免把所有问题都归给 Host |

可先在 Guest 容器中对实际主线程和 ACL TID 保存基础信息，TID 从成功计划或当前进程中读取：

```bash
VMGAP_WORKER_PID='<当前worker PID>'
VMGAP_MAIN_TID="$VMGAP_WORKER_PID"
VMGAP_ACL_TID='<当前ACL TID>'

taskset -pc "$VMGAP_MAIN_TID"
taskset -pc "$VMGAP_ACL_TID"
cat "/proc/$VMGAP_WORKER_PID/cgroup"
cat "/proc/$VMGAP_WORKER_PID/task/$VMGAP_MAIN_TID/schedstat" \
  > "$VMGAP_RESULTS/main_schedstat_before.txt"
cat "/proc/$VMGAP_WORKER_PID/task/$VMGAP_ACL_TID/schedstat" \
  > "$VMGAP_RESULTS/acl_schedstat_before.txt"
```

同一业务窗口结束后保存增量终点：

```bash
cat "/proc/$VMGAP_WORKER_PID/task/$VMGAP_MAIN_TID/schedstat" \
  > "$VMGAP_RESULTS/main_schedstat_after.txt"
cat "/proc/$VMGAP_WORKER_PID/task/$VMGAP_ACL_TID/schedstat" \
  > "$VMGAP_RESULTS/acl_schedstat_after.txt"
```

这些只是基础计数；schedstat 受内核统计配置影响，Guest 统计也不足以排除宿主 vCPU 停顿。需要与同窗口宿主调度证据对应，不能仅凭零计数排除争用。全程累计 IRQ 或只看 emulator 子组的 quota 同样不能替代目标线程及祖先 cgroup 的窗口证据。

## 9. 给维护方的最小问题描述
