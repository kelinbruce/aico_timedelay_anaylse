# 宿主机 BAR / WC 核验命令

适用于 Linux ARM64 KVM/VFIO 宿主机。脚本依赖 Python 3.6+、virsh；lspci、modinfo、Git 可选，自动导出页表需要 timeout。默认虚机名根据已有配置设为 `instance-00000b34`，运行时仍读取 live XML，不使用历史 candidate XML。

## 快速执行方式

本地保存目录：

```text
/Users/zhangfan/project/aico_timedelay_report/xuji_luoji_test/env_conf/1029/PCIe BAR_uc_wc/gpt
```

将整个 `gpt` 目录复制到 Linux 宿主机，例如保存为 `/tmp/host_bar_wc_gpt`。下面的采集命令在该 Linux 宿主机上执行；本地 macOS 路径仅用于保存、传输文件。

```bash
cd /tmp/host_bar_wc_gpt

# 核对虚机名称
sudo virsh --connect qemu:///system list --all

# 基础采集，自动创建唯一结果目录
sudo bash ./run.sh --vm instance-00000b34

# 业务预热后、性能计时窗口之外，增加 Stage-2 页表采集
sudo bash ./run.sh --vm instance-00000b34 --dump-stage2
```

`run.sh` 自动定位同目录的 Python 脚本，也可以直接运行：

```bash
sudo python3 ./check_host_bar_wc.py --vm instance-00000b34 --dump-stage2
```

终端会打印 `OUTPUT_DIR=/tmp/host_bar_wc_...`。将以下命令中的示例目录替换为实际输出目录后查看和打包：

```bash
sudo cat /tmp/host_bar_wc_实际输出目录/report.txt
sudo tar -C /tmp -czf /tmp/host_bar_wc_result.tar.gz host_bar_wc_实际输出目录
```

需要指定结果目录时使用 `--out /tmp/bar_wc_before`，该目录必须尚不存在。查看全部参数：

```bash
bash ./run.sh --help
```

## 1. 在宿主机执行

把 `check_host_bar_wc.py` 放在宿主机当前目录。先确认实际虚机名：

```bash
sudo virsh --connect qemu:///system list --all
```

基础采集，含内核、设备绑定、QEMU Guest BAR 地址和页表接口路径：

```bash
sudo python3 ./check_host_bar_wc.py --vm instance-00000b34
```

业务预热后、性能计时窗口之外，采集实际 Stage-2 页表：

```bash
sudo python3 ./check_host_bar_wc.py \
  --vm instance-00000b34 \
  --dump-stage2 \
  --out /tmp/bar_wc_before
```

`--out` 必须是新目录，防止覆盖之前的结果。不指定时自动在 `/tmp` 创建唯一目录，终端打印 `OUTPUT_DIR=...`。脚本只写结果目录，不挂载 debugfs、不装软件、不改内核或设备绑定、不重启 VM、不读写 PCI BAR 数据。

如果宿主机已装有与运行内核对应的完整源码，可一起采集补丁线索。将以下路径替换为实际源码目录：

```bash
sudo python3 ./check_host_bar_wc.py \
  --vm instance-00000b34 \
  --kernel-src /path/to/running-kernel-source \
  --dump-stage2 \
  --out /tmp/bar_wc_before_with_source
```

仅有 `kernel-devel`、`linux-headers` 通常不足以判断完整修复。源码版本、Git 提交与运行内核二进制仍须核对；厂商 backport 后原始 commit SHA 不一定存在。

## 2. 直接粘贴的核心只读命令

这些命令不会直接操作 BAR 的内容。`info pci` 用于查看 Guest BAR 地址，宿主 `lspci` 的 BAR 地址不能代替它。

```bash
VM_NAME=instance-00000b34
uname -a
sudo virsh --connect qemu:///system domstate "$VM_NAME"
sudo virsh --connect qemu:///system qemu-monitor-command "$VM_NAME" --hmp 'info pci'
sudo virsh --connect qemu:///system qemu-monitor-command "$VM_NAME" --hmp 'info mtree'
sudo virsh --connect qemu:///system qemu-monitor-command "$VM_NAME" '{"execute":"query-pci"}'
```

`report.txt` / `qemu-pid.txt` 确认目标 QEMU PID 后，可单独查目标 VM 的接口（把 12345 换成实际 PID）：

```bash
QEMU_PID=12345
sudo find /sys/kernel/debug/kvm -maxdepth 2 \
  -path "/sys/kernel/debug/kvm/${QEMU_PID}-*/stage2_page_tables" -print
```

对找到的**目标 VM**路径读取一次（把整条路径替换成实际结果）：

```bash
sudo timeout -k 2s 30s cat /sys/kernel/debug/kvm/12345-10/stage2_page_tables \
  > ./target_vm_stage2.txt
```

此接口依赖内核实现及 `CONFIG_PTDUMP_STAGE2_DEBUGFS`。不存在、权限不足或超时，均不能据此判定没有 WC 修复。`/sys/kernel/debug/kernel_page_tables` 是宿主页表，不能代替目标 VM 的 Stage-2 页表。脚本会根据已挂载的 debugfs 自动发现路径，比手写默认路径兼容性更好。

## 3. 查看并打包

以下使用上面的显式输出目录：

```bash
sudo cat /tmp/bar_wc_before/report.txt
sudo cat /tmp/bar_wc_before/host-pci-bars.txt
sudo cat /tmp/bar_wc_before/guest-bar-ipa.json
sudo find /tmp/bar_wc_before -maxdepth 1 -name 'stage2-bar-matches-*.txt' \
  -exec cat {} \;
sudo tar -C /tmp -czf /tmp/bar_wc_before.tar.gz bar_wc_before
```

主要证据：

| 文件 | 回答的问题 |
|---|---|
| `kernel.txt`、`kernel-config.txt` | 运行内核是什么，有无页表导出支持 |
| `kernel-source-evidence.txt`（如可用） | 是否存在配套代码及上游提交祖先线索 |
| `live-pci-devices.json`、`host-pci-bars.txt` | 哪些物理 PCI 设备直通给目标域、实际驱动与 BAR 信息 |
| `guest-bar-ipa.json` | 通过 live XML alias 和 QMP qdev_id 对应的 Guest BAR IPA |
| `stage2-*.txt`（如可用） | 目标 VM 实际 Stage-2 导出，保留原始属性 |
| `stage2-bar-matches-*.txt`（如可用） | Guest BAR IPA 与 Stage-2 范围的交集 |

Stage-2 中必须看**已实际映射的参数 BAR 子范围**。没有触发访问的范围可能尚未建页表；不能把空洞当成 Device 或 Normal-NC。脚本保留原始属性，不根据地址出现就判断映射有效，也不把 prefetch 标志当成 WC 证明。

## 4. 结果如何判断

- 参数 BAR 对应有效范围为 `Device-nGnRE`：支持“Stage-2 限制写合并”的候选解释；仍须确认 Guest Stage-1、Runtime 地址和耗时。
- 参数 BAR 对应有效范围为 `Normal-NC`：该范围不符合“Stage-2 为 Device”的具体假设；检查 Guest Stage-1、实际复制策略和屏障等。
- 页表接口缺失、匹配失败或只有头文件：状态是 UNKNOWN，需要厂商提供与运行内核匹配的页表导出/诊断支持。
- BAR 标记 prefetch、设备绑定 vfio-pci、QEMU maps 出现 VFIO：各自只是路径线索，不能单独证明有效 WC。

不要把整个 BAR 或 Doorbell 统一修改为 WC。核验对象是驱动允许采用 Normal-NC 的参数/队列内存子范围，控制寄存器应保留驱动要求的属性。

## 5. 后续分段计时与 A/B

HostArgs `copy policy`、`argsSize`、BAR-copy、DMA 完成等待和 `halSqTaskSend` 都属于虚机内 Runtime/驱动执行路径。仅在宿主运行通用 perf/bpftrace，不能直接获得这些内部函数的时间；必须先确认虚机安装包 build-id、符号及已有 timestamp 支持，再在虚机采集。不能用 QEMU 进程上的同名 uprobe 替代。

宿主端 A/B：在完成受控内核切换、VM 重建并复现相同工作负载后，使用相同采集命令，换一个新结果目录：

```bash
sudo python3 ./check_host_bar_wc.py \
  --vm instance-00000b34 \
  --dump-stage2 \
  --out /tmp/bar_wc_after
sudo diff -u /tmp/bar_wc_before/kernel.txt /tmp/bar_wc_after/kernel.txt
sudo diff -u /tmp/bar_wc_before/guest-bar-ipa.json /tmp/bar_wc_after/guest-bar-ipa.json
```

PID、Guest BAR 地址都可能在 VM 重建后改变，所以重新对应参数 BAR/offset 再比较属性，不能按文件名/PID或绝对地址硬配。性能采样应在页表快照采集之外进行，并保持输入、参数大小、核放置、日志和 profiler 配置一致。此包只提供核验命令，不替现场选择补丁或执行内核切换。
