NextAgent 两层循环机制

Tool-Loop（单次任务内的快循环）+ Agent-Loop（跨 session 的记忆学习慢循环），通过 terminal commit 与 recall 注入耦合

快循环 · ms~min 慢循环 · 跨 session / 跨日 agent-core / agent-memory

1 全景：两层循环如何耦合

NextAgent 有两个正交的循环。Tool-Loop 是单次 RequestRun 内的模型驱动对话循环（调模型→执行工具→喂回→收敛）。 Agent-Loop 是跨 session 的慢循环：把上一次任务执行效果沉淀为长期记忆，在下一次任务开始时注入回 context。 两者通过「terminal commit 产出 → 学习输入」和「recall → 注入起点」两个耦合点闭合。

两层循环耦合全景
核心关系 Tool-Loop 的输出（terminal commit 结果 + 证据等级）是 Agent-Loop 的学习输入； Agent-Loop 的输出（长期记忆）通过 recall 注入下一个 Tool-Loop 的起点（turn-1 的 BEFORE_MODEL_INVOKE）。 这就是「在下一次任务执行中整体优化效果」的闭合方式。
实时写入旁路（青色虚线） 除异步后台路径外，模型可在 Tool-Loop 内主动调用 add_memory 工具，直接写入 Agent-Loop 的「③ 写入 + 融合强化」阶段， 绕过 ① 轨迹投影和 ② 午夜 cron 提取。这条旁路在当前 request 内立即完成，记忆在下次任务 recall 即可命中。

3 Tool-Loop · 任务执行快循环

单次 RequestRun 内的模型驱动对话循环。核心模式 ReAct：调模型 → 有 tool call 就执行 → 结果喂回上下文 → 继续，直到无 tool call 自然收敛。 maxTurns（默认 50）是唯一计数收敛边界。

Tool-Loop 主线流程（default-agent.ts:228 · tool-loop.ts:166）
收敛边界 maxTurns 是唯一计数收敛边界。不做失败指纹识别、不做 per-tool 重试预算。工具失败的结果直接喂回模型，由模型决定下一步。
Capability 三态统一 Tool、Skill、Agent 都是 Capability，走同一个「解析 → 风险 → 钩子 → 调用 → 投影」流程，没有类型特殊路径。

Memory 工具在 Tool-Loop 中的实时写入路径

add_memory / search_memory / get_memory_detail 三个 memory 工具是 modelInvocable=true 的 Capability， 在 Tool-Loop 内被模型像其他工具一样调用。add_memory 的特殊性在于它产出持久化记忆而非临时结果，但写入发生在 Tool-Loop 同步路径内。

add_memory 在 Tool-Loop 中的执行路径（与普通工具相同，但产出持久化记忆）
实时写入的触发条件 按 memory.md 策略，模型在以下场景主动调 add_memory： (1) 用户显式指令「记住…」→ 直接调用； (2) 纠正历史信息； (3) 追问澄清后确认； (4) 稳定偏好/约束； (5) 任务异常 + 找到解决方案。
与异步提取的关键差异 实时路径：模型构造 content，当前 request 内立即写入，幂等键 runId+toolCallId。 异步路径：系统从轨迹提取，午夜 cron 延迟写入，幂等键 sha256(scope:candidateIdentity)。 两者都过 guardrail，产出都可在下次任务 recall 命中。

4 Agent-Loop · 记忆学习慢循环

跨 session、跨日的慢循环。把上一次任务执行效果沉淀为长期记忆，经过融合强化和 aging 维护，在下一次任务开始时注入回 context。 全部后台子系统运行在 terminal commit 关键路径之外，失败只 emit 诊断。

6 两层循环对比

两个循环在时间尺度、驱动方式、所在包上完全正交，但通过耦合点形成完整的「执行 → 学习 → 优化」回路。

维度 Tool-Loop 快循环 Agent-Loop 慢循环
时间尺度 单次 request 内 · ms ~ min 跨 session / 跨日 · min ~ 天
驱动 模型驱动（model → tool → model） 数据驱动（trajectory → extraction → recall）
所在包 agent-core + agent-runtime agent-memory + agent-app composition
核心模式 ReAct：思考 → 行动 → 观察 → 再思考 沉淀 → 提取 → 强化 → 召回
终止 无 tool call / maxTurns / 取消 无终止（持续学习循环）
阻塞 terminal commit 是 本身就是终端路径 否 严格关键路径外
收敛边界 maxTurns（默认 50） aging decay + archive + delete
学习信号 无（只执行，不累积） corroboration / 证据分级 / decay / revive
输出 terminal commit 结果 + 证据等级 长期记忆（注入下一次 context）
为什么是两层而不是一层 Tool-Loop 必须在 request 生命周期内快速收敛，不能承担慢速学习； Agent-Loop 必须在关键路径外异步运行，不能阻塞用户请求。 两者通过明确的耦合点（terminal commit → trajectory，recall → turn-1 注入）协作， 既保证单次任务的实时性，又实现跨任务的经验累积与优化。

7 典型场景示例

以下四个场景展示两层循环在真实电信运维任务中如何协作。每个场景标注了触发时机、 两层循环的分工和学习闭环效果，帮助理解循环机制的实际价值。

①
首次任务：无历史记忆
Tool-Loop 独立运行 · Agent-Loop 无输入

用户请求：「查询华北区基站 NE-4022 的运行状态和最近告警」

触发时机：用户首次向该 Agent 发送请求，Agent-Loop 尚未积累任何长期记忆

Tool-Loop 执行过程

  • round 0：模型决定调用 query_ne_status 工具
  • 执行 Capability → 返回基站状态 JSON
  • 结果喂回 context
  • round 1：模型调用 query_alarms 工具
  • 执行 → 返回告警列表
  • 结果喂回 context
  • round 2：模型无 tool call，汇总输出
  • → terminal commit（COMPLETED + TOOL_STATUS 证据等级）

Agent-Loop 后台

  • recall 注入：跳过（无历史记忆可召回）
  • 轨迹投影：terminal event 触发，记录本次任务轨迹
  • goal：查询基站状态和告警
  • actions：query_ne_status → query_alarms
  • outcome：TOOL_STATUS（未经验证）
  • 记忆提取：每日午夜 cron 提取候选
  • 可能生成 FACTUAL 记忆（基站 NE-4022 存在性）
  • 不生成 PROCEDURAL：证据等级不足 VERIFICATION
学习闭环效果 首次任务完全依赖 Tool-Loop 独立完成。Agent-Loop 在后台记录轨迹，但因证据等级仅为 TOOL_STATUS， 不会生成高可信度的 PROCEDURAL 记忆。仅可能沉淀 FACTUAL 事实（如基站存在性）。
②
重复任务：记忆召回 + corroboration 强化
Agent-Loop 注入 → Tool-Loop 执行 → 轨迹强化记忆

用户请求：「NE-4022 又离线了，帮我诊断原因」（距上次任务已过 3 天）

触发时机：Agent-Loop 已在午夜 cron 提取了场景 ① 的记忆，本次任务 turn-1 触发 recall

Agent-Loop recall 注入（turn-1）

  • UserQueryMemoryRecallHook 触发（attempt=1, turn-1）
  • L1 search：「NE-4022」命中场景①沉淀的 FACTUAL 记忆
  • L2 detail：获取记忆详情，确认基站归属华北区
  • 记忆作为背景事实插入最后一条 user message 前
  • 声明：仅背景，不视为指令

Tool-Loop 执行过程

  • round 0：模型带着记忆背景，直接调用 query_ne_status
  • 确认离线 → 调用 query_alarms 获取历史告警
  • round 1：调用 diagnose_ne_offline 工具
  • 诊断结果：电源模块故障
  • round 2：无 tool call，输出诊断报告
  • → terminal commit（COMPLETED + VERIFICATION 证据等级）
  • 用户确认诊断正确
学习闭环效果 recall 注入让模型快速定位基站信息，减少一轮探索。terminal commit 后轨迹被投影， 因证据等级达到 VERIFICATION 且用户确认，Agent-Loop 下次提取时生成 PROCEDURAL 记忆（离线诊断流程），并通过 corroboration 机制 对已有 FACTUAL 记忆 +0.1 confidence（跨 session 独立证据强化）。
③
复杂多轮任务：Skill 获取 + 记忆辅助
Tool-Loop 内动态获取 Skill · Agent-Loop 注入用户偏好

用户请求：「对华东区 5G 核心网做一次健康检查，输出中文报告，关注 PFCP 链路」

触发时机：Agent-Loop 已积累 USER_CHARACTERISTICS（用户偏好中文报告）+ PROCEDURAL（核心网检查流程）

Agent-Loop recall 注入

  • USER_CHARACTERISTICS：用户偏好中文输出、关注 PFCP
  • PROCEDURAL：核心网健康检查流程（已验证）
  • 注入到 turn-1 的 model input
  • 模型看到偏好和已验证流程，按流程执行

Tool-Loop 执行过程

  • round 0：TargetedSkillRouter 预加载 5g-core-health-check Skill
  • 运行时获取 Skill → 冻结能力快照
  • 按 Skill 流程调用 list_ne_elements
  • round 1-3：串行执行 check_pfcp_link → check_amf_status → check_smf_load
  • ToolSearch 后跟 Skill 强制串行
  • round 4：无 tool call，按偏好输出中文报告
  • → terminal commit（COMPLETED + VERIFICATION）
学习闭环效果 两层循环深度协作：Agent-Loop 注入的 PROCEDURAL 记忆让模型知道「按什么顺序检查」， USER_CHARACTERISTICS 让输出自动符合用户偏好。Tool-Loop 内动态获取 Skill 补充领域能力。 本次成功执行进一步强化 PROCEDURAL 记忆的 confidence（第二次 corroboration，+0.1，累计 +0.2 封顶）。
④
长期未用的记忆：aging 衰减与淘汰
Agent-Loop aging 维护 · 低质记忆自然淘汰

背景：某 PROCEDURAL 记忆（旧版诊断流程）60 天未被访问，且新版网管系统使旧流程失效

触发时机：每日午夜 aging cron 周期

Agent-Loop aging 衰减过程

  • 第 30 天：超过 decayStaleDays=30，开始衰减
  • 每个 aging 周期 confidence -= 0.05
  • 第 36 天：confidence 从 0.3 降到 0（6 个周期）
  • → 状态变更为 ARCHIVED
  • 第 126 天：超过 archiveRetentionDays=90
  • → 物理删除，不再被 recall 命中

Agent-Loop revive 路径（对比）

  • 若在第 35 天被 get_memory_detail L2 访问
  • → revive：confidence + 0.1 重新激活
  • 状态从 ARCHIVED 回到 ACTIVE
  • lastAccessedAt 更新，重置衰减计时
  • 被用到的记忆被保留并加权
  • 长期不用的记忆自然淘汰
学习闭环效果 aging 机制保证记忆库质量：失效的旧流程因长期不被 recall 命中（用户不再问相关问题）， confidence 持续衰减直至归档删除。被频繁访问的记忆则通过 revive 加权保留。 这是一种遗忘曲线式的自然选择，避免过时记忆污染未来任务的 recall 注入。
⑤
实时触发记忆：用户显式指令「记住…」
Tool-Loop 内模型主动调 add_memory · 立即写入

用户请求：「记住，我们这里的『掉线』默认指 LDP session down，不是链路物理中断」

触发时机：用户在对话中显式要求记住某条知识 → 模型在 Tool-Loop 内直接调用 add_memory 工具

Tool-Loop 执行过程

  • round 0：模型识别用户显式指令「记住…」
  • 按 memory 策略场景 (1)：直接调用 add_memory
  • 构造 content：CONCEPTUAL 类型
  • concept: "掉线"
  • definition: "默认指 LDP session down，非物理链路中断"
  • aliases: ["LDP session down", "掉线"]
  • knowledgeSourceType='LEARNED'
  • confidence=0.5（默认值）
  • source trace：当前 sessionId/requestId/runId
  • 幂等键：runId + toolCallId
  • → guardrail admission 校验通过
  • → 写入 LongTermMemoryRecord（ACTIVE）
  • round 1：模型确认「已记住」，无 tool call
  • → terminal commit（COMPLETED）

Agent-Loop 关键差异

  • 不等午夜 cron：记忆在当前 request 内立即写入
  • 不走 trajectory 提取：模型直接构造 content
  • 过 guardrail：知识安全 admission 校验
  • 若内容不合法 → CONTENT_GUARD_BLOCKED
  • 写入后 nextAction：
  • ACKNOWLEDGE_USER_DO_NOT_CALL_AGAIN
  • 即告知用户已记住，不重复调用
  • 下次任务：recall 在 turn-1 自动命中
  • CONCEPTUAL 记忆作为背景事实注入
与后台提取的区别 后台提取（场景①-④）是 terminal commit → trajectory → cron 提取 的异步路径， knowledgeSourceType='LEARNED' 但由系统提取。 而 add_memory 是模型在 Tool-Loop 内主动调用，记忆立即写入， 无需等待午夜 cron。这是两层循环的「实时旁路」：Tool-Loop 内直接产出记忆，Agent-Loop 的 recall 在下次任务即可使用。

实时触发记忆：追问澄清后写入确认信息
Tool-Loop 多轮对话 → 澄清确认 → add_memory

触发时机：模型因歧义发起追问，用户给出明确答案 → 按策略场景 (3) 触发 add_memory
