# NextAgent 用户配置和使用指导

本文面向使用 NextAgent 搭建、配置和调用电信网络智能体的系统管理员、集成方和业务配置人员。它不覆盖 Tool / Skill 的代码开发细节，而是说明如何根据 NextAgent 的能力特性完成用户侧配置、能力启用、任务提交和日常验证。

## 适用场景

NextAgent 适合把大模型、网络知识、受控工具、人员确认、执行审计和平台集成放到同一条可治理的网络智能体主路径中。典型用途包括：

- 网络故障诊断、告警根因分析、链路 flap 排查、KPI 异常分析。
- 巡检报告解读、配置核查、知识问答和运维报告生成。
- 通过 Web channel 面向人工交互，或通过 Task channel 接入网管、告警平台、编排系统。
- 通过 Tool、Skill、Agent 和 Workflow 组合沉淀领域能力。

## 配置层次

NextAgent 的配置分三层，用户配置时要避免跨层覆盖：

| 层次 | 配置对象 | 作用 |
| --- | --- | --- |
| App composition config | `application.yaml` 覆盖内置 `default-system.yaml` | 部署模式、路径、认证、通道、模型、RAG、sandbox、gateway、capability provider |
| Agent package config | `agent.yaml` + `prompts/` + `skills/` | 当前 Agent 的模型授权、能力绑定、运行参数、提示模板和 Agent-owned Skill |
| Runtime / request input | Web / Task API 请求 | 输入文本、附件、路由约束、模型参数、幂等键 |

内置 `packages/agent-app/config/default-system.yaml` 是框架默认配置来源，不建议作为交付环境的直接编辑文件。用户侧应准备自己的 `application.yaml`，让它覆盖默认配置。`application.yaml` 所在目录会成为 `configRoot`，该目录下可放置 `skills/` 和 `agents/`。

## 最小系统配置

用户侧最小 `application.yaml` 应至少明确运行目录、模型 provider 和活跃 Agent。示例：

```yaml
paths:
  workspaceRoot: workspaces
channel:
  transport: fastify
  host: 127.0.0.1
  port: 3000
hostedAgent:
  activeAgentId: default-agent
modelProfiles:
  - providerId: openai-compatible
    baseUrl: https://your-model-endpoint.example/v1
    credentialRef: env:YOUR_MODEL_API_KEY
    models:
      - modelId: MiniMax-M2.7-highspeed
        timeoutMs: 300000
        temperature: 0.2
        maxOutputTokens: 2048
        topP: 1
        contextWindowTokens: 128000
        fallbackEligible: false
```

关键规则：

- `credentialRef` 使用 `env:VAR` 或 `file:path` 引用，不要写明文密钥。
- 默认 `default-system.yaml` 不再预置 `baseUrl` 和 `credentialRef`；未配置模型接入参数时，服务仍会启动并进入 `DEGRADED_READY`，模型目录会提示模型不可用。
- `OPENAI_MODEL_NAME` 仍作为可选模型名覆盖保留；provider 未配置且该变量缺失时，系统使用安全占位模型名并进入 `DEGRADED_READY`。`baseUrl` 和 `credentialRef` 建议通过部署 overlay 使用部署方自有环境变量名或 `file:` 引用注入。
- `modelProfiles[].providerId` 标识 provider registration；子项 `models[].modelId` 是全局唯一 canonical 模型标识。
- Agent 可用 `modelIds` 显式收窄系统模型清单；省略时继承系统全部已校验模型。可选的顶层 `defaultModelId` 必须属于解析后的 `modelIds`。
- `paths.workspaceRoot` 是用户侧主要运行目录入口；SQLite、执行 workspace、Skill projection 等运行目录由 app composition 派生。
- app 配置是启动期校验并冻结的，运行中修改配置不会影响当前进程，需重启后生效。

## 工具执行结果显示策略

集成方可以在自己的 `application.yaml` 中配置普通 Agent Web 对 Capability 执行结果的显示级别。该配置属于 App composition config，对同一应用实例中的 local、immersive、collaborative 三种 Web 宿主统一生效；它不是 `agent.yaml`、Skill 或请求级参数。

```yaml
nextAgent:
  system:
    capability-result-presentation:
      default-level: SUMMARY
      rules:
        - capability-id: Bash
          level: STATUS_ONLY
        - capability-id: Read
          level: DETAIL
        - capability-id: VendorNetworkProbe
          level: DETAIL
```

| 级别 | 用户可见效果 |
| --- | --- |
| `STATUS_ONLY` | 显示 Capability 公开身份和执行状态，不显示成功结果摘要或详情。 |
| `SUMMARY` | 在状态基础上显示平台生成的本地化安全摘要，不显示结果正文或 `safeResult`。 |
| `DETAIL` | 在摘要基础上允许显示经过 schema 校验、字段白名单、脱敏和容量限制的安全详情；不表示原始输入、原始输出或任意 JSON。 |

未配置时，平台采用以下内置基线：

- `Skill`、`Agent`、`ApiCall`、`search_memory`、`get_memory_detail`、`add_memory`、`acquire_skill`：`STATUS_ONLY`。
- `AskUserQuestion`、`TodoWrite`、`Cron`、`Rag`、`Bash`、`Python`：`DETAIL`。
- `Read`、`Write`、`Edit`、`Glob`、`Grep`、`ToolSearch`、`Workflow`：`SUMMARY`。

配置规则：

- `default-level` 缺失时为 `SUMMARY`，主要应用于没有精确规则的扩展 Tool；内置 Capability 继续使用各自的基线，除非在 `rules` 中显式覆盖。
- `rules[].capability-id` 按大小写敏感的最终 Tool `capabilityId` 精确匹配。同一个 `Read` 无论由模型直接调用、Skill 激活还是 ToolSearch 激活，都只配置 `Read`，不按 Skill 名称或调用来源重复配置。
- 合法级别只有 `STATUS_ONLY`、`SUMMARY`、`DETAIL`。`rules` 最多 256 项；每个 `capability-id` 长度为 1 至 128 个 Unicode code point，且不得重复。未知字段、空标识、重复规则或非法级别会阻止应用进入 ready 状态。
- 配置表达产品期望级别，不授予更高的数据披露权限。系统始终先计算平台安全上限；没有平台安全 projector、结果 schema 不受支持或来源无法证明安全的扩展 Tool，即使配置为 `SUMMARY` 或 `DETAIL`，也会降级为 `STATUS_ONLY`。
- `search_memory`、`get_memory_detail`、`add_memory`、`acquire_skill` 当前没有平台安全 projector。集成规则可将其请求级别改为 `SUMMARY` 或 `DETAIL`，但普通 Web 界面的有效级别仍为 `STATUS_ONLY`，只显示业务身份和执行状态，不显示记忆正文、记忆标识、检索分数、SkillHub provider 信息或其他成功结果字段。
- AskUserQuestion 已被接受的用户答案属于有界公开对话事实，不会被普通结果显示级别隐藏。三种级别只控制其余附属结果字段。
- 三种级别只控制成功结果披露。Capability 失败始终显示同一条事实性安全原因；`DETAIL` 不会放宽失败技术详情或暴露原始诊断数据。
- 策略在应用启动时校验并冻结，不支持运行期管理界面、热更新、按用户配置或按 Agent 配置。修改 `application.yaml` 后必须重启服务。

## Agent 配置

Agent 决定当前智能体能用哪些模型、哪些能力、采用什么默认语言和运行参数。开发者 Agent 位于自己的配置根目录：

```text
<configRoot>/agents/{agentId}/agent.yaml
```

`agent.yaml` 使用 YAML；JSON 也是 YAML 的兼容子集。一个最小 Agent 示例：

```yaml
agentId: network-diagnostic-agent
agentVersion: v1
displayName: 网络诊断智能体
description: 用于网络故障诊断、配置审查和报告生成的智能体
modelIds:
  - MiniMax-M2.7-highspeed
defaultModelId: MiniMax-M2.7-highspeed
capabilityBindings:
  - capabilityId: network-explorer
    capabilityType: AGENT
    providerId: builtin-agents
    enabled: true
  - capabilityId: search_memory
    capabilityType: TOOL
    providerId: memory-tools
    enabled: true
runtimeSettings:
  defaultLanguage: zh-CN
  maxToolIterations: 30
  requestTimeoutMs: 1800000
resources: []
```

能力绑定的判断顺序是：被 provider 发现，不等于当前 Agent 可调用；必须在 `capabilityBindings` 中绑定，并且 `enabled=true`，才会进入当前 Agent scope 的可用能力集合。

## 已有项目升级

迁移脚本不在 runtime 运行包中。若项目仍使用旧版模型相关字段，应从目标 NextAgent release/tag 的源码复制 `migration/model-authoring-v2/migrate.py` 到任意本地工具目录；无需把脚本复制到 Agent 项目。采用目标 runtime 前，以 `--root` 指向开发者自己的配置根目录执行离线迁移。默认命令只预览计划，不写文件：

```bash
python /path/to/nextagent-tools/migrate.py --root /path/to/agent-project
```

确认 system config、Agent、Prompt Template 与 Skill 使用同一 canonical `modelId` 映射后，再加 `--write`。工具会在项目根目录的 `.nextagent-migration/model-authoring-v2/` 创建备份与 journal，也支持显式恢复和自定义目录布局；该本地恢复目录可能包含原始开发者源码，必须加入项目 `.gitignore`，不得进入提交或发布包。详见[模型资产迁移工具说明](../migration/model-authoring-v2/README.md)。runtime 只接受目标格式，不会自动迁移或兼容旧字段。

## 能力类型和启用方式

NextAgent 的能力统一进入 Capability Catalog，但用户使用时可按三类理解：

| 类型 | 适合场景 | 用户配置入口 |
| --- | --- | --- |
| Tool | 单一动作，如文件读取、检索、命令执行、RAG、提问 | `agent.yaml.capabilityBindings` |
| Skill | 复合领域流程或操作手册，如告警诊断、报告生成 | `configRoot/skills` 或 `configRoot/agents/{agentId}/skills` + `agent.yaml.capabilityBindings` |
| Agent | 独立上下文专家 Agent，如只读网络证据采集 | `agent.yaml.capabilityBindings` |

常见内置 Tool：

| Tool | 作用 |
| --- | --- |
| `Read` / `Glob` / `Grep` | 受控读取、枚举和搜索 workspace 文件 |
| `Write` / `Edit` | 受控写入或编辑授权目录内文本文件 |
| `Bash` / `Python` | 经 sandbox gateway 执行命令或 Python |
| `Rag` | 查询本地知识索引 |
| `ToolSearch` | 搜索并激活 deferred capability |
| `Skill` | 执行 governed Skill |
| `Agent` | 调用 governed subagent |
| `AskUserQuestion` | 触发用户补充输入 |

记忆能力由 `memory-tools` provider 提供，常见为 `search_memory`、`get_memory_detail`、`add_memory`。

## Skill 配置

系统级本地 Skill 放在：

```text
<configRoot>/skills/<skill-name>/SKILL.md
```

Agent-owned Skill 放在：

```text
<configRoot>/agents/<agentId>/skills/<skill-name>/SKILL.md
```

Skill 目录名必须与 `SKILL.md` frontmatter 中的 `name` 一致。示例：

```markdown
---
name: alarm-diagnosis
description: Diagnose telecom alarm chains and produce probable root cause.
context: inline
user-invocable: true
model-invocable: true
allowed-tools: Read Grep Rag
metadata:
  version: "1.0.0"
---

# Alarm Diagnosis

Analyze alarm correlation, affected NE/interface, KPI degradation, recent
changes, and likely root cause. Use only governed context and allowed tools.
```

注意：

- 当前可执行 Skill 使用 `context: inline`；`context: fork` 是 manifest 契约扩展，但当前版本不执行 fork Skill 路径。
- `allowed-tools` / `disallowed-tools` 是约束事实，不会授予额外权限；最终执行仍受 Agent capability binding 和 catalog governance 控制。
- Skill 若声明 `model` 或 `metadata.modelOptions`，只是下一轮模型调用的受治理 canonical `modelId` hint；目标模型仍必须在当前 Agent 的 `modelIds` 中授权。
- Skill 资源只应放在 `scripts/`、`references/`、`assets/` 子目录。

## 远程能力来源

用户可以通过 `nextAgent.system.capability-providers` 配置外部 capability source。常见类型：

| `type` | 用途 | 关键字段 |
| --- | --- | --- |
| `mcp-server` | 接入 MCP 服务 | `id`、`url` |
| `skill-hub` | 接入远程 SkillHub | `id`、`gatewayId`、`installDir` |
| `agent-registry` | 接入远程 Agent 注册中心 | `id`、`url` |
| `custom` | 接入自定义适配器 | `id`、`adapter`、`config` |

远程 source 只提供候选能力。候选能力仍需经过 catalog governance、Agent binding、request scope 校验后才能对模型可见或可执行。

## RAG 和知识检索配置

`rag.indexes` 是默认逻辑索引列表，供 `Rag` Tool 在输入未指定 indexes 时使用：

```json
{
  "rag": {
    "indexes": ["local"]
  }
}
```

规则：

- 索引名是 provider-neutral 逻辑名，不应写 endpoint、credential、SQLite 路径、workspace 路径或检索参数。
- 默认值为 `["local"]`。
- 运行中请求、模型输出和 Tool 输入不能修改启动期冻结的默认索引列表。

## Sandbox 与文件权限

动态执行和文件操作都走受控边界：

- `Bash` / `Python` 走 sandbox gateway；默认 `sandbox.enabled=true`，保持严格校验。
- `sandbox.enabled=false` 仅表示本地受限 sandbox 进入 trusted shell mode，仍保留 sandbox gateway 所有权边界；运行时请求不能覆盖。
- 文件读写权限来自可信 Agent-scoped workspace file 配置，不来自用户输入、模型输出或 Tool 参数。
- `writeDirectories` 默认应保持最小；需要写文件时只开放必要目录。

Agent 的 `workspaceFiles` 可分别限制读取类 Tool（Read/Glob/Grep）和写入类 Tool（Write/Edit）的最终文件后缀。建议显式列出所需文本类型：

```yaml
workspaceFiles:
  readAllowedExtensions: [".txt", ".md", ".yaml", ".yml", ".json", ".log"]
  readDeniedExtensions: [".pem"]
  writeAllowedExtensions: [".txt", ".md", ".yaml", ".yml", ".json"]
  writeDeniedExtensions: [".sh", ".exe"]
```

- allowlist 和 denylist 都缺省时不限制后缀；只配置 denylist 时仅排除命中项。
- 只配置 allowlist 时仅允许命中项；显式空 allowlist 表示该类操作全部拒绝。
- 同一后缀同时出现在 allowlist 和 denylist 时，denylist 始终优先，其余后缀继续由 allowlist 控制。
- 配置项必须使用类似 `.json` 的小写单一最终后缀；目标文件名匹配大小写不敏感，`archive.tar.gz` 按 `.gz` 判断。
- 读取和写入策略互不扩权。覆盖已有文件或 Edit 仍需先通过读取策略完成 full-Read；新建文件只需满足写入策略。
- 后缀策略拒绝会作为安全 Tool 错误返回模型；Agentic loop 会继续，模型可改选允许的文件，不会因单次拒绝直接结束 request。
- Skill resource 和 tool-result 等内部产物仍可生成，但模型读回时需要显式允许 `.md`、`.txt` 等对应后缀。
- 默认 Agent 不配置这些列表，保持现有兼容行为。

## Web 使用流程

启动本地开发服务：

```bash
npm run dev:watch
```

默认地址：

- 后端：`http://127.0.0.1:3000`
- 前端：`http://127.0.0.1:5173`

curl 示例：

```bash
BASE=http://127.0.0.1:3000

curl -s -X POST "$BASE/api/v1/sessions" \
  -H "Content-Type: application/json" \
  -d '{"locale":"zh-CN"}'

curl -s -X POST "$BASE/api/v1/sessions/sess_xxx/requests" \
  -H "Content-Type: application/json" \
  -d '{"inputText":"分析小区掉话率升高原因","idempotencyKey":"idem-001","locale":"zh-CN"}'

curl -N "$BASE/api/v1/sessions/sess_xxx/stream?requestId=req_xxx"
```

请求提交、取消、重试、编辑等 command 都应携带 `idempotencyKey`，避免重复提交造成副作用。

## Task Channel 使用流程

Task Channel 面向后台系统，路径前缀为 `/api/v1/task`。适合网管系统、告警平台和编排系统直接创建任务。

创建任务示例：

```bash
curl -s -X POST "$BASE/api/v1/task" \
  -H "Content-Type: application/json" \
  -H "x-tenant-id: tenant-a" \
  -H "x-subject-id: nms-system" \
  -H "x-display-name: NMS System" \
  -d '{
    "inputText": "分析 NE-01 的 OSPF 邻居震荡原因",
    "mode": "sse",
    "idempotencyKey": "task-001",
    "locale": "zh-CN",
    "routingConstraints": {
      "targetRecipe": "ospf-diagnosis",
      "allowSubagents": true
    }
  }'
```

Task Channel 支持：

- `mode=sse`：调用方通过 SSE 或 WebSocket 读取进展。
- `mode=async`：需要配置并传入 `callbackClipTarget`。
- create / edit 支持 `multipart/form-data` 附件。
- `taskId` 对应内部 session，但 API 不暴露内部 session 概念。

## 能力路由

用户可以用两种方式指定 Skill / Workflow：

1. `routingConstraints`

```json
{
  "routingConstraints": {
    "targetSkill": "alarm-diagnosis",
    "targetRecipe": "ospf-diagnosis",
    "executionMode": "default"
  }
}
```

> `routingConstraints` 是封闭 schema，不支持 `maxToolCalls` 等未列出字段。Tool 次数控制请使用 Agent 级 `runtimeSettings.maxToolCallsPerTurn`（见 [Agent 配置参考](./developer/03-agent-configuration.md)）。

2. 输入文本 directive

```text
$skill:alarm-diagnosis 分析这批告警的根因
$workflow:ospf-diagnosis 检查 NE-01 的邻居震荡
```

选择建议：

- 不需要在 edit 时切换 Skill / Workflow：优先使用 `routingConstraints`。
- 希望 edit 后能切换目标：把 `$skill:` 或 `$workflow:` 写进 `inputText`，edit 时修改文本即可。
- 两者同时存在时，directive 是更显式的文本路由意图；具体字段约束以 Web / Task API 文档为准。
- `executionMode="model-only"` 可用于强制仅模型执行，不调用能力。

## 流式事件与结果查看

Web channel 和 Task channel 都会投影能力调用过程。常见事件：

| 事件 | 含义 |
| --- | --- |
| `REQUEST_ACCEPTED` / `TASK_ACCEPTED` | 请求已受理 |
| `LLM_THINKING_DELTA` / `THINKING_DELTA` | 模型思考增量 |
| `LLM_CONTENT_DELTA` / `CONTENT_DELTA` | 模型内容增量 |
| `CAPABILITY_STARTED` | 能力开始调用 |
| `CAPABILITY_RESULT_DELTA` | 能力结果增量 |
| `CAPABILITY_COMPLETED` | 能力调用完成 |
| `USER_INPUT_REQUIRED` | 等待用户补充输入 |
| `REQUEST_COMPLETED` / `TASK_COMPLETED` | 请求完成 |
| `REQUEST_FAILED` / `TASK_FAILED` | 请求失败 |

如果需要排查能力调用结果，可通过 conversation API 查询，并设置 `includeCapabilityResults=true`。

## 认证和身份

本地默认配置中 `auth.mode="local"` 且 `auth.localAuth.enabled=false`，开发环境可直接调用 API。启用本地认证后，先调用：

```bash
curl -s -X POST "$BASE/api/v1/auth/local/login" \
  -H "Content-Type: application/json" \
  -d '{"credential":"local-secret"}' \
  -c cookies.txt
```

后续请求使用 `-b cookies.txt` 携带 cookie。Owner Scope 来自 channel / auth 边界，不能从请求体、query 或 path 覆盖。Agent Scope 来自可信 app composition 或已持久化 session / run，也不能由客户端请求体指定。

## 日常验证

配置变更后建议至少执行：

```bash
npm run build
npm test
npm run test:contract
npm run lint:architecture
npm run lint:openspec
```

用户侧运行验证建议：

1. 启动服务并确认 `/health` 或 `/health/deep` 可用。
2. 调用 `/api/v1/runtime/bootstrap` 检查 stream transport。
3. 创建会话或 Task，提交一个不使用危险能力的只读诊断请求。
4. 观察 stream 中是否出现 `CAPABILITY_STARTED` / `CAPABILITY_COMPLETED`。
5. 通过 run-event history 检查 Capability 过程结果的安全投影；conversation 只承担用户问题、最终 Assistant Message 和既有 AskUserQuestion 兼容事实。即使显式使用 `includeCapabilityResults=true`，普通 Capability Result 的原始 `content` 也不会作为过程详情返回。

## 常见配置问题

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 启动 blocked | 无通过校验的模型、凭据引用无效、配置 ownership 越界 | 检查 `modelProfiles[].models[]`、provider `credentialRef`、`paths.workspaceRoot` 和 active branch |
| Agent 不使用某个模型 | Agent 显式 `modelIds` 未包含该 canonical model ID，或模型当前不可用 | 在 `agent.yaml.modelIds` 中授权目标模型并检查目录可用性 |
| Skill 可搜索但不能调用 | 未绑定到当前 Agent、deferred Skill 未经 `ToolSearch` 激活、manifest 被拒绝 | 检查 `capabilityBindings`、Skill name、frontmatter 和 ToolSearch 流程 |
| Tool 被标记 unavailable | 缺少 `sandbox`、`workspaceFiles`、`skillSources`、`ragRetrieval` 等依赖 | 检查 app composition 和对应 provider / gateway |
| 工具详情仍只显示状态 | 工具没有平台安全 projector、结果未通过安全 schema，或配置被平台安全上限收窄 | 检查最终 `capabilityId`、对应 `rules` 和平台是否支持该结果类型；不能通过配置开放原始结果 |
| 修改工具显示策略后没有变化 | 配置只在启动期读取并冻结，或规则的 `capability-id` 大小写不匹配 | 确认修改的是当前进程使用的 `application.yaml`，使用最终 Tool ID，并重启服务 |
| edit / retry 后路由没有变化 | 初次提交使用了固定 `routingConstraints` | 需要切换时把 `$skill:` / `$workflow:` 写入输入文本并通过 edit 修改 |
| RAG 没查到预期索引 | `rag.indexes` 只是默认逻辑索引，未配置实际知识来源或请求指定了其他 indexes | 检查 RAG provider / gateway 和请求输入 |
