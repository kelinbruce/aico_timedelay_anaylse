02 / LOCALITY

把线程、内存与 NPU 放在同一侧

重配 Guest NUMA 只是第一步。CPU binding patch 再把每张卡的线程池映射到正确 vCPU，并通过 vcpupin 对齐宿主物理核。

144 vCPU 配置映射

Guest vCPU→Host pCPU↔本地内存 / 本地 NPU

每 NUMA cell：36 vCPU / 120 GiB；每 NPU：18 vCPU。图中 NPU 分组依据项目启动脚本与 XML 联合推导，需与现场 PCIe 拓扑核对。

WHAT CHANGED
  • 明确物理映射按设备拓扑定义 CPU 池，避免 Guest 的 NPU 编号与 NUMA 编号被误认为天然对应。
  • CPU 和内存一起对齐XML 为每个 cell 指定 strict memnode；已有内存页另做 NUMA 迁移。
  • 绑定失败可发现patch 检查 CPU 池重叠、跨 NUMA、允许 CPU 范围，并记录迁移失败。
CPU 亲和性需要穿过两层映射

应用线程 → Guest vCPU → Host pCPU。只固定 Guest CPU，不能保证对应的物理 NUMA 节点正确。

机制：减少远端内存访问与跨 NUMA 的 CPU–NPU 交互。
边界：migratepages 迁移现有页；后续分配仍需内存策略约束。
配置快照：10/28 XML + 144 vCPU 启动脚本；最新生效情况以 live XML、线程 affinity 和 numa_maps 为准。
03 / CPU ISOLATION

让关键线程获得更稳定的 CPU 时间

绑核决定“在哪里运行”；核隔离进一步减少同一物理核上的系统任务、中断与调度干扰。

物理核分工示意

业务 vCPU 所在核系统 / housekeeping干扰任务（示意）

项目 XML 中，每组 48 个 Host CPU 的后 36 个分配给 VM；emulator 使用保留池的一部分。IRQ 和系统任务是否迁出，需独立核验。

WHY IT HELPS

减少微小停顿被多卡同步放大

一张卡的 Host 线程晚提交，其他卡可能在集合通信中等待。隔离有助于降低调度抖动，但同一 CPU 池内部的主线程、ACL 与辅助线程仍可能互相竞争。

调度域与 CPU 池

核对 cpuset / isolcpus、实际 vcpupin、cgroup 配额与 runqueue。

Tick / RCU

nohz_full、rcu_nocbs 等按内核支持与工作负载配置。

IRQ / Emulator

核对中断、emulator 与系统线程，确保保留核足够处理后台工作。

关键线程分工

若慢 Rank 仍存在，再做主线程与 ACL / 辅助线程分离 A/B。

10 / NEXT EXPERIMENTS

先验证能力与路径，再判断业务收益

保持已经完成的 NUMA、大页与 CPU 配置，每轮只改变一类因素。现阶段的结论是修复优先级，而非预先承诺完全持平。

01 / ALIGN

对齐真实驱动栈

核对业务容器 HAL、Guest 驱动模块、固件与宿主版本，采用厂商支持的完整组合。

验收：实际加载路径、版本与哈希一致于目标配套。
02 / RESTORE

恢复 BAR-copy 能力

查询实际使用的 8 张卡，确认有效支持位；检查固定算例的 DMA 请求是否减少。

验收：能力变化与实际 copy path 变化吻合。
03 / ISOLATE

复查慢 Rank

当前最终配置下重采 8 Rank；若仍拖后，再做主线程与 ACL / 辅助线程分离 A/B。

验收：拖后消失、减小或随 CPU 映射迁移。
04 / VALIDATE

回到原业务验收

每配置先做 3–5 个独立运行，交替对照；记录逐请求 TTFT、E2E、token 与尾延迟。

验收：改善超出运行间波动，且输出正确性保持。

能力恢复实验的两个分支

能力恢复，耗时仍未改善→查实际 copy policy、argsSize、分配 / 映射回退、SQ 与等待；不只看能力掩码。
配套对齐，能力仍然为零→驱动与虚拟化团队核对 BAR4 WC 门控、Guest 映射、宿主 KVM / VFIO 和精确补丁构建。
下发改善，业务仍然较慢→继续定位剩余关键路径；评估具体 eager 阶段的融合或图覆盖，避免重复开启已有开关。
完整闭环：能力 → 路径 → 无探针性能 → 业务 E2E

既有基础优化已有总体进展。下一步优先控制驱动差异，并确认慢 Rank 在最终配置下是否仍存在。
