# 虚机与裸机性能拉齐：优化措施、实现原理与验证结果

版本：V1.0  
整理日期：2026-11-03  
适用范围：本项目 ARM64 / KVM 虚机上的 Ascend NPU 推理场景

## 1. 优化结论

在本项目相同硬件条件及对齐业务配置的测试中，通过 **NUMA 重分组与 CPU binding patch、核隔离、宿主侧 1 GiB 大页、Guest idle / VM-exit 路径优化**，虚机业务性能已达到裸机水平。

最新性能记录中，虚机平均端到端时延由初始的 **11275.850 ms 降至 7295.910 ms，下降 35.30%**；对应裸机基线为 **7987.733 ms**。最终虚机记录的首字、增量及端到端时延均不高于裸机基线，支持“当前测试场景已完成性能拉齐”的结论。最后将无效的 `idle=poll` 改为 `nohlt`，是消除剩余业务时延差距的关键步骤。[性能记录：工作表 `030`，第 40、43、68 行](/Users/zhangfan/project/aico_timedelay_report/xuji_luoji_test/test_result/虚机对比测试.xlsx)

这次优化的核心，是让 **NPU 附近的 CPU 和内存能够持续、及时地为设备提供任务**：既缩短跨 NUMA 访问路径，也降低 CPU 调度干扰和地址转换开销，最后减少 Guest 空闲进入 WFI 后带来的虚拟化停驻与唤醒成本。

“拉齐”指本项目已测业务指标达到裸机水平，不意味着所有底层 API 时延完全相同。最新 Excel 只有一条 nohlt 汇总记录，不能据此推广为虚机在所有负载下稳定优于裸机 8.66%；现有回退验证则进一步支持 nohlt 对本环境业务改善的因果作用。

## 3. 优化一：NUMA 重分组与 CPU binding patch

### 3.1 为什么只修改 NUMA 分组还不够

NPU 推理仍需要 Host CPU 完成请求调度、输入准备、算子参数组织、任务提交和完成处理。若负责某张 NPU 的线程运行在远端 NUMA，或其工作内存落在另一节点，访问就可能经过跨节点互联；线程迁移还会破坏缓存局部性。

虚机多了一层映射，必须同时对齐三组关系：

```text
NPU worker / Runtime 线程
          ↓ Guest CPU binding
Guest vCPU / Guest NUMA
          ↓ libvirt vcpupin / memnode
Host CPU / Host NUMA 内存
          ↔ 对应直通 NPU 的物理邻近节点
```

Guest 看到的逻辑 NPU 编号、PCI 地址和 NUMA 编号，不能直接当作宿主的同名编号使用。修改虚拟拓扑之后，还需要让应用实际使用正确的 CPU 池，才能把拓扑调整传导到业务线程。

### 3.2 本项目的实现

运行域配置将 144 个 vCPU 分成四组，每组 36 个，分配 120 GiB 内存；vCPU 固定到对应宿主 CPU，内存通过每 cell 的 `memnode mode='strict'` 绑定到对应宿主 NUMA。

| Guest NUMA | Guest vCPU | Host CPU | Host NUMA | 内存 |
|---|---|---|---|---:|
| 0 | 0–35 | 12–47 | 0 | 120 GiB |
| 1 | 36–71 | 60–95 | 1 | 120 GiB |
| 2 | 72–107 | 108–143 | 2 | 120 GiB |
| 3 | 108–143 | 156–191 | 3 | 120 GiB |

XML 中同时存在全局 `memory mode='interleave' nodeset='0-3'` 和四个 per-cell strict 规则。本文的本地分配结论依据 **per-cell 规则及实际 QEMU 内存后端、`numa_maps`**，不能仅看到全局 interleave 就认定每个 cell 的内存跨四节点交错。libvirt 支持用 per-cell 策略覆盖对应节点的全局默认策略。[libvirt NUMA 配置说明](https://libvirt.org/formatdomain.html#numa-node-tuning)

应用侧 patch 增加 `LOCAL_ASCEND_CPU_POOLS`，按**全局逻辑 NPU ID** 显式指定 Guest CPU 池。当前 144 vCPU 启动脚本使用：

```bash
export LOCAL_ASCEND_CPU_POOLS='{"0":"108-125","1":"126-143","2":"72-89","3":"90-107","4":"0-17","5":"18-35","6":"36-53","7":"54-71"}'
```

结合 vCPU pinning，实际映射为：

| 逻辑 NPU | Guest CPU 池 | Guest / Host NUMA | 映射后的 Host CPU |
|---|---|---:|---|
| 0 | 108–125 | 3 | 156–173 |
| 1 | 126–143 | 3 | 174–191 |
| 2 | 72–89 | 2 | 108–125 |
| 3 | 90–107 | 2 | 126–143 |
| 4 | 0–17 | 0 | 12–29 |
| 5 | 18–35 | 0 | 30–47 |
| 6 | 36–53 | 1 | 60–77 |
| 7 | 54–71 | 1 | 78–95 |

这套编号是本项目实例的配置，迁移部署时应根据实际 NPU PCI 拓扑重新映射。

patch 校验 CPU 池不重叠、不跨 Guest NUMA，且 CPU 位于允许集合内；同时检查必需的 NPU 是否都有映射。启动日志中八个 worker 均打印了 `mode=explicit_local`，可确认显式池分配被实际采用。每张 NPU 分到 18 个 vCPU，其中日志显示 2 个用于设备 IRQ，14 个用于主线程 CPU 集合，1 个用于 ACL/Runtime，1 个用于 release。以 NPU0 为例：

```text
pool    = 108–125，numa=3
IRQ     = 108、109
main    = 110–123
acl     = 124
release = 125
```

来源：[CPU binding patch](/Users/zhangfan/project/aico_timedelay_report/xuji_luoji_test/env_conf/1028/apply_cpu_binding_patch.py)、[八个 worker 的绑定与 IRQ 日志](/Users/zhangfan/project/aico_timedelay_report/xuji_luoji_test/env_conf/1028/在虚机上的va启动绑核相关日志)。patch 文件开头的 64 vCPU 示例不是当前配置，应以 144 vCPU 启动脚本及实际日志为准。

### 3.3 内存亲和性要分两层验证

宿主侧的 `memnode` 控制 Guest 某个 NUMA cell 的 RAM 落在哪个物理 NUMA；Guest 内的页分配和页迁移控制某个进程使用哪些 Guest NUMA 页。两层都匹配，才能形成完整的 CPU—内存—NPU 亲和关系。

本项目还进行了手动 NUMA 页迁移；patch 保留了 `migratepages` 路径，并增加失败日志。**迁移已有页面不等于为后续所有分配设置永久策略**，日志打印迁移目标也不等于所有页均迁移成功。因此实现效果应结合进程 `numa_maps`、`numastat` 与迁移返回状态判断。

### 3.4 结果如何体现

仅重配 NUMA 时，E2E 为 11478.326 ms；加入绑定 patch 后降至 10336.142 ms，再加入手动迁移后为 9995.584 ms。记录说明了应用绑定与内存放置需要配套完成，也说明“改了 NUMA 拓扑”本身不足以保证收益。上述是阶段结果，不是各措施的独立消融结论。

## 4. 优化二：核隔离，降低关键 CPU 的运行抖动

### 4.1 已实施配置

宿主每个 NUMA 节点划出 36 个 CPU 承载虚机 vCPU，其余 12 个用于系统维护等任务。

| 用途 | Host CPU 集合 | 数量 |
|---|---|---:|
| 虚机业务 vCPU | `12-47,60-95,108-143,156-191` | 144 |
| 系统维护及默认 IRQ | `0-11,48-59,96-107,144-155` | 48 |
| QEMU emulator 允许集合 | `0-3,48-51,96-99,144-147` | 16，属于维护 CPU 子集 |

现场宿主启动参数摘录：

```text
isolcpus=managed_irq,domain,nohz,12-47,60-95,108-143,156-191
nohz_full=12-47,60-95,108-143,156-191
rcu_nocbs=12-47,60-95,108-143,156-191
rcu_nocb_poll
skew_tick=1
irqaffinity=0-11,48-59,96-107,144-155
```

`/sys/devices/system/cpu/isolated` 与 `nohz_full` 的现场结果均为上述 144 CPU 集合，运行域的 vCPU pinning 也落在该集合中。[现场核隔离与大页查询](/Users/zhangfan/project/aico_timedelay_report/xuji_luoji_test/ppt/evidence/runtime-observations.txt)

### 4.2 生效原理

| 配置 | 作用 |
|---|---|
| `isolcpus=domain` | 从普通调度负载均衡域中隔离指定 CPU，配合显式绑定安排业务线程 |
| `nohz_full` / `isolcpus=nohz` | 满足条件时减少调度 tick，降低周期性干扰，并非关闭全部定时器与中断 |
| `rcu_nocbs` | 将指定 CPU 的 RCU 回调处理卸载到内核线程；仍需关注相关线程实际落点 |
| `irqaffinity` / `managed_irq` | 将默认 IRQ 引向维护 CPU，并尽力避开隔离 CPU；最终效果受具体 IRQ 和队列配置影响 |
| `emulatorpin` | 约束 QEMU emulator 线程，减少其与业务 vCPU 竞争 |

参数语义依据 [Linux 内核启动参数文档](https://www.kernel.org/doc/html/v6.6/admin-guide/kernel-parameters.html)。现场同时配置的 `rcu_nocb_poll` 与 `skew_tick=1` 属于辅助设置，现有记录没有拆分其独立收益。

对于 TP8 推理，一个 rank 的短暂迟到可能让其余 rank 在集合通信处等待。核隔离主要改善 Host 提交的及时性和稳定性，收益可以表现为跨 rank 等待减少，而不一定是 NPU 算子自身计算变快。

**Guest 与 Host 的 IRQ 配置承担不同职责：** Host 默认 IRQ 使用维护 CPU；Guest 中 NPU IRQ 则按 binding 逻辑放到每张卡 CPU 池预留的两个 vCPU。两者属于不同层级，不应把 Host CPU 编号直接套入 Guest。

### 4.3 阶段结果

加入核隔离的记录中，E2E 从 9736.280 ms 降到 9403.652 ms，增量指标从 31.511 ms 降到 29.722 ms。该阶段仍比裸机 E2E 高 17.73%，说明隔离改善了运行条件，但剩余 idle / 唤醒路径问题尚未消除。

## 5. 优化三：宿主侧 1 GiB 大页内存

### 5.1 大页配置在哪一层

本项目的“1 GB 大页”，准确说是 **宿主使用 1 GiB HugeTLB 页面为 QEMU Guest RAM 提供后端**。运行域配置为：

```xml
<memoryBacking>
  <hugepages>
    <page size='1048576' unit='KiB'/>
  </hugepages>
</memoryBacking>
```

现场证据包括：

| 查询项 | 实际结果 |
|---|---|
| Host Hugepagesize | 1048576 kB，即 1 GiB |
| Host HugePages_Total | 480 |
| QEMU HugetlbPages | 503316480 kB，即 480 GiB |
| QEMU 各 RAM 后端 | `prealloc=true`，每个 120 GiB，分别绑定 Host NUMA 0–3 |
| QEMU `numa_maps` | 每个节点 120 个大页，`kernelpagesize_kB=1048576` |
| Guest HugeTLB 页池 | 查询到的各页大小池均为 0；Guest 另有 AnonHugePages |

因此，大页已经在宿主 Guest RAM 后端生效；不能将其写成“Guest 应用已分配 1 GiB HugeTLB 页”。Guest 的透明大页、Guest 显式 HugeTLB 和宿主 RAM 后端大页是不同层次。[现场大页与 NUMA 映射证据](/Users/zhangfan/project/aico_timedelay_report/xuji_luoji_test/ppt/evidence/runtime-observations.txt)

### 5.2 为什么有助于虚机性能

CPU 通过 TLB 缓存地址转换结果。页面更大时，同等内存容量所需的映射项更少，通常有助于降低 TLB 压力和页表遍历成本。虚拟机还涉及 Guest 地址转换及 KVM 的 Stage-2 转换；连续、对齐的大页后端为采用更大粒度的映射提供条件，但实际 Stage-2 映射粒度仍取决于 KVM、对齐及运行状态，不能只凭 HugeTLB 统计断言所有访问均使用 1 GiB Stage-2 映射。[Linux HugeTLB 说明](https://www.kernel.org/doc/html/v6.6/admin-guide/mm/hugetlbpage.html)

本项目将大页与 NUMA 绑定同时使用：预分配减少运行时分配的不确定性，按节点绑定则避免大页集中到错误的物理节点。只扩大页尺寸而不控制节点，仍可能存在远端访问。

### 5.3 已证明与未单独量化的效果

当前记录已经证明 480 GiB Guest RAM 使用宿主 1 GiB HugeTLB，并按四节点分布。阶段测试中，加入大页后首字从 1874.629 ms 改善为 1708.883 ms，但 E2E 从 9570.004 ms 增至 9736.280 ms。

所以，大页应列为已完成的基础优化，本文不为其宣称独立、稳定的 E2E 降幅。它也不等于 NPU 参数 BAR-copy/WC 快速路径开关；两者的作用对象不同。

## 6. 优化四：通过 nohlt 改善 Guest idle 与 VM-exit 路径

### 6.1 从 idle=poll 到 nohlt

前期尝试以 `idle=poll` 规避 idle 相关退出，但项目后续确认该参数在当前 Guest 环境中未达到预期效果。11 月 2 日改用 `nohlt` 后，业务性能恢复到裸机水平；既有八卡复核报告还记录了用户完成的单因素切换与回退验证：其他条件不变时，加入 nohlt 后改善，回退原配置后差距复现。[完整八卡复核与回退验证记录](/Users/zhangfan/project/aico_timedelay_report/xuji_luoji_test/md/nohlt完整八卡profiling复核_20261102.md)

这里改变的是 **Guest 内核空闲行为**，不是一个名为 `vm_exit` 的统一开关，也不是禁止全部虚拟化退出。

### 6.2 为什么 nohlt 在本环境有效

项目已有配置核对记录指出，Guest 为 EulerOS ARM64 6.6，启用了 `CONFIG_GENERIC_IDLE_POLL_SETUP=y`，命令行包含 `nohlt`，启动日志未将其列为未知参数。[配置核对记录，第六部分](/Users/zhangfan/project/aico_timedelay_report/xuji_luoji_test/md/nohlt后虚机与裸机profiling综合对比_20261102.md)

上游 Linux 6.6 的通用 idle 实现中，`nohlt` 在上述编译条件下注册为启动参数，将 `cpu_idle_force_poll` 设为 1，使 idle 走轮询路径。而 `idle=poll` 的相关解析位于 x86 架构实现，不能把其用法直接当作 ARM64 通用保证。现场厂商内核是否生效仍应结合构建与启动记录核对。[通用 idle 实现](https://raw.githubusercontent.com/torvalds/linux/v6.6/kernel/sched/idle.c)、[x86 idle 参数实现](https://raw.githubusercontent.com/torvalds/linux/v6.6/arch/x86/kernel/process.c)

ARM64 默认 idle 路径执行 WFI（Wait For Interrupt）。当 Guest WFI 被 KVM 捕获时，会进入相应处理路径，可能伴随 vCPU 停驻以及后续的唤醒和重新运行。对于频繁提交、短任务和多线程交接，这些小成本可能反复出现在 Host 供给链路中。[ARM64 idle 实现](https://raw.githubusercontent.com/torvalds/linux/v6.6/arch/arm64/kernel/idle.c)、[KVM WFx 处理实现](https://raw.githubusercontent.com/torvalds/linux/v6.6/arch/arm64/kvm/handle_exit.c)

```text
原路径的额外等待来源：
Guest CPU 暂无可运行任务 → idle / WFI → KVM 处理与可能的 vCPU 停驻
    → 等待唤醒与重新运行 → Host 任务提交迟到 → 其他 rank 同步等待

nohlt 的作用方向：
Guest CPU 空闲时轮询 → 减少上述 idle 进入 WFI 的机会
    → 任务就绪后更及时运行 → 降低关键提交路径上的额外等待
```

这是结合配置、历史退出计数和业务回退结果形成的机制解释。nohlt 的业务效果已经有回退验证支持，但尚无前后同窗口退出计数与每次请求的逐事件关联，不能给出“减少了多少百分比 VM exit”或每个内部环节的耗时占比。

### 6.3 历史 VM-exit 采样提供了什么证据

历史采样每组约 30 秒，统计对象是目标 VM 的聚合计数：

| 状态 | 全部 exits / 秒 | WFI exits / 秒 | 内核 MMIO exits / 秒 | 用户态 MMIO exits / 秒 |
|---|---:|---:|---:|---:|
| idle | 141629.88 | 136493.76 | 104.33 | 100.46 |
| workload | 353591.15 | 214908.21 | 132.16 | 104.83 |

### 6.4 性能效果与使用代价

在已完成亲和性、大页、核隔离的基础上，改用 nohlt 后，E2E 从 9403.652 ms 降为 7295.910 ms，阶段记录下降 **22.41%**。该数值是两条汇总记录的比较；回退验证支持 nohlt 是剩余业务差距的关键配置。

轮询以更多 CPU 占用和功耗换取更短的空闲唤醒延迟。本项目有专用 CPU 池和核隔离作为配套条件。迁移到 CPU 超分或多租户环境时，应重新评估资源竞争；`nohlt` 也不会消除 MMIO、中断等其他原因的退出。

## 8. 为什么底层仍有差异，业务却能拉齐

完整八卡 profiling 显示，历史 rank 6 持续迟到并让其他 rank 等待数百毫秒的模式，在 nohlt 后的采样窗口中未重现；匹配规格的设备计算也没有呈现与 Host 下发差异同等规模的普遍退化。

同时，普通 `aclrtLaunchKernelWithHostArgs` 的同规格标准化均值仍有差距：nohlt rank 0 为 24.90 μs，裸机为 5.55 μs。但业务使用图执行，普通 Launch 与图提交入口不是同一 API；CPU 提交、设备执行和跨 rank 等待又存在重叠。因此，局部 API 的倍数不能直接换算成端到端损失。

完整八卡中，同轮主模型图的 Host 提交时刻最多相差约 48.46 ms，关联设备完成边界代理的跨 rank 差却不超过约 0.055 ms，说明各侧的等待可以落在不同阶段。当前 profiling 仍存在局部长尾，但它们与业务平均时延拉齐并不矛盾。[完整八卡 profiling 复核](/Users/zhangfan/project/aico_timedelay_report/xuji_luoji_test/md/nohlt完整八卡profiling复核_20261102.md)

历史 BAR-copy/WC 能力和 Runtime 参数复制路径排查属于额外诊断。现有资料没有证明本轮已修改并恢复该快速路径，因此不将其列为本次已经完成的四项优化之一。

## 9. 配置固化与复用核验

| 层次 | 固化内容 | 核验依据 |
|---|---|---|
| Host 拓扑 | NPU 物理 PCI、NUMA、CPU 对应关系 | 宿主 PCI sysfs 与 NUMA 拓扑，不能只用 Guest 逻辑编号 |
| 虚机定义 | vCPU pinning、四 NUMA cell、strict memnode、HugeTLB RAM 后端 | 运行域 XML、QEMU 后端参数、Host `numa_maps` |
| 应用绑定 | 144 vCPU 对应的显式 CPU 池、启用 CPU binding | 八个 worker 的 `explicit_local`、main/acl/release/IRQ 日志及实际线程亲和性 |
| 内存局部性 | Host RAM 本地分配与 Guest 进程页放置 | 两层 `numa_maps` / `numastat`，以及迁移返回状态 |
| 核隔离 | 144 个业务 CPU 与 48 个维护 CPU 分组 | `isolated`、`nohz_full`、vCPU / emulator 亲和性、IRQ 实际分布 |
| Guest idle | 当前内核可识别的 `nohlt` | Guest 启动参数、内核编译配置、启动日志，必要时同窗口 WFI 计数 |
| 业务结果 | 同请求集、并发、模型、图执行、投机配置 | 保留逐请求输出与重复测试结果，区分业务验收和 profiler 分析 |

复用时应保存一套对应版本的 XML、Guest 启动参数、binding patch、启动脚本与业务结果，避免 48/64/144 vCPU 的历史配置混用。核验 idle 参数时要检查实际被内核识别的证据，不能只看 `/proc/cmdline` 中是否出现了参数文本。

本项目已经完成的优化形成了相互配合的四个环节：**亲和性让访问路径更短，隔离让 CPU 运行更稳定，大页改善内存映射条件，nohlt 降低关键线程交接中的空闲唤醒成本。** 最新业务结果及回退验证支持：这套组合已在当前场景中消除虚机相对裸机的业务性能劣势。
