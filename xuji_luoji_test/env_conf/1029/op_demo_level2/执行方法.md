# 执行方法

## 1. 准备

两侧使用先前已经对齐的 torch_npu post6 环境，在无业务请求窗口中各执行一次。沿用已经完成的直通、大页、核隔离和内存策略。

在原 demo 可正常运行的 Linux Ascend 容器内执行。需要已有 `torch`、`torch_npu`、CANN 和驱动，无需安装其他 Python 包，无需 root。

- 设备编号、CPU 和 NUMA 编号须与之前测试一致，继续使用包内 `placements.json`。
- 容器应保留原始设备编号；脚本会拒绝非空的 `ASCEND_RT_VISIBLE_DEVICES`，避免逻辑设备重编号造成绑核错配。
- `ASCEND_LAUNCH_BLOCKING` 不能为1；脚本会检查。`TASK_QUEUE_ENABLE` 由入口在导入 torch_npu 前固定为0。
- 输出目录必须是新目录。重复测试请更换 `--out`，不要删除已有结果。
- 脚本只绑定新建的诊断进程及其线程。内存策略继承启动环境，不额外修改 NUMA 内存绑定。

如果通过 ZIP 传到服务器，在 ZIP 所在目录执行：

```bash
unzip op_demo_level2.zip
cd op_demo_level2
```

如果已经通过 Git 获取本目录，直接进入仓库中的 `xuji_luoji_test/env_conf/1029/op_demo_level2`，不必解压。

可选校验：Linux 使用 `sha256sum -c SHA256SUMS`；macOS 使用 `shasum -a 256 -c SHA256SUMS`。

## 2. 虚机执行

在上述 `op_demo_level2` 目录下执行：

```bash
python3 runtime_level2.py --placement vm144 --out results/vm_runtime_l2
```

默认设备0，使用现有 VM CPU 池108–125，主线程110–123，ACL线程124，release线程125。queue0 下是否实际存在对应辅助线程，以结果记录为准。

执行结束后，无论退出码是0还是2，都打包整个结果目录：

```bash
tar -czf vm_runtime_l2.tar.gz -C results vm_runtime_l2
```

## 3. 裸机执行

在裸机的同一套诊断包目录下执行：

```bash
python3 runtime_level2.py --placement bare192 --out results/bare_runtime_l2
```

默认设备0，使用现有裸机 CPU 池144–167，主线程146–165，ACL线程166，release线程167。

执行结束后，无论退出码是0还是2，都打包整个结果目录：

```bash
tar -czf bare_runtime_l2.tar.gz -C results bare_runtime_l2
```

两侧都只需要上述一条 Python 命令。无需再运行 `run_suite.py`，无需增加核数或重新跑模型业务测试。

## 4. 本次固定测试内容

| 项目 | 配置 |
|---|---|
| 算子 | `torch.sub`，INT32 `[8]`，预分配输入与输出 |
| 设备 | 设备0，单设备，无 HCCL |
| Host 队列 | `TASK_QUEUE_ENABLE=0` |
| 预热 | 绑核前200次，线程分工绑定后再200次 |
| 正式计时 | 每轮256次调用后同步，共20轮，不开启 profiler |
| 独立采集 | Level 2，128次调用，关闭 AI Core metrics，保留原始采集数据 |
| 内存策略 | 继承运行环境 |

本轮优先获取 Launch 内部可见的 Runtime API。不要将 Level 2 的绝对耗时与之前 Level 1 的耗时相减；两侧应使用本包相同配置比较，实际性能差距以无 profiler 计时为依据。

## 5. 结果与退出码

每侧结果目录中应保留：

| 文件或目录 | 用途 |
|---|---|
| `summary.json` | 运行状态、正确性、计时与采集摘要 |
| `timing_unprofiled.json` | 启动 profiler 之前保存的计时结果 |
| `measurements.csv` | 20轮无 profiler 原始计时 |
| `environment.json`、`threads.json` | 环境、动态库哈希及线程绑核记录 |
| `profile/` | 完整采集目录，包括导出的 trace 和保留的原始数据 |
| `runtime_detail.json` | 找到唯一 trace 后生成的 Runtime API 统计及区间覆盖 |

- **退出码0**：正式计时成功，并找到嵌套在 HostArgs Launch 中的 Runtime API。
- **退出码2**：正式计时成功，但采集失败或没有获得可用的嵌套 Runtime API。保留整个目录；不能解释成 Runtime 耗时为0。
- **退出码1或启动参数错误**：计时或初始化未完成。查看终端报错及存在的 `summary.json`，保留已有文件。

即使退出码0，也可能只多出一个较大的 Runtime 包装调用，仍不足以分解内部锁、复制和提交。分析时先看实际 API 名称与覆盖区间，再决定是否需要少量函数探针。

后续分析需要 `vm_runtime_l2.tar.gz` 和 `bare_runtime_l2.tar.gz` 两个完整结果包，不要只保留截图或 `runtime_detail.json`。
