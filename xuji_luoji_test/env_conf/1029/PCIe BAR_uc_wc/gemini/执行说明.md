# PCIe BAR 空间内存属性 (WC vs UC) 闭环验证工具集

本目录提供一套完整的**端到端闭环验证方案**，用于直接证实或排除以下关键推论：
> **“在 KVM/VFIO 直通下，PCIe BAR 内存属性因 Stage-2 强制降级为 UC（Device-nGnRE），导致 Write-Combining (WC) 彻底失效，产生 ~15-20 μs 的算子下发硬件 Stall 延迟。”**

本方案由两大部分组成：
1. **虚机 / 裸机端硬件流水线探针** (`bar_wc_probe.c` + `run_guest_probe.sh`)：直接测量 CPU 连续小包写入 BAR 时的单指令纳秒延迟与吞吐带宽，从微观硬件层面抓取证据。
2. **宿主机端 Stage-2 页表与补丁核验脚本** (`check_host_bar_wc.py`)：读取 live QEMU 进程与 KVM Stage-2 页表（S2PT），核验 BAR 物理映射到底被配置成了 `Normal-NC` 还是 `Device-nGnRE`。

| :--- | :--- | :--- |
| **`bar_wc_probe.c`** | 虚机 / 裸机 (ARM64) | 核心 C 语言微基准探针，利用 `cntvct_el0` 纳秒计时器测量 128B (16×8B Store) 及 256B memcpy 延迟与吞吐 |

## 一、 虚机与裸机测试：硬件流水线实测 (Guest / Bare-metal)

本测试在**裸机**和**虚机**中分别执行，对比两者在写入 BAR 空间时的真实物理耗时。

### 1. 一键全自动运行

将本目录拷贝至虚机与裸机环境，在终端直接运行：
```bash
cd "xuji_luoji_test/env_conf/1029/PCIe BAR_uc_wc/gemini"

# 赋予执行权限并运行
chmod +x run_guest_probe.sh
./run_guest_probe.sh
```
脚本将自动完成编译，扫描 NPU PCIe 设备，并依次测试系统 DRAM 基线以及所有的 PCIe BAR 资源。

### 2. 手动针对特定 BAR 运行

若需针对已确认的参数 BAR（如 `resource2` 或 `resource4`）精确测试：
```bash
# 1. 手动编译
gcc -O1 bar_wc_probe.c -o bar_wc_probe

# 2. 查看当前 NPU 的 BAR 资源与 Prefetchable 属性
lspci -vvv -d 19e5: | grep -E "(Region.*prefetchable|Memory at)"

# 3. 执行测试 (需 root 权限以 mmap PCIe resource 文件)
sudo ./bar_wc_probe /sys/bus/pci/devices/0000:01:00.0/resource2

# 4. 若系统内核生成了 resource2_wc，可同时执行对比：
sudo ./bar_wc_probe /sys/bus/pci/devices/0000:01:00.0/resource2_wc
```

### 3. 输出判定速查表

| 观测指标 | **Write-Combining 生效 (正常裸机)** | **UC / Device-nGnRE 退化 (异常虚机)** |
| :--- | :---: | :---: |
| **单个 8B Store 耗时** | **1 ~ 3 ns**（进 Store Buffer） | **150 ~ 300 ns**（无缓冲，CPU 流水线 Stall） |
| **128B 连续写 (16次 8B)** | **15 ~ 40 ns** (0.015~0.04 μs) | **2.4 ~ 4.8 μs** |
| **256B memcpy 写入** | **30 ~ 80 ns** (0.03~0.08 μs) | **5.0 ~ 10.0 μs** |
| **等效写入带宽** | **3,000 ~ 8,000 MB/s (3~8 GB/s)** | **20 ~ 60 MB/s** |
| **控制台判定标记** | `[PASS] Write-Combining (WC) 正常生效` | `[CRITICAL] 内存属性已退化为 UC！WC 彻底失效！` |

> [!IMPORTANT]
> **结论定性**：如果在虚机中单个 8B Store 耗时在 **150~300 ns**，且 128~256B 写入达到 **微秒级（3~8 μs）**，即可 **100% 证实硬件写合并失效**。单次算子下发多次写入累计带来的 15~20 μs 刚性底噪即被完全确证。

## 二、 宿主机测试：KVM Stage-2 页表与内核补丁核验 (Host)

本脚本在 **KVM 宿主机** 执行，全只读操作，不写任何寄存器、不挂载/重启/修改任何虚拟机。

### 1. 执行命令

```bash
cd "xuji_luoji_test/env_conf/1029/PCIe BAR_uc_wc/gemini"

# 1. 确认当前运行的虚拟机名称 (例如 instance-00000b34)
sudo virsh --connect qemu:///system list --all

# 2. 导出 Stage-2 页表与 BAR 属性匹配分析
sudo python3 ./check_host_bar_wc.py \
  --vm instance-00000b34 \
  --dump-stage2 \
  --out /tmp/bar_wc_check
```

### 2. 核心证据查看

采集完成后，查看输出目录中的关键文件：
```bash
# 查看整体汇总报告
cat /tmp/bar_wc_check/report.txt

# 查看 Guest BAR IPA 与 Stage-2 页表的实际属性交集
cat /tmp/bar_wc_check/stage2-bar-matches-*.txt

# 查看宿主内核是否包含 ARM64 Normal-NC 补丁标记
cat /tmp/bar_wc_check/kernel-source-evidence.txt (如宿主有内核源码)
```

### 3. 宿主机判定标准

1. **Stage-2 属性**：
   * 若对应的 BAR IPA 范围在 Stage-2 中属性显示为 **`Device-nGnRE`**：**直接证实宿主机 Stage-2 限制了写合并**，触发了 ARMv8 架构的“取交集降级规则”。
   * 若对应的 BAR IPA 范围在 Stage-2 中显示为 **`Normal-NC`**：说明宿主机已经支持并配置了 WC 透传，需转而检查 Guest 侧 Stage-1 页表及 CANN 驱动的映射配置。
2. **内核补丁状态**：
   * Linux upstream 引入了以下补丁才正式支持 ARM64 KVM VFIO 的 Normal-NC 透传：
     * `c034ec84e879` (*KVM: arm64: Introduce new flag for non-cacheable IO memory*)
     * `5c656fcdd6c6` (*mm: Introduce new flag to indicate wc safe*)
     * `8c47ce3e1d2c` (*KVM: arm64: Set io memory s2 pte as normalnc for vfio pci device*)
     * `a39d3a966a09` (*vfio: Convey kvm that the vfio-pci device is wc safe*)
   * 当前宿主内核为 `5.10.0-136.12.0.86.h2196.eulerosv2r12.aarch64`，脚本将自动检查内核树中是否缺少该套特性的 backport。
