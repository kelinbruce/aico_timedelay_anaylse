## Why

电信网络知识问答在单个问题内可以多次调用 `Rag`，每次检索结果都满足当前问题的证据需求，但这些原始结果在回答完成后仍持续进入后续问题的模型上下文。多轮对话会因此累积数万 token 的历史检索内容，挤占当前问题所需的上下文预算，并可能触发无收益的摘要压缩或请求降级。

已完成轮次的最终 assistant 回复已经承载该轮面向后续对话的结论。后续问题需要新的知识证据时可以再次调用 `Rag`，不需要继续携带历史轮次的原始检索 payload。因此系统需要在轮次转换时及时移除全部已完成历史轮次的模型可见 RAG 原文，同时完整保护当前问题的检索结果。

## 目标与非目标（Goals / Non-Goals）

**目标：**

- 每个新问题组装上下文时，当前问题之前全部 canonical 已完成轮次中的 `Rag` 结果均以有界确定性占位形式进入模型上下文，不受通用工具结果数量阈值和最近保留窗口影响。
- 当前问题产生的全部 `Rag` 结果保持完整，直到该问题完成；同一问题内反复组装上下文不得提前压缩这些结果。
- 历史 RAG 微压缩保持幂等，并保持工具调用与结果的结构配对；重新读取历史时不得恢复已压缩的模型可见原文。
- canonical 消息记录继续保留原始 RAG 结果，模型上下文投影的变化不得删除或改写持久化历史。

**非目标：**

- 不改变 `Rag` 的检索、去重、排序、结果 schema、默认 `topK` 或 gateway 行为。
- 不对 RAG 结果生成模型摘要、证据胶囊或来源摘要。
- 不改变其他受信工具现有的数量阈值与最近结果保留规则。
- 不改变 summary compression、large-content 外置、Web API、stream event 或公共 contract。

## What Changes

- 修改历史工具结果微压缩行为：新问题组装上下文时，无条件微压缩当前问题之前全部 canonical 已完成轮次中的 `Rag` capability results。
- 修改当前请求保护边界：当前问题的 RAG 结果始终排除在该专用微压缩行为之外，即使同一问题内发生多次模型与工具迭代。
- 保持通用微压缩兼容性：非 RAG 工具继续遵循既有白名单、触发阈值和最近保留窗口规则。
- 保持存储与渲染一致性：系统只改变模型可见投影，并在后续渲染重新读取 canonical 消息后重放相同替换。

## Feature 影响（Features）

### 修改的 Feature

- `F-4.4 压缩长对话`：历史工具结果压缩增加已完成轮次 RAG 的确定性生命周期边界，减少多轮知识问答的历史检索占用，同时保持当前问题证据完整。

## Function 影响（OpenSpec Capabilities）

### 新增 Function

无。

### 修改的 Function

- `FN-4.5 压缩转储工具结果` → `specs/context-engine/spec.md`
  - 功能边界：历史微压缩从仅按通用工具数量触发，扩展为在每轮转换时压缩上一已完成轮次的全部 RAG 结果，并保持当前轮结果与 canonical 历史不变。
  - 系统质量属性：性能/容量、可靠性/恢复、可测试性、审计/可追溯性。
  - 映射说明：`context-engine` 是 canonical spec；本 change 不触及 `large-content-references` 的大内容外置 Requirements。

## 影响范围（Impact）

- 多轮知识问答的后续模型输入不再重复携带任何已完成历史轮次的原始 RAG payload；历史 assistant 回复仍保持可见。
- 上下文预算评估与后续摘要压缩将观察到已经完成 RAG 专用微压缩的历史投影。
- Context Engine 的微压缩候选选择、幂等状态和 render 重放测试需要覆盖轮次转换规则。
- 无公共 API、配置、数据库 schema、runtime command 或前端行为变化。
