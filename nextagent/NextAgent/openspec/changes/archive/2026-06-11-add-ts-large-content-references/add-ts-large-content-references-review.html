add-ts-large-content-references

这份页面面向设计评审，提炼当前 change 的黑盒目标、实现边界、核心策略、固定流程、 决策契约、输出、失败/降级规则、典型示例和评审重点。页面只描述稳定业务语义和实现约束， 不展开代码细节。

Primary Owner: agent-context-engine 类型: OpenSpec Change 焦点: Large Content Projection 状态: Apply-ready

黑盒目标

当请求生命周期中出现无法安全 inline 的内容时，系统必须把它从“原文直接拼接” 收敛成“owner-scoped 引用 + 按需投影”的稳定行为。对外可观察到的效果是： 小内容正常 inline；大内容按预算和权限进入 prompt；关键内容读不到就显式失败； 非关键内容读不到就显式降级；模型、前端、日志和 stream 都看不到物理路径或越权内容。

核心黑盒承诺：系统不会通过静默截断、静默丢弃、路径泄露或 fake owner identity 来“勉强成功”。

Change 边界

  • 负责：什么时候 externalize、什么时候读 ref、谁能读、读多少、读失败如何分流。
  • 负责：Context Engine / MessageContentLoader 对大内容的同步消费契约。
  • 负责：attachment、长消息、archived capability result、replacement 内容进入上下文时的统一语义。
  • 不负责：重写 Query Policy 阶段模型、summary 生成、附件上传规则、后台 projection job、下载器或文件浏览器。
  • 不负责：改变 attachment 或 summary 的领域 ownership。

当前核心实现策略

  • 写时 externalize：超阈值或天然不该 inline 的内容先存为 LargeContentRef。
  • 读时同步 projection：只在真正消费时按 identity、purpose、budget 做投影。
  • Query Policy 只做决策：预算、trim、archive、replacement 由 Query Policy 决定，不提前读正文。
  • Context Engine 单点判定关键性：latest-request-critical 只能由 ContextEngine.build(...) 划定。
  • 失败显式化：关键内容失败阻断，非关键内容失败降级。

核心实现流程

1
内容产生时判断是否 inline
消息正文、attachment blob、capability result 等内容先判断是否还能安全 inline；不能 inline 的内容 externalize 为 LargeContentRef。
2
组装前收集候选，不读正文
Context Engine 收集 current request、prior history、attachment context、capability result refs 和 replacement 内容，只建立候选集合。
3
Query Policy 做预算与 compaction 决策
决定 trim、archive、replacement、drop 和 degrade 路径，但不读正文。
4
Context Engine 单点划定 latest-request-critical
基于当前 root request、任务语义和等价替代物，决定哪些内容失败时必须阻断请求。
5
执行 authorized projection
真实消费时才按 caller identity、gateway、ref 状态、purpose 和 budget 选择 FULL / RANGE / SUMMARY / EXCERPT / METADATA_ONLY。
6
失败按关键 / 非关键两路分流
关键内容失败返回 failure / insufficient-context；非关键内容失败返回 degradation marker。
7
渲染最终模型输入
小内容 inline，大内容以预算允许的 projection 进入 prompt，失败内容以显式 marker 或 failure 呈现。
8
下游只消费安全结果
model invocation、history、stream、observability 只消费已处理结果，不得绕过 Context Engine 回头读物理路径。
9
输出 machine-readable 证据
每次 externalize、projection、replacement、failure、degrade 都要产出 safe diagnostics 和 lineage evidence。

决策契约

问题 当前契约
什么时候存 ref 当内容已不适合继续作为 inline 事实跨越 message / prompt / stream / log / archive 边界传播时。
什么时候读 ref 只有在真实消费流程需要正文或其投影时才读；Query Policy 决策阶段不得 eager 读正文。
谁能读 只有携带真实 IdentityContext 的合法调用链能读取正文级内容；不能从 ref 反推 fake owner。
读多少 按 purpose + budget + policy 选择 FULL / RANGE / SUMMARY / EXCERPT / METADATA_ONLY。
读失败怎么办 关键内容失败阻断；非关键内容失败显式降级，并输出 diagnostics。

latest-request-critical 判定公式

latest-request-critical = 当前请求显式绑定 AND 离开后基本任务语义失真 AND 当前装配中不存在等价已保留替代物
单点判定者: Context Engine 禁止: 其他模块各自重定义

输出

  • ContextAssembly
  • rendered model-facing messages
  • ArchivedRef
  • CleanupAction.contentRef
  • LargeContentProjection 结果
  • compactionReasons()
  • contextWindowSelectionReasons()
  • safe degradation marker / omission reason / placeholder
  • 可供 runtime、stream、observability 使用的 safe lineage evidence

失败 / 降级规则

  • 关键内容失败：返回 failure、insufficient-context 或明确 degraded outcome。
  • 非关键内容失败：返回 degradation marker / placeholder / omission reason。
  • 无 identity：只能 METADATA_ONLY，不得伪造 owner。
  • cross-owner：返回 not-found / unavailable 风格安全结果，不暴露存在性。
  • 已有等价替代物：原始大内容不再升级为 latest-request-critical。
  • 禁止静默处理：不得静默截断、静默丢弃、静默降级或暴露路径。

典型示例

  1. 当前请求明确要求“根据超大附件回答”，附件成为 latest-request-critical，读不到就阻断。
  2. 当前请求正文本身超长，写时 externalize，装配时不得拿 excerpt 冒充完整正文。
  3. 大 capability result 被 compaction 决定 archive，后续通过 ArchivedRef + contentRef 继续消费。
  4. 较早历史中的 archived result 读取失败，但当前请求不依赖它，系统显式降级并继续执行。
  5. 当前调用没有真实 caller identity，只能拿到 METADATA_ONLY。
  6. cross-owner 读取返回 not-found / unavailable，不泄露该 ref 是否存在。
  7. 当前请求绑定附件，但本次装配已保留等价 excerpt / summary，原始大内容不再算 critical。
  8. Query Policy 阶段看到 ref，只能做预算与 compaction 决策，不能提前读正文。

评审重点

  • 边界是否足够窄：是否真的只处理 large-content 消费逻辑，而没有顺手重做 attachment / summary 子系统。
  • 判定者是否唯一：latest-request-critical 是否只由 Context Engine 单点判定。
  • 决策与消费是否分离：Query Policy 是否只做预算与 compaction，Context Engine / loader 是否才负责读正文。
  • 失败语义是否明确：关键内容失败是否必然阻断，非关键内容失败是否必然显式降级。
  • 安全边界是否稳定：无 identity、cross-owner、路径不暴露、不能 fake owner 这些规则是否在实现层也能落住。
  • 替代物逻辑是否收敛：存在等价 excerpt / summary / replacement 时，是否能防止原始大内容被过度提升为 critical。
  • 测试是否覆盖主流程：九步主流程和 8 个典型示例是否都能映射到 characterization tests。
这份 change 值得评审的关键，不是“有没有 large content store”，而是 “externalize、budget/compaction、authorized projection、critical/non-critical failure split 是否被收敛成唯一稳定语义”。
